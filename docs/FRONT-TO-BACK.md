## F-003 · Типи в JSON і заголовок Authorization (PHP)
**Статус:** done
**Дата:** 2026-10-29
**Стосується:** усі відповіді API, авторизація адмінки, розгортання

Бекенд буде на PHP, хостинг, найімовірніше, GoDaddy (Apache, cPanel). Є кілька типових для PHP речей, через які фронт зламається, хоча формально відповідь «схожа» на контракт.

1. **Числа — числами.** `id`, `total`, `active`, `page`, `perPage`, `created`, `index`, значення в `byCategory` і `missing` мають бути JSON-числами (`42`), а не рядками (`"42"`). PDO з MySQL за замовчуванням повертає рядки — потрібні `PDO::ATTR_EMULATE_PREPARES => false` + `PDO::ATTR_STRINGIFY_FETCHES => false` або явне приведення `(int)`.
   _Наслідок, якщо ні:_ в адмінці не працюють «Изменить»/«Удалить» (фронт шукає фразу за числовим `id`), а `exclude` у `GET /api/message` порівнює ID некоректно.
2. **Булеві — булевими.** `isActive` — `true`/`false`, а не `1`/`0` чи `"1"`/`"0"` (TINYINT з MySQL). Приводити `(bool)`.
   _Наслідок, якщо ні:_ рядок `"0"` у JS істинний — приховані фрази показуються як «Показывается».
3. **Об'єкти — об'єктами, навіть порожні.** `text`, `byCategory`, `missing`, `fields` мають бути `{}`, а не `[]`. `json_encode([])` дає `[]` — для порожніх асоціативних масивів використовувати `(object)[]` або `JSON_FORCE_OBJECT` точково.
   Також для коректної кирилиці/латиської: `JSON_UNESCAPED_UNICODE` (не обов'язково, але читабельніше в логах).
4. **Заголовок `Authorization` має доходити до PHP.** На Apache з PHP у режимі CGI/FastCGI він часто зрізається. Перевірити й за потреби додати в `.htaccess`:
   ```apache
   RewriteEngine On
   RewriteCond %{HTTP:Authorization} .
   RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]
   ```
   _Наслідок, якщо ні:_ усі `/api/admin/*` повертають `401`, адмінка після входу одразу викидає на форму логіну.
5. **Роздача фронта.** `/admin/` має віддавати `frontend/dist/admin/index.html` (на Apache працює `DirectoryIndex index.html`), а `/api/*` — іти в PHP. Правила `.htaccess` для `/api` не повинні перехоплювати статику.

Прошу врахувати з самого початку і відповісти, якщо щось із цього не підходить під вашу реалізацію.

### Відповідь

1. **Числа** — завжди JSON-числами (нативні типи PDO + явне приведення `(int)`).

## F-005 · Статистика відвідувань: сканування, відкриття, послання по днях
**Статус:** done
**Дата:** 2026-11-03
**Стосується:** нові ендпоінти `POST /api/visit`, `GET /api/admin/visits`; лічильник у `GET /api/message`; `API.md` (новий розділ)

### Навіщо

Запит клієнта: «посмотреть статистику по количеству сканирований/обращений по периоду и дню». Сторонню аналітику (Google Analytics тощо) не беремо: у ЄС їй потрібен банер згоди на cookies, а це зайвий екран перед посланням. Рахуємо самі, лише кількості, без персональних даних.

Фронт уже зробив свою частину на моку (`frontend/src/shared/api/mock/visits.js` імітує контракт нижче): вкладка «Статистика» в адмінці і відправка відкриттів зі сторінки користувача. Прохання — реалізувати бекенд за цим контрактом або запропонувати зміни. Після згоди внесемо в `API.md` разом із B-001, F-001…F-004 і підвищенням версії.

### Що рахуємо (три метрики на день)

| Метрика | Що це | Де рахується |
|---------|-------|--------------|
| `visits` | Відкриття сайту — будь-яке: QR, посилання, яким поділились (кнопка «Поделиться» на екрані послання), адреса вручну | `POST /api/visit` |
| `scans` | Відкриття саме з QR на стаканчику (підмножина `visits`) | `POST /api/visit` з `source: "qr"` |
| `messages` + `byLang` | Видані послання (усього і по мовах `lv`/`en`/`ru`) | сам бекенд у `GET /api/message` при відповіді `200` |

Як фронт відрізняє QR: QR на стаканчиках вестиме на `https://<домен>/?qr`. Фронт бачить параметр, шле `source: "qr"` і прибирає `?qr` з адреси (щоб він не потрапив у закладки й посилання). Бекенду це знати не потрібно — лише поле `source`.

Повторне сканування протягом 20 хв показує те саме послання з localStorage і **не викликає** `GET /api/message`, тож `messages` < `visits` — це очікувано (в адмінці пояснено).

**День** — календарна дата за часом **Europe/Riga** (клієнт у Латвії; «вчора» має означати латвійське вчора, а не UTC). Пропозиція: дату рахувати в PHP (`new DateTimeImmutable('now', new DateTimeZone('Europe/Riga'))`), а не в MySQL — на shared-хостингу таблиці часових поясів MySQL можуть бути не завантажені, і `CONVERT_TZ` поверне `NULL`.

### `POST /api/visit` — публічний

Фронт викликає один раз при кожному відкритті сторінки користувача (до вибору мови), `fetch` з `keepalive: true`, відповідь не читає, помилки ігнорує.

Тіло: `{ "source": "qr" }` або `{ "source": "direct" }`.

| Ситуація | Відповідь |
|----------|-----------|
| Нормальний запит | `204` без тіла, `Cache-Control: no-store`; `visits += 1`, а при `source = "qr"` ще й `scans += 1` |
| `source` відсутній, `null`, невідомий рядок, не рядок | рахуємо як `direct`, `204` (це лічильник, а не форма — суворість тут нічого не дає) |
| Тіло порожнє / не JSON / не об'єкт | `400 bad_request` (як скрізь у вас), нічого не рахується |
| Помилка БД | `500 server_error` у лог; фронт це ігнорує |

Авторизації немає. Лічильник може «накрутити» будь-хто, хто шле запити вручну, — для статистики кав'ярні вважаю це прийнятним; ліміт за IP не просимо (якщо вирішите додати — лише так, щоб звичайний відвідувач не відсікався, і без збереження IP довше, ніж треба для ліміту). Боти, що не виконують JS, у `visits` не потрапляють — це плюс підходу.

### Лічильник у `GET /api/message`

При відповіді `200`: `messages += 1` і `byLang[lang] += 1` за сьогоднішній ризький день. **Важливо:** помилка запису лічильника не повинна ламати видачу послання — краще втратити одну одиницю статистики (і написати в лог), ніж показати користувачу помилку. `400`/`404` не рахуються. Контракт відповіді `GET /api/message` не змінюється.

### `GET /api/admin/visits?from=YYYY-MM-DD&to=YYYY-MM-DD` — адмінка

Потрібен `Authorization: Bearer <token>` (без нього `401`, як усі `/api/admin/*`).

Параметри (обидва обов'язкові; фронт завжди шле обидва): `from`, `to` — дати за ризьким часом, включно з обома кінцями.

Відповідь `200`, `Cache-Control: no-store`:

```json
{
  "from": "2026-10-05",
  "to": "2026-11-03",
  "timezone": "Europe/Riga",
  "total": { "visits": 1600, "scans": 1403, "messages": 1324, "byLang": { "lv": 674, "en": 254, "ru": 396 } },
  "days": [
    { "date": "2026-10-05", "visits": 38, "scans": 33, "messages": 30, "byLang": { "lv": 15, "en": 6, "ru": 9 } },
    …
  ]
}
```

- `days` — **кожен** день періоду по зростанню дати, і дні без даних теж (нулі). Фронт малює графік по днях і на пропуски не розрахований.
- `byLang` — завжди всі три ключі (`lv`, `en`, `ru`) у цьому порядку, навіть із нулями (як `byCategory` у BE-008).
- `total` = сума `days` (фронт її не перераховує).
- Усі числа — JSON-числа.
- Дати в майбутньому дозволені (нулі) — фронт їх не шле, але й помилки не треба.

Помилки — `400 bad_request` (без `fields`, як у фільтрах BE-005):

| Ситуація | |
|----------|---|
| `from` або `to` відсутній, порожній, не `YYYY-MM-DD` або неіснуюча дата (`2026-02-30`) | `400` |
| `from > to` | `400` |
| Період довший за **366 днів** включно з кінцями | `400` |

Фронт перевіряє те саме до запиту (`frontend/src/shared/dates.js`, `MAX_PERIOD_DAYS = 366`), тож `400` у UI не очікується.

### Зберігання — пропозиція, рішення за вами

Без журналу подій і без персональних даних (IP, User-Agent, cookies не зберігаються) — лише агреговані лічильники по днях, наприклад:

```sql
CREATE TABLE daily_stats (
  day DATE NOT NULL,                -- дата за Europe/Riga
  metric VARCHAR(16) NOT NULL,      -- visit | scan | message_lv | message_en | message_ru
  count INT UNSIGNED NOT NULL DEFAULT 0,
  PRIMARY KEY (day, metric)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

INSERT INTO daily_stats (day, metric, count) VALUES (?, ?, 1)
  ON DUPLICATE KEY UPDATE count = count + 1;   -- MySQL 5.7 ок, атомарно
```

`messages` = сума `message_*`. ~5 рядків на день → ~1 800 на рік; зберігати безстроково. Звіт за період — один `SELECT … WHERE day BETWEEN ? AND ? GROUP BY day, metric`, порожні дні доповнює PHP.

### Що на фронті вже є

- `frontend/src/app/main.js` → `trackVisit()` (виклик `POST /api/visit`), `frontend/src/shared/api/real.js` → `trackVisit`, `getVisits`.
- Адмінка: вкладка «Статистика» (`frontend/src/admin/visits.js`) — періоди «Сегодня / Вчера / 7 дней / 30 дней / Этот месяц / Прошлый месяц» і довільний «с … по …», плитки, графік відкриттів по днях, таблиця по днях з підсумком.
- Поки бекенд не готовий: на проді `POST /api/visit` дасть `404` — фронт мовчки ігнорує, користувач нічого не помітить; вкладка «Статистика» покаже помилку.

Питання до вас: чи підходить формат і поведінка помилок; чи є заперечення щодо підрахунку дати в PHP за Europe/Riga.
