## Автентифікація адміна (BE-004)

Рішення — [D-20 … D-23](decisions.md). Статус: ✅ — зроблено й перевірено тестами (`tests/api/auth.php`, `tests/run.php`), ⏳ — заплановано.

| Захід | Статус |
|-------|--------|
| Один адмін, логін і **хеш** пароля в конфігурації; `password_verify` (підтримує bcrypt і argon2id, алгоритм береться з самого хеша) | ✅ |
| Guard у `Kernel` **до** маршрутизації: усі шляхи `/api/admin/*`, окрім `POST /api/admin/auth/login`, вимагають токена; невідомий адмін-шлях без токена — `401`, а не `404`; новий адмін-ендпоінт захищений автоматично (D-20) | ✅ |
| Токен — JWT HS256 без бібліотек; header порівнюється як константа (`alg: none`/`HS512` неможливі), підпис — `hash_equals`, payload розбирається лише після підпису, base64url канонічний (D-21) | ✅ |
| Термін токена **7 діб** за замовчуванням (`TOKEN_TTL_HOURS=168`, діапазон 1…720, рішення користувача). Компроміс: вкрадений токен «живе» довше, а фронт тримає його в `localStorage` | ✅ |
| Ротація: ключ підпису = `HMAC-SHA256(TOKEN_SECRET, ADMIN_PASSWORD_HASH)`; зміна пароля, `TOKEN_SECRET` або `ADMIN_LOGIN` анулює всі видані токени. При підозрі на витік достатньо змінити пароль | ✅ |
| Однакова відповідь `401 Invalid credentials` для невірного логіна й невірного пароля; `password_verify` виконується завжди, без короткого замикання, тож час відповіді не розкриває існування логіна (D-23) | ✅ |
| Ліміт спроб входу за IP: 5 невдалих за 15 хв → `429` + `Retry-After`; перевіряється **до** `password_verify`; заблоковані запити не записуються й не продовжують блокування; успіх лічильник не збільшує; прострочені записи видаляються (D-22) | ✅ |
| Ліміт не за логіном (інакше будь-хто міг би заблокувати адміна) | ✅ |
| IP лише з `REMOTE_ADDR`; `X-Forwarded-For` і подібні заголовки ігноруються (їх підробляє клієнт) | ✅ |
| Некоректна конфігурація (`ADMIN_LOGIN`, `ADMIN_PASSWORD_HASH`, `TOKEN_SECRET` < 32 символів, `TOKEN_TTL_HOURS`) → `500` на логіні й на guard'і, доступ не відкривається; у лог — лише назва змінної | ✅ |
| Публічні шляхи (`/api/message`, `/api/health`) не читають адмін-конфігурацію й не залежать від неї | ✅ |

## Що навмисно не робимо

- **CORS** — фронт і API на одному домені, тож не потрібен (і не вмикаємо «про запас»).
- **Cookie й сесії** — токен передається заголовком, тому CSRF-захист не потрібен.
- **Ролі й керування користувачами** — адмін один (за контрактом).
- **Ліміт на кількість посланнь** — рішення клієнта: одна людина може отримати кілька (F-002). Повтори обмежує фронт.
