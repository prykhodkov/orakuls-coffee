# Розгортання

> **Статус: хостинг ще не налаштований.** Тут зафіксовано те, що відомо про середовище, і план. Покроковий порядок деплою з'явиться після задачі [BE-009](tasks/BE-009-hosting-deploy/task.md).

## Середовище

GoDaddy Web Hosting (cPanel, Apache, shared).

| Компонент | Версія | Примітка |
|-----------|--------|----------|
| PHP | **8.4** | Доступні 8.2 / 8.3 / 8.4, типова 8.3 — **8.4 треба вибрати вручну** в cPanel («Select PHP Version»). 8.1 і старіші — платний Extended Support |
| MySQL | **5.7** (5.7.38) | Найновіша для cPanel-хостингу; MySQL 8.0 є лише на Managed WordPress. Запасний варіант — MariaDB 10.6 |

Версії взято з довідки GoDaddy через пошукову видачу (сторінку напряму прочитати не вдалося). **Перед початком деплою звірити реальні версії в cPanel** і виправити цей файл та `docs/BACKEND.md`.

Обмеження shared-хостингу, які впливають на код: немає root-доступу, довгоживучих процесів, CLI може бути недоступний (тому схема БД має імпортуватись через phpMyAdmin), `.htaccess` доступний.

## Цільова топологія

```
https://<домен>/        ─ статика фронта   (frontend/dist)
https://<домен>/admin/  ─ статика адмінки  (frontend/dist/admin)
https://<домен>/api/*   ─ PHP-бекенд
```

Один домен, CORS не потрібен.

## Розкладка файлів на сервері (план BE-009)

Код і секрети лежать **вище** веб-кореня, у `public_html` — лише те, що має бути публічним:

```
~/orakuls/                  вище public_html, недоступне по HTTP
    src/                    код застосунку
    .env                    секрети (створюється вручну, один раз)
~/public_html/
    index.html, assets/…    збірка фронта
    admin/                  збірка адмінки
    api/index.php           точка входу API
    .htaccess               правила (нижче)
```

Поточний `public/index.php` розрахований на локальну структуру (`../src/bootstrap.php`). Для хостингу точка входу буде адаптована: вона визначить `APP_ROOT` на `~/orakuls` і підключить звідти `bootstrap.php`. Решта коду від розкладки не залежить — шляхи беруться від `APP_ROOT`.

## Що має робити `.htaccess` (BE-009)

- передавати заголовок `Authorization` у PHP (`RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]`) — без цього всі `/api/admin/*` повертатимуть `401` (F-003, п. 4);
- спрямовувати `/api/*` на `api/index.php`, не чіпаючи реально існуючі файли й папки;
- віддавати `/admin/` як `admin/index.html`;
- забороняти доступ до службових файлів;
- перенаправляти HTTP на HTTPS.

## База даних на хостингу

Порядок розгортання схеми (без CLI):

1. cPanel → **MySQL Databases**: створити БД і користувача, додати користувача до БД з усіма правами (`ALL PRIVILEGES`). Значення — у `.env` на сервері (`DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASS`).
2. cPanel → **phpMyAdmin** → у лівій панелі обрати щойно створену **порожню** базу → вкладка **Import** → файл `database/schema.sql` → кодування файлу `utf-8` → **Go**. Файл створює таблиці `migrations`, `phrases` і записує в `migrations` усі міграції, які в нього вже входять.
3. Перевірити: `SHOW TABLES;` показує `migrations` і `phrases`; `SELECT * FROM migrations;` — застосовані міграції.
4. **Сід не імпортується.** Він працює лише з БД, назва якої закінчується на `_test`. Реальні фрази завантажує адмін через імпорт (BE-007).

Наступні зміни схеми приходять як нові файли `database/migrations/NNN_*.sql` разом з оновленим `schema.sql`. На чинній БД виконується **лише новий** файл (phpMyAdmin → вкладка SQL → вставити вміст → Go) — повторний імпорт повного `schema.sql` не потрібен. Якщо на хостингу є CLI/SSH, те саме робить `php bin/migrate.php` (таблиця `migrations` показує, що вже застосовано). Після ручного виконання міграції треба вручну додати її ім'я в `migrations`: `INSERT INTO migrations (name, applied_at) VALUES ('NNN_name.sql', UTC_TIMESTAMP());`, інакше runner спробує застосувати її вдруге.

Тестова БД `orakuls_test` існує тільки локально в Docker.

## Деплой фронта і бекенда

Відкрите питання (не узгоджено з фронтом): `frontend/dist/` не лежить у git, тож `git pull` на сервері готового фронта не дасть. Пропозиція — два незалежні кроки: збірка й заливка статики; заливка API. Один скрипт, що заливає все разом, може перезаписати чужі зміни. Рішення — в BE-009 / BE-010, узгодження — через `docs/BACK-TO-FRONT.md`.

## Логи на хостингу

Бекенд пише лише через `error_log()`. У BE-009 треба з'ясувати, куди він іде на цьому хостингу (`ini_get('error_log')`), переконатись, що файл не публічний і що лог ротується хостингом або іншим способом не росте безмежно.

## Адмін і IP клієнта (BE-004 → BE-009)

- **Боєві облікові дані** розробник створює на сервері перед запуском за процедурою з [configuration.md](configuration.md) (`bin/hash-password.php`, `TOKEN_SECRET` не коротший за 32 символи, хеш у `.env` — в одинарних лапках): пароль передається клієнту безпечним каналом, у серверному `.env` лишаються лише хеш пароля й `TOKEN_SECRET`. Термін сесії адміна — 7 діб. Зміна пароля анулює всі видані токени.
- **IP клієнта.** Ліміт спроб входу (5 за 15 хв, [D-22](decisions.md)) рахується за `REMOTE_ADDR`; `X-Forwarded-For` код свідомо ігнорує (BE-004). Якщо хостинг стоїть за проксі, цей IP буде спільним для всіх, і чужі невдалі спроби блокуватимуть адміна. Тому в BE-009 обов'язкова перевірка діагностичним скриптом; якщо `REMOTE_ADDR` не справжній, потрібне рішення користувача, якому заголовку довіряти. Результат перевірки записується сюди.

## Перевірка після деплою

```
docker compose run --rm --no-deps php php tests/smoke.php https://<домен>
```

Smoke не відправляє неправильних облікових даних (вони рахуються в ліміт). Плюс ручна перевірка `login` → `me` з токеном (чи доходить `Authorization`) і відкриття `/` та `/admin/`. Повний список критеріїв — в BE-009.
