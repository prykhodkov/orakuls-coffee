## 2. Проєктні рішення

### 2.1. М'яке правило мов (Частина А) — точно

У `PhraseValidator::validate()` цикл по `Languages::CODES` змінюється так:

| Значення `text[$lang]` | Раніше | Тепер |
|---|---|---|
| ключа немає | `text.xx = required` | порожній переклад `""` (помилки немає) |
| `null` | `text.xx = invalid` | порожній переклад `""` (помилки немає) |
| не рядок (число, `true`/`false`, масив, об'єкт, `[]`) | `invalid` | `invalid` (без змін) |
| рядок: невалідний UTF-8, керівні символи, > 500 | `invalid` / `too_long` | без змін |

Наслідки: `text: {}` / `[]` → усі три мови порожні → `fields = { text: "empty" }` (раніше три `required`). `text` відсутній → `text: required` (без змін); `text` не об'єкт → `invalid` (без змін). Код `required` для `text.xx` більше **не існує**. `empty` ставиться, коли немає помилок `text.xx` і всі три тексти після trim порожні (відсутні й `null` — теж порожні). Решта правил (`category`, `isActive`, trim, довжина, керівні символи, порядок ключів у `fields`) — без змін.

### 2.2. Імпорт — компоненти і порядок

- `PhraseRepository::createMany(array $inputs): int` — `list<PhraseInput>`, повертає кількість вставлених. **Керує транзакцією сам**: `beginTransaction()`, пакети по `INSERT_BATCH = 100` (`array_chunk`), `commit()`. Будь-який `Throwable` → `rollBack()` (лише якщо `inTransaction()`) і той самий виняток далі (контролер не ловить його: `ErrorHandler` віддасть `500`). Порожній список → `0` без жодного запиту й без транзакції. Для кожного пакета — окремий prepared `INSERT` на `count($batch)` рядків: `(?, ?, ?, ?, ?, UTC_TIMESTAMP(), UTC_TIMESTAMP())` × N, параметри: `category` (STR), `text_lv`, `text_en`, `text_ru` (STR), `is_active` (INT = 1/0). Колонки текстів — з `Languages::column()`.
- `PhraseController::import()` — порядок: `Request::json()` (400) → перевірка `items` (422) → цикл по елементах → (лише якщо є валідні) `createMany` → відповідь.
- Константа `MAX_IMPORT_ITEMS = 1000` у контролері.

### 2.3. Правила контролера (точно)

1. `$data = $request->json()`.
2. `items` відсутній (`!array_key_exists`) → `ApiException::validation(['items' => 'required'])`.
3. `items` не масив, або непорожній і **не** список (`$items !== [] && !array_is_list($items)`) → `['items' => 'invalid']`. Порожній масив — ок (див. факт 2).
4. `count($items) > 1000` → `['items' => 'too_many']`, нічого не зберігається.
5. Для кожного елемента (ключ `$index` — позиція в списку з 0):
   - не масив, або непорожній список (`[1,2]`) → помилка елемента `['item' => 'invalid']` (елемент `[]`/`{}` — це порожній об'єкт: іде до валідатора);
   - інакше `unset($item['isActive'])` (імпортовані завжди активні; значення від клієнта ігнорується, навіть невалідне), потім `PhraseValidator::validate($item)`; `input === null` → `errors[] = ['index' => $index, 'fields' => $fields]`; інакше `$inputs[] = $input`.
6. Якщо `$inputs !== []` — `(new PhraseRepository(Db::pdo()))->createMany($inputs)`; інакше БД **не відкривається** (0 запитів).
7. Відповідь `200`: `{"created": N, "errors": [...]}`; `errors` — список (не `null`), зростання `index` (природно, бо цикл проходить по порядку); `Cache-Control: no-store`.

Порядок створених записів = порядок валідних елементів у запиті (зростаючі `id`).

## 5. Крок 2 (Частина А). Тести BE-006 під нове правило

Це **заміна очікувань**, а не послаблення: старі «required» стають «успіхом», нові випадки додаються.

**`tests/run.php`:**
1. `phraseValidator: text — немає → required; не об'єкт → invalid; {} і [] — об'єкт без ключів`: для `['text' => []]` очікувати `['text' => 'empty']`; в назві тесту замінити хвіст.
2. `phraseValidator: text.xx — немає ключа → required; …`: переписати. Для кожної мови: ключа немає → `[]` (немає помилок) **і** `input->text[$lang] === ''`; значення `null` → теж `[]` і `''`; `5`, `true`, `false`, `['x']`, `[]`, `1.5` → `["text.{$lang}" => 'invalid']`; невалідний UTF-8 → `invalid` (як було). Нова назва: «text.xx — немає ключа або null → порожній переклад; не рядок → invalid; …».
3. `phraseValidator: text = empty …`: рядок `assertSame(['text.ru' => 'required'], pvFields(...['lv' => '', 'en' => '']))` замінити на `['text' => 'empty']`; додати: усі три `null`; два ключі відсутні, третій `""`; `text` з єдиним ключем `lv: "  "`; і успіх: `['en' => 'x']` (решта відсутні) → `[]`, `input->text === ['lv' => '', 'en' => 'x', 'ru' => '']`.
4. `phraseValidator: кілька помилок …`: у другому `assertSame` (довгий) прибрати `'text.en' => 'required'` — очікування стає `['category' => 'required', 'text.lv' => 'too_long', 'text.ru' => 'invalid', 'isActive' => 'invalid']`.

**`tests/api/phrases-write.php`:**
1. `форма text …`: для `{}` / `[]` (три місця: `(object) []`, сирий `{"text":{}}`, `[]`) очікувати `['text' => 'empty']` замість `$allRequired`; у назві прибрати «{} → три required»; випадок «без en» перетворити на успіх: `POST` з `text: {lv: 'a', ru: 'c'}` → `201`, `text.en === ''` у відповіді й у БД (`rowOf`); у циклі нерядкових значень прибрати `null` зі списку `invalid`-значень (`[5, true, [], ['x'], 1.5]`) і додати окремий успіх: `POST` з `en: null` → `201`, `en === ''`.
2. Додати **PUT**: на фразі сіду `PUT` з `text` без ключа `en` → `200`, `text.en === ''` (повна заміна: попередній `en` не зберігається), `createdAt` без змін.
3. Інші тести файла не чіпай. Перевір `grep -n "required" tests/api/phrases-write.php tests/run.php`: `required` лишається тільки для `category` і `text` (відсутній).

## 12. Пастки

- **Частина А — першою і окремо зеленою.** Не змішуй зміни валідатора з імпортом: замовник закомітить їх окремо.
- **`{}` та `[]` після `json_decode` однакові** (факт 2): не намагайся відрізнити їх; `items: {}` → порожній список, елемент `{}` → порожній об'єкт.
- **Не покладайся на `lastInsertId`** після багаторядкової вставки та `commit`.
- **Відкат**: у тесті 16 помилковий рядок має бути в **останньому** пакеті, а перед ним — щонайменше один успішний пакет (інакше мутація «без транзакції» не буде помітна). Тригер завжди видаляй у `finally`, інакше він зламає наступні тести.
- **`assertSame` на масивах чутливий до порядку ключів** — порівнюй `fields` у порядку `category`, `text`/`text.lv|en|ru`, а `errors` — у порядку `index`.
- **Контрольні символи в JSON-тілах** тестів кодуй `json_encode` (`JSON_THROW_ON_ERROR`); зламаний JSON передавай рядком.
- **Тест швидкодії** не повинен бути хиткім: вимога — < 10 с; фактично ≈ сотні мс. Не став жорсткіших лімітів.
- **BE-005/BE-006 тести лишаються зеленими** (крім свідомо змінених очікувань у кроці 2).
