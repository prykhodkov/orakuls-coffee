# BE-007 · Масовий імпорт фраз

| Поле | Значення |
|------|----------|
| Тип | Story |
| Пріоритет | Medium |
| Компонент | backend |
| Залежить від | BE-006 (`PhraseValidator`, `PhraseInput`, методи запису в `PhraseRepository`, `withFreshSeed`) |

## Опис

Як адмін, я хочу завантажити сотні фраз одним запитом (з CSV/Excel), щоб швидко наповнити базу. Файл розбирає фронт і шле готовий масив; бекенд валідує кожен елемент, зберігає валідні, а по невалідних повертає звіт.

Захищати ендпоінт окремо не потрібно: усе під `/api/admin/` закрите `AdminGuard` (D-20).

Як фронт це використовує (`frontend/src/admin/import.js`, `parse-sheet.js`): файл розбирається на фронті; кожен рядок проходить ту саму перевірку, що й форма фрази; на бекенд летять **лише валідні рядки**, шматками по **≤ 1000** (`CHUNK_SIZE`), кожен елемент — `{ category, text: { lv, en, ru } }` (усі три ключі завжди є, тексти вже обрізані `trim()`). Фронт читає `created` та `errors[].index` (мапить `index` на номер рядка файла в межах шматка) і показує підсумок; на `401` повертає на вхід, на будь-яку іншу помилку шматка — зупиняє імпорт і пише «Импорт прерван на строке …». Тож бекенд-помилки рівня запиту (`422` про `items`) для справжнього клієнта практично недосяжні, але поведінку треба визначити.

Прийняті рішення (докладно — `backend/docs/decisions.md`; нові D-xx з'являться разом із реалізацією):
- **Та сама валідація, що й у BE-006**: `Domain\PhraseValidator::validate()` викликається для кожного елемента без жодних поблажок — зокрема юнікодний trim, заборона керівних символів, довжина в символах.
- **М'яке правило мов — скрізь (рішення користувача, 2026-11-01).** `API.md` вимагає лише, щоб значення мов були рядками, а хоча б одна була непорожньою; що відсутній ключ мови — помилка, ніде не сказано (це була наша власна, надто сувора трактовка в BE-006). Тому **відсутній ключ мови в `text` і значення `null` = порожній переклад `""`**, а не помилка — і для імпорту, і для `POST`/`PUT` (BE-006); так само, як у фронті (`input?.text?.[lang] ?? ''`). Значення іншого не-рядкового типу (число, `true`/`false`, масив, об'єкт) — як і раніше `invalid`. Наслідки: `text: {}` / `[]` більше не дає трьох `required`, а дає `text: "empty"`; `text` без ключа взагалі лишається `required`, `text` не-об'єкт — `invalid`. Це **змінює вже закомічений BE-006** (див. «Обсяг → Переробка BE-006»). Ціна м'якості: опечатка в імені ключа (`"eng"` замість `"en"`) не дає помилки, текст мовчки не зберігається — якщо при цьому інші мови заповнені; про це знає тільки автор ручного скрипта (справжній фронт завжди шле всі три ключі).
- **`isActive` в елементі ігнорується**: імпортовані фрази завжди активні (`true`). Решта зайвих ключів (`id`, `createdAt` …) теж ігнорується, як у BE-006. Реалізація: перед валідацією з елемента вилучається `isActive`.
- **Елемент, що не є JSON-об'єктом** (число, рядок, `null`, список), — помилка цього елемента, а не запиту: `{ index, fields: { item: "invalid" } }`.
- **Помилки рівня запиту** (раніше «відкрите питання»): тіло не JSON-об'єкт → `400` (як скрізь); `items` відсутній → `422 { items: "required" }`; не список (об'єкт, рядок, число, `null`) → `422 { items: "invalid" }`; довше за 1000 → `422 { items: "too_many" }` — **нічого не зберігається**. Порожній список — не помилка (`200`, `created: 0`). Узгодження з фронтом — запит B-001 у `docs/BACK-TO-FRONT.md`; реалізуємо, не чекаючи відповіді (фронт цих випадків не викликає; якщо в `API.md` захочуть інше — це правка в одному місці).
- **Сховище: вся валідація — до першого SQL.** Спершу перевіряються всі елементи в пам'яті, далі всі валідні записуються **однією транзакцією** багаторядковими `INSERT` (пакети по 100 рядків, один `UTC_TIMESTAMP()` на пакет). Будь-яка помилка БД → відкат усієї транзакції, `500 server_error`, у БД нічого немає. Якщо валідних елементів немає — транзакція не відкривається. Експериментально (MySQL 5.7): 1000 найдовших фраз (3 × 500 символів, 4-байтні) вставляються за ≈100 мс.
- Відповіді з `Cache-Control: no-store` (як у BE-005/006).

## Обсяг

- **Переробка BE-006 на м'яке правило мов** (робиться першим кроком, до імпорту; окремий коміт). Змінити:
  - `src/Domain/PhraseValidator.php`: відсутній ключ мови і `null` → `''` замість `text.xx = required`/`invalid`; решта правил без змін (число, bool, масив → `invalid`); `empty` рахується з урахуванням відсутніх і `null` як порожніх.
  - Юніт-тести `tests/run.php` (`phraseValidator: text — …`, `text.xx — немає ключа …`, перевірка з `lv`+`en` без `ru`, «кілька помилок разом», порожнє тіло): очікування `required` для мов замінити на нові; додати випадки «ключа немає або `null` — як порожній», «усі три ключі відсутні або `null` → `text: empty`», «ключа немає, але інший непорожній → `201`».
  - API-тести `tests/api/phrases-write.php` (тест «форма text», «кілька помилок», «текст порожній»): те саме; додати `POST`/`PUT` без одного ключа → успіх, у БД порожній переклад, у відповіді `""`.
  - Документація: `decisions.md` (D-27/D-28: прибрати `required` для `text.xx` і формулювання про `{}`/`[]`; D-30 — нове правило, з посиланням на помилкову трактовку), `api-conventions.md` (таблиця кодів `fields`), `architecture.md` (рядок про валідатор), `testing.md` (опис тестів), `docs/BACKEND.md` (перелік кодів `422`), BE-006 `task.md` (примітка та правка критеріїв, що згадують `required` для мов).
- `POST /api/admin/phrases/import`, тіло `{ "items": [ { "category", "text": { "lv", "en", "ru" } }, … ] }`.
- До 1000 елементів за запит.
- Кожен елемент валідується `PhraseValidator`; `isActive` для імпортованих — `true`.
- Валідні зберігаються, невалідні пропускаються (часткове збереження, а не все-або-нічого); збереження валідних — атомарне (див. вище).
- Відповідь `200`: `{ "created": N, "errors": [ { "index": i, "fields": { … } } ] }`; `index` — позиція в `items` з 0; ключі `fields` — як у BE-006 (`category`, `text`, `text.lv` …); `errors` — завжди масив, у порядку зростання `index`.
- Лише додавання; наявні фрази не змінюються і не дедуплікуються.
- Новий метод `PhraseRepository` для пакетної вставки (приймає список `PhraseInput`, повертає кількість; транзакцією керує він сам).
- Маршрут реєструється у `routes.php` разом з іншими `phrases`-маршрутами (`POST /api/admin/phrases/import` не перетинається з `/{id}`: для `POST` другого такого шляху немає).

## Поза обсягом

- Дедуплікація, оновлення наявних фраз за ключем, ліміти на довжину всього файла — фронт шле шматками, бекенд тримає ліміт 1000 елементів.
- Розбір CSV/XLSX на бекенді (його робить фронт).
- Налаштування ліміту розміру тіла на хостингу: найгірший запит (1000 × 3 × 500 чотирибайтних символів) ≈ 6 МБ, тоді як `post_max_size` за замовчуванням — 8 МБ. Перевірку значень хостингу додано до BE-009.
- Зміна `API.md`: поведінка йому відповідає; відповіді на `items` (`required`/`invalid`/`too_many`) поки лише в запиті B-001.

## Acceptance criteria

- [ ] Без токена → `401` (навіть з невалідним тілом); БД не змінюється.
- [ ] Запит із 600 валідних елементів → `200`, `created = 600`, `errors = []` (масив), у БД з'являється 600 нових записів, усі `isActive = true`, `createdAt = updatedAt`.
- [ ] Елемент з невідомою категорією → пропущений, у `errors` є `{ index, fields: { category: "invalid" } }`; без `category` → `required`; решта зберігається.
- [ ] Елемент, де всі три переклади порожні (чи лише пробіли, у т. ч. нерозривні) → пропущений, `fields: { text: "empty" }`.
- [ ] Елемент з перекладом довшим за 500 символів → пропущений, `fields` вказує на відповідну мову (`text.lv: "too_long"` тощо); рівно 500 символів (у т. ч. емодзі) — зберігається.
- [ ] Елемент без одного з ключів мови (`text: { lv, ru }`) **не** помилка: відсутня мова = порожній переклад (зберігається `""`), якщо хоча б одна мова непорожня; усі три ключі відсутні (`text: {}`) → `fields: { text: "empty" }`; `text` відсутній → `text: required`.
- [ ] Значення мови `null` = порожній переклад (як відсутній ключ), не помилка.
- [ ] Елемент з нерядковим значенням мови (число, `true`/`false`, масив, об'єкт) або з керівними символами → пропущений з тими самими кодами, що й у BE-006 (`text.xx: invalid`).
- [ ] Один елемент з кількома помилками повертає їх усі разом в одному `fields`.
- [ ] Елемент не є об'єктом (число, рядок, `null`, список) → `{ index, fields: { item: "invalid" } }`, решта зберігається.
- [ ] `isActive` в елементі (`false`, `"x"`) ігнорується: фраза створюється активною, помилки немає; зайві ключі (`id`, `createdAt`, `text.de`) ігноруються.
- [ ] Тексти зберігаються trimmed (юнікодні пробіли теж), `\n`, `<script>`, емодзі, спецсимволи — без змін; зберігаються байт у байт.
- [ ] `created + errors.length = items.length` для будь-якого запиту.
- [ ] `index` у `errors` збігається з позицією елемента у вхідному масиві (з 0), не зсувається через пропущені елементи; `errors` відсортовані за `index`.
- [ ] Порядок створених записів відповідає порядку валідних елементів у запиті (зростання `id`).
- [ ] Порожній масив `items: []` → `200`, `created = 0`, `errors = []`, жодного SQL-запиту.
- [ ] `items` рівно 1000 елементів → `200`; 1001 → `422 { items: "too_many" }`, у БД нічого не з'явилось.
- [ ] `items` відсутній → `422 { items: "required" }`; не список (`{}`-об'єкт, рядок, число, `null`) → `422 { items: "invalid" }`; тіло не JSON-об'єкт / порожнє / зламаний JSON → `400 bad_request`.
- [ ] 1000 найдовших елементів обробляються успішно за < 10 с (медіана кількох запусків; реально ≈ сотні мс).
- [ ] Повторний імпорт того самого набору створює дублікати (існуючі не змінюються) — це очікувана поведінка; наявні рядки не змінюються (`tableDump` до/після для старих `id`).
- [ ] Елементи зі списку `errors` не залишають жодних даних: у БД лише валідні, кількість рядків зросла рівно на `created`.
- [ ] Збій БД посеред запиту (у тесті — тригер `BEFORE INSERT` з `SIGNAL` на одному з пізніх рядків) → `500 server_error` (без деталей), у БД **жодного** нового рядка (відкат усієї транзакції), тригер у тесті видаляється в `finally`.
- [ ] Кількість SQL-запитів: відхилений на рівні запиту (`400`/`422`) — 0; усі елементи невалідні — 0; успішний — `ceil(valid / 100)` вставок + службові `START TRANSACTION`/`COMMIT` (точне число зафіксувати тестом).
- [ ] Імпортовані фрази одразу доступні в `GET /api/admin/phrases` (збігаються з відповіддю `GET /{id}`) і (якщо мають текст відповідною мовою) в `GET /api/message`.
- [ ] Відповіді (і `200`, і помилки) мають `Cache-Control: no-store`.
- [ ] Переробка BE-006 виконана: `POST` і `PUT` без ключа мови → успіх (порожній переклад), `text: {}` → `422 { text: empty }`; усі тести BE-006 оновлені й зелені; документація й `task.md` BE-006 узгоджені з новим правилом.
- [ ] Нові D-xx записані в `decisions.md`; документація (`architecture.md`, `database.md`, `api-conventions.md`, `security.md`, `testing.md`, `docs/BACKEND.md`) оновлена; у `security.md` рядки «⏳ BE-007» про імпорт позначені як зроблені.
