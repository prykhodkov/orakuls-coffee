# BE-002 · Схема БД і міграції

| Поле | Значення |
|------|----------|
| Тип | Task |
| Пріоритет | High |
| Компонент | backend, database |
| Залежить від | BE-001 |
| Блокує | BE-003 … BE-008 |

## Опис

Спроєктувати і створити схему MySQL 5.7 для фраз, механізм застосування міграцій, який працює на shared-хостингу (без CLI-доступу — як мінімум запуск через phpMyAdmin / SQL-файли), і окрему тестову базу з відомими даними для перевірки ендпоінтів.

Прийняті рішення (докладно — `backend/docs/decisions.md`, D-11 … D-14):
- категорія — `VARCHAR(16)` із перевіркою в коді, а не `ENUM`;
- таблицю `login_attempts` створює BE-004 власною міграцією, не ця задача;
- пошук нечутливий до регістру й діакритики (наслідок колації `utf8mb4_unicode_ci`);
- тести ендпоінтів ходять в окрему БД `orakuls_test`, сід — лише для неї.

## Обсяг

**Таблиця `phrases`:**

| Поле | Тип | Примітка |
|------|-----|----------|
| `id` | `INT UNSIGNED AUTO_INCREMENT` PK | |
| `category` | `VARCHAR(16) NOT NULL` | коди з `API.md`; допустимі значення перевіряє код, а не БД (див. нижче) |
| `text_lv`, `text_en`, `text_ru` | `VARCHAR(500) NOT NULL DEFAULT ''` | 500 **символів** (utf8mb4), порожній рядок = переклад відсутній |
| `is_active` | `TINYINT(1) NOT NULL DEFAULT 1` | |
| `created_at`, `updated_at` | `DATETIME NOT NULL` | зберігаються в UTC |

Індекси: за `category`, за `is_active`.

**Допустимі категорії.** MySQL 5.7 ігнорує `CHECK`-обмеження, тому БД не захищає від «чужої» категорії. Єдиний список кодів (`love`, `money`, `luck`, `work`, `travel`, `mood`) живе в одному місці коду; його використовують валідація (BE-006, BE-007) і фільтри (BE-005). Нову категорію додаємо там, міграція не потрібна.

**Кодування:** `utf8mb4`, колація `utf8mb4_unicode_ci`, рушій InnoDB.

**Міграції:** SQL-файли з нумерацією (`001_create_phrases.sql`…) + простий runner (`bin/migrate.php`) з таблицею `migrations`, ідемпотентний. Кожна наступна задача, що змінює схему, додає власну міграцію (зокрема BE-004 — `login_attempts`). Поряд — повний `schema.sql` для ручного імпорту через phpMyAdmin; він оновлюється разом із кожною міграцією.

**Тестова БД `orakuls_test`:**
- створюється `docker-compose` разом із основною (init-скрипт у `docker/mysql-init/`, права для користувача `orakuls`);
- наповнюється сідом (`bin/seed.php`): кілька фраз на категорію, частина з порожніми перекладами та прихованих, фрази з латиською діакритикою, кирилицею, емодзі та переносами рядків;
- `tests/api.php` перед кожним прогоном сам застосовує міграції до `orakuls_test`, очищає таблиці й заливає сід, потім викликає `Kernel` у процесі (без HTTP-сервера) — тож тести завжди бачать однакові дані й не чіпають основну БД;
- `bin/seed.php` і `tests/api.php` відмовляються працювати, якщо назва БД не закінчується на `_test`. Це захищає і локальну БД розробника, і прод.

Основна локальна БД (`orakuls`) після міграцій лишається порожньою: реальні фрази в неї завантажує адмін через імпорт (BE-007).

## Поза обсягом

- Таблиця `login_attempts` (BE-004).
- Реальний контент 600 фраз (BE-007).
- Самі тести ендпоінтів (з'являються в BE-003 … BE-008); тут лише інфраструктура для них.

## Acceptance criteria

- [ ] Міграції застосовуються на чистій MySQL 5.7 без помилок і не використовують синтаксис 8.0.
- [ ] Повторний запуск runner'а (`bin/migrate.php`) нічого не ламає (ідемпотентність) і не дублює дані; у таблиці `migrations` видно застосовані файли.
- [ ] `schema.sql` дає ту саму схему, що й послідовність міграцій; його можна імпортувати через phpMyAdmin. `login_attempts` у `schema.sql` з'явиться разом із BE-004.
- [ ] Таблиці й текстові колонки мають `utf8mb4` / `utf8mb4_unicode_ci`; фраза з латиськими діакритиками, кирилицею та емодзі зберігається й читається без спотворень.
- [ ] Рядок завдовжки рівно 500 символів (у т.ч. з багатобайтовими) зберігається повністю; 501-й символ відхиляє валідація (BE-006), а не мовчки обрізає БД (strict mode).
- [ ] `category` — `VARCHAR(16)`; список допустимих кодів існує в коді в одному місці, а в `docs/database.md` зазначено, що БД допустимість не гарантує (MySQL 5.7 ігнорує `CHECK`).
- [ ] Є індекси за `category` та `is_active`; `EXPLAIN` вибірки з BE-003 не робить повного перебору по неіндексованих умовах, окрім `RAND()`.
- [ ] Дати зберігаються в UTC; доступ з коду повертає їх у ISO 8601 (`…Z`).
- [ ] `docker compose up` створює обидві бази: `orakuls` і `orakuls_test`; користувач `orakuls` має доступ до обох.
- [ ] `tests/api.php` відтворює однакові дані на кожному прогоні (повторний запуск дає той самий результат) і не змінює дані в `orakuls`.
- [ ] `bin/seed.php` та `tests/api.php` з БД, назва якої не закінчується на `_test`, завершуються з помилкою й нічого не змінюють (перевірено на `DB_NAME=orakuls`).
- [ ] Сід містить випадки, потрібні задачам BE-003 … BE-008: активні й приховані фрази, порожні переклади різними мовами, всі шість категорій, діакритика, кирилиця, емодзі, `\n`.
- [ ] Порядок розгортання схеми на хостингу (імпорт `schema.sql` через phpMyAdmin, без сіду) описано в `docs/BACKEND.md` і `backend/docs/deployment.md`.
- [ ] Для вже створеного локального Docker-volume описано одноразовий крок (`docker compose down -v`), без якого `orakuls_test` не з'явиться (init-скрипти MySQL виконуються лише при створенні volume).
