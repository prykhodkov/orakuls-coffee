# BE-008 · `GET /api/admin/stats`

| Поле | Значення |
|------|----------|
| Тип | Story |
| Пріоритет | Medium |
| Компонент | backend |
| Залежить від | BE-005 (`PhraseRepository`, критерій порожнього перекладу); для наскрізних тестів — BE-006/BE-007 (запис фраз) |

## Опис

Як адмін, я хочу бачити на головній адмінки зведення по базі фраз (скільки всього, скільки активних, розподіл за категоріями, у скількох бракує перекладів), щоб розуміти, що ще треба дописати.

Захищати ендпоінт окремо не потрібно: усе під `/api/admin/` закрите `AdminGuard` (D-20).

Як фронт це використовує (`frontend/src/admin/phrases.js`): плитки на головній — «всього» (скидає фільтри), по плитці на кожну з 6 категорій (клік відкриває список з `category=<код>`) і по лічильнику на кожну мову (клік відкриває `missing=<мова>`). Читає `total`, `active`, `byCategory[категорія] ?? 0`, `missing[мова]`; після кожного збереження/видалення/імпорту запитує статистику заново. Тому **числа в плитках мусять збігатися з `total` списку з відповідним фільтром** — інакше адмін побачить «12 без англійської», а клік покаже 11.

Прийняті рішення (докладно — `backend/docs/decisions.md`; нове D-xx з'явиться разом із реалізацією):
- **Один SQL-запит з умовною агрегацією** (`COUNT(*)`, `SUM(<умова>)` по категоріях, мовах і `is_active`): знімок даних атомарний (два окремі запити могли б побачити різний стан, якщо адмін щось змінив між ними) і найдешевший. SQL — у `PhraseRepository` (D-17), контролер тонкий.
- **«Порожній переклад» — тільки `PhraseRepository::lacksTextSql()`** (те саме визначення, що в фільтрі `missing` у BE-005 та у видачі BE-003). Звідси гарантія: `missing.xx` збігається з `total` списку `?missing=xx` за побудовою.
- **`missing` рахує всі фрази, і приховані теж** (так само, як фільтр `missing` у списку): статистика відповідає на питання «що ще дописати», а прихована фраза без перекладу теж недописана.
- **Імена колонок/умов — лише зі списків-констант** (`Categories::CODES`, `Languages::CODES` через `Languages::column()`): ввід користувача в цей запит не потрапляє взагалі, параметрів у ендпоінта немає (зайві query-параметри ігноруються).
- **Типи:** `SUM()` у MySQL повертає `DECIMAL` (у PHP — рядок) і `NULL` на порожній таблиці: кожне значення приводиться `(int)`, `NULL` → `0` (`COALESCE`). `byCategory` і `missing` — завжди JSON-об'єкти з усіма ключами у порядку констант (`love, money, luck, work, travel, mood` і `lv, en, ru`).
- Фраза з категорією поза списком (можлива лише при ручному редагуванні БД: API такої не створить) у `byCategory` не потрапляє, але входить у `total`; цей випадок не обробляється окремо і описаний у документації.
- Відповідь з `Cache-Control: no-store` (як у решти адмін-ендпоінтів), без кешу на сервері.

## Обсяг

- `GET /api/admin/stats` → `200`:

```json
{
  "total": 600,
  "active": 595,
  "byCategory": { "love": 100, "money": 100, "luck": 100, "work": 100, "travel": 100, "mood": 100 },
  "missing": { "lv": 0, "en": 12, "ru": 3 }
}
```

- `total` — усі фрази; `active` — з `isActive = true`.
- `byCategory` — кількість фраз кожної категорії; присутні **всі** 6 категорій, навіть із нулем.
- `missing` — кількість фраз із порожнім (після `TRIM`) перекладом по кожній мові; присутні всі 3 мови.
- Підрахунок — одним агрегуючим SQL-запитом, без завантаження фраз у PHP; сумісно з MySQL 5.7.
- Новий метод `PhraseRepository` і новий `StatsController` (контролер не відкриває БД до моменту запиту; без параметрів валідувати нічого).

## Поза обсягом

- Кеш статистики, історія, розбивка «активні за категоріями» чи «відсутні переклади за категоріями» — `API.md` цього не вимагає.
- Фільтри в `stats` (за категорією чи мовою).
- Зміна `API.md`: поведінка йому відповідає.

## Acceptance criteria

- [ ] Без токена → `401`.
- [ ] Усі значення — JSON-числа (`int`, не рядки); `byCategory` і `missing` — об'єкти з ключами у порядку `love, money, luck, work, travel, mood` та `lv, en, ru`; відповідь — рівно ключі `total, active, byCategory, missing`.
- [ ] На порожній БД: `total = 0`, `active = 0`, `byCategory` містить усі 6 категорій зі значенням `0`, `missing` — усі 3 мови зі значенням `0` (у сирому JSON це `{...}`, а не `[]`; `SUM` по порожній таблиці не дає `null`).
- [ ] На сіді (30 фраз) значення збігаються з оракулом, обчисленим у PHP з даних сіду (`total`, `active`, кожна категорія, кожна мова), зокрема фраза з перекладом із самих пробілів вважається порожньою, прихована фраза входить у `total` і `missing`, але не в `active`.
- [ ] `total` дорівнює `total` з `GET /api/admin/phrases` без фільтрів.
- [ ] `active` дорівнює `total` з `GET /api/admin/phrases?isActive=true`.
- [ ] Для кожної категорії `byCategory[c]` дорівнює `total` з `GET /api/admin/phrases?category=c`; сума значень `byCategory` дорівнює `total`.
- [ ] `missing.xx` дорівнює `total` з `GET /api/admin/phrases?missing=xx` для кожної з трьох мов.
- [ ] Статистика відображає зміни одразу: після `POST`, `PUT` (категорія, `isActive`, очищення перекладу), `DELETE` і імпорту значення відповідно змінюються без кешу (перевірено наскрізним тестом, і кожен крок збігається зі списком).
- [ ] Відповідь формується **одним** SQL-запитом (перевіряє `statementCount()`), < 200 мс на 600 записах (медіана з кількох запитів).
- [ ] Відповідь має `Cache-Control: no-store`; зайві query-параметри (`?x=1`, `?category=love`) ігноруються й не впливають на результат.
- [ ] Метод, відмінний від `GET`, до цього шляху → `404` (роутер).
- [ ] Нове D-xx записане в `decisions.md`; документація (`architecture.md`, `api-conventions.md`, `database.md`, `testing.md`, `docs/BACKEND.md`) оновлена: `StatsController` прибрано з «Що ще буде додано».
