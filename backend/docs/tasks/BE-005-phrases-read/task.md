| Поле | Значення |
|------|----------|
| Тип | Story |
| Пріоритет | High |
| Компонент | backend |
| Статус | Done (2026-11-01) |
| Залежить від | BE-004 (guard адмінки, авторизація в тестах) |
| Блокує | BE-006, BE-008 |

## Опис

Як адмін, я хочу бачити список усіх фраз із фільтрами, пошуком і пагінацією та відкривати окрему фразу, щоб знаходити й редагувати потрібне серед ~600 записів.

Також у цій задачі фіксується сутність `Phrase` та її серіалізація, яку перевикористовують BE-006 і BE-007.

Захищати ендпоінти окремо не потрібно: усе під `/api/admin/` уже закрите `AdminGuard` у `Kernel` (D-20), `401` без токена дають вони автоматично.

Як фронт це використовує (`frontend/src/admin/phrases.js`): сторінка по **50** записів (`perPage=50`), фільтри `category`, `missing`, `search` (обрізаний `trim()`, порожній не відправляється); `isActive` фронт не використовує, але він є в контракті. Номер сторінки береться з `data-page`; якщо після видалення остання сторінка стала порожньою (`items: []`, `page > 1`), фронт сам зменшує номер і запитує знову — тож сторінка за межами діапазону **мусить** давати `200` з порожнім списком, а не помилку. Кількість сторінок фронт рахує як `ceil(total / perPage)`.

Прийняті рішення (докладно — `backend/docs/decisions.md`, D-24 … D-26):
- SQL живе в `Repository\PhraseRepository` (D-17), там же — спільний критерій «переклад порожній» (`hasTextSql`) для `missing`;
- `Domain\Phrase` — єдине місце, де рядок БД перетворюється на об'єкт API (`isActive` → `bool`, дати → ISO 8601, `text` → об'єкт з трьома ключами); його ж використають BE-006 і BE-007;
- пошук — `LIKE … ESCAPE` зі **службовим символом** (див. нижче), нечутливий до регістру й діакритики (D-13);
- явні фільтри, на відміну від `exclude` у BE-003, **строгі**: невідоме значення — це помилка клієнта (`400`), бо адмін сам їх обирає й має побачити опечатку.

## Обсяг

- `GET /api/admin/phrases` — query-параметри (усі необов'язкові): `category`, `search`, `missing` (`lv|en|ru`), `isActive` (`true|false`), `page` (з 1, за замовч. `1`), `perPage` (1–100, за замовч. `50`).
  - Порожній рядок (`category=`) трактується як відсутній параметр (форми часто шлють порожні поля).
  - `category` — один із кодів `Categories::CODES`; `missing` — код мови з `Languages::CODES`; `isActive` — рівно `true` або `false` (нижній регістр); `page` — ціле від 1 до 999 999 999; `perPage` — ціле від 1 до 100. Інакше `400 bad_request` з назвою параметра в повідомленні.
  - `search` обрізається `trim()`; порожній після обрізання — як відсутній; довший за 200 символів → `400`.
  - Параметр-масив (`category[]=love`) → `400` (це робить `Request::query()`).
- Сортування: `id` за спаданням.
- Відповідь: `{ "items": Phrase[], "total", "page", "perPage" }`; `total` — кількість після фільтрів, `page` і `perPage` — застосовані значення.
- `GET /api/admin/phrases/{id}` → `Phrase` або `404`. `id` — лише канонічне ціле (`^[1-9][0-9]{0,9}$`); `007`, `1.5`, `abc`, `-1`, `0` → `404`.
- `Phrase`: `{ id, category, text: { lv, en, ru }, isActive, createdAt, updatedAt }` з коректними типами (`id` — число, `isActive` — boolean, дати — ISO 8601 UTC через `Iso8601::fromDb`). Ключі `text` завжди всі три, порожній переклад — `""`. Службових колонок (`text_lv`, `is_active`, `created_at`) у відповіді немає.
- `search` — підрядок по всіх трьох мовах; `%`, `_`, `\` і будь-які інші символи шукаються як звичайні. Пошук **нечутливий до регістру й діакритики** — наслідок колації `utf8mb4_unicode_ci`, прийнято свідомо (D-13): `sodien` знаходить `Šodien`, `bus` — `būs`. Межі, перевірені на MySQL 5.7: `ё` = `е`, але `й` ≠ `и`; усі емодзі між собою порівнюються як рівні.
- **Чому не звичайне екранування через `\`.** На MySQL 5.7 запит `LIKE '%\\%' ESCAPE '\'` (пошук одного символа `\`) нічого не знаходить, хоч такі фрази є; те саме з будь-яким символом, що одночасно є символом екранування (`!`, `|`). Перевірено експериментом. Тому екранувальний символ — службовий керівний `x'01'`: його не можна набрати в полі пошуку, і він вилучається з ввідного рядка. Ще одна вада виявлена під час реалізації: ввід, що **починається з `%`**, на `utf8mb4_unicode_ci` дає хибні збіги навіть так, тому для нього `%` замінюється службовим `0x02` у шаблоні й у колонці (`REPLACE`), див. D-24. `LOCATE()` як заміна не підходить: він нечутливий до регістру, але **не** до діакритики (`sodien` не знаходить `Šodien`), тобто суперечить D-13.
- Тестова обв'язка: допоміжні функції входу (`authToken`, `authAs`) зараз лежать у `tests/api/auth.php`. Нові тести залежать від них, тож вони виносяться в спільний `tests/` файл (щоб порядок підключення файлів не мав значення).

## Acceptance criteria

- [x] Без токена обидва ендпоінти → `401` (забезпечує guard; перевірити тестом).
- [x] `GET /api/admin/phrases` без параметрів → `200`, `page = 1`, `perPage = 50`, не більше 50 елементів, відсортовані за `id` DESC.
- [x] `id`, `total`, `page`, `perPage` — JSON-числа; `isActive` — `true`/`false`; `text` — об'єкт з трьома ключами `lv`, `en`, `ru` (порожній переклад = `""`); у фразі рівно ключі `id, category, text, isActive, createdAt, updatedAt`; дати в ISO 8601 з `Z`.
- [x] Обидва ендпоінти (і `200`, і помилки) мають `Cache-Control: no-store`.
- [x] `category=love` повертає лише фрази категорії `love`; невідома категорія (у т. ч. `LOVE`) → `400 bad_request`.
- [x] `isActive=false` повертає лише приховані, `isActive=true` — лише активні; інше значення (`1`, `True`, `yes`) → `400`.
- [x] `missing=en` повертає лише фрази, де англійський переклад порожній (після `TRIM`, зокрема з самих пробілів); невідоме значення → `400`.
- [x] `search` знаходить підрядок у будь-якій з трьох мов без урахування регістру (напр. `LUCK` знаходить `Luck is on your side`); пошук по кирилиці працює.
- [x] Пошук ігнорує діакритику: `search=sodien` знаходить фразу з `Šodien`, `search=bus` — з `būs`; регістр не важливий і для кирилиці (`тест` знаходить `Тест`).
- [x] Спецсимволи шукаються як звичайні: `search=100%` знаходить лише фразу з `100%`; `search=_` — лише фрази з підкресленням; `search=\` — фразу зі зворотним слешем; `search=%` не повертає все; `search=%_` не діє як шаблон.
- [x] `search` з пробілами по краях діє як без них; порожній або лише з пробілів — як відсутній; довший за 200 символів → `400`; SQL-ін'єкція (`' OR '1'='1`, `%'; DROP TABLE phrases; --`) нічого не ламає й повертає порожній (або коректний) результат.
- [x] Порожні значення параметрів (`category=`, `missing=`, `isActive=`, `search=`, `page=`, `perPage=`) діють як відсутні.
- [x] Фільтри комбінуються (AND): `category` + `missing` + `search` + `isActive`.
- [x] `total` відповідає кількості записів після фільтрів, а не загальній; `page=2&perPage=10` повертає записи 11–20 у порядку `id` DESC (перевірено на таблиці, де записів > 20).
- [x] `page` за межами діапазону → `200` з порожнім `items`, правильним `total` і тим самим `page`; `perPage=100` повертає до 100 записів.
- [x] `perPage=0`, `perPage=101`, `page=0`, `page=-1`, `page=1.5`, нечислові значення, `page` довший за 9 цифр → `400 bad_request`.
- [x] Порожній результат → `items: []` (масив), не `null`, і `total: 0`.
- [x] `GET /api/admin/phrases/42` → `200` з повним `Phrase` (збігається з елементом списку); неіснуючий, нечисловий, нульовий, від'ємний, з ведучими нулями або задовгий `id` → `404 not_found`.
- [x] Пошук і фільтри виконуються двома SQL-запитами (вибірка сторінки + `COUNT`), без N+1; час відповіді < 300 мс на 600 записах із фільтрами та пошуком (медіана з кількох запитів).
- [x] Допоміжні функції входу для тестів винесені з `tests/api/auth.php` у спільний файл; усі наявні тести лишаються зеленими.
- [x] Нові D-xx записані в `decisions.md`; документація (`database.md`, `api-conventions.md`, `architecture.md`, `testing.md`, `security.md`, `docs/BACKEND.md`) оновлена.
