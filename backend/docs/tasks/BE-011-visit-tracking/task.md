## Опис

Клієнт хоче знати, скільки людей відкриває сайт і скільки з них прийшло саме зі сканування QR на стаканчику. Це головний показник того, чи працює «стаканчик як канал»: скільки стаканчиків реально скануються, у які дні і наскільки частіше, ніж люди заходять на сайт іншими шляхами (за посиланням, яким поділилися, чи вводячи адресу вручну).

Сторонню аналітику (Google Analytics тощо) не використовуємо: у ЄС їй потрібен банер згоди на cookies — зайвий екран перед посланням. Рахуємо самі, **лише кількості по днях, без жодних персональних даних** (без IP, User-Agent, cookies, ідентифікаторів відвідувача).

Фронт уже готовий і працює на моку: при кожному відкритті сторінки користувача (до вибору мови) він повідомляє бекенду «відкрили сайт» і вказує, чи це було сканування QR.

## Бізнес-правила

- **Дві метрики на день:**
  - «Відкриття сайту» (`visits`) — будь-яке відкриття: QR, посилання, адреса вручну;
  - «Сканування QR» (`scans`) — відкриття саме з QR; це частина «відкриттів», тож `scans ≤ visits` завжди.
- **Що вважається скануванням** — вирішує лише поле `source` у запиті: `"qr"` → сканування, `"direct"` → просто відкриття. Бекенд не аналізує адресу, заголовки чи пристрій.
- **Що таке «день»** — календарна дата за часом Риги (`Europe/Riga`): клієнт у Латвії, «вчора» має означати латвійське вчора, а не UTC. Дату рахує PHP, а не MySQL (на shared-хостингу таблиці часових поясів MySQL можуть бути не завантажені).
- **Лічильник — не форма, тож суворості мінімум:** невідоме, порожнє чи нерядкове значення `source` рахується як `direct`; відповідь у всіх нормальних випадках `204` без тіла.
- **Збій статистики не повинен впливати на користувача:** фронт ігнорує будь-яку відповідь, а сторінка з посланням працює незалежно від того, чи записалось відкриття.
- **Захисту від накрутки немає свідомо:** для статистики кав'ярні це прийнятно (рішення з F-005). Ліміт за IP не додаємо; якщо клієнт колись захоче — окремою задачею й без довгого зберігання IP.
- **Зберігання — безстроково:** це лічильники (~5 рядків на день, ~1800 на рік), чистити нічого не треба.

## Обсяг

- Нова таблиця агрегованих лічильників по днях (пропозиція з F-005: `daily_stats(day, metric, count)` з первинним ключем `(day, metric)`; метрики `visit`, `scan`, `message_lv`, `message_en`, `message_ru`). Міграція + оновлений `schema.sql`. Таблицю використовують і BE-012, і BE-013, тож остаточну форму фіксуємо тут.
- Атомарне збільшення лічильника (`INSERT … ON DUPLICATE KEY UPDATE count = count + 1`, сумісно з MySQL 5.7), щоб паралельні відкриття не губились.
- `POST /api/visit` — публічний, без авторизації, `Cache-Control: no-store`:

| Ситуація | Відповідь |
|----------|-----------|
| `{ "source": "qr" }` | `204`; `visits +1`, `scans +1` |
| `{ "source": "direct" }` | `204`; `visits +1` |
| `source` відсутній / `null` / невідомий рядок / не рядок | `204`; рахується як `direct` |
| Тіло порожнє, не JSON, або JSON не є об'єктом (число, рядок, непорожній масив) | `400 bad_request`; нічого не рахується |
| Тіло `[]` | `204`, рахується як `direct` (PHP не відрізняє `[]` від `{}`, `Request::json()` це не розрізняє; на статистику не впливає) |
| Помилка БД | `500 server_error`, деталі — у лог |

- Відповісти на F-005 у `docs/FRONT-TO-BACK.md` (розділ «Відповідь»): формат підходить / що змінюємо; підрахунок дати в PHP за `Europe/Riga` — без заперечень.

## Acceptance criteria

- [x] `POST /api/visit` з `{ "source": "qr" }` → `204` без тіла; за сьогоднішню дату `visits` і `scans` зросли рівно на 1.
- [x] З `{ "source": "direct" }` → `204`; зріс лише `visits`, `scans` не змінився.
- [x] `source` відсутній, `null`, `"abc"`, `123`, `["qr"]`, `true` → `204`, рахується як `direct` (зріс лише `visits`).
- [x] Порожнє тіло, не-JSON, JSON-число, JSON-рядок, непорожній масив (`["qr"]`) → `400 bad_request`, лічильники не змінились. Тіло `[]` → `204`, рахується як `direct` (свідоме відхилення: PHP не відрізняє `[]` від `{}`, `Request` не змінюємо), у тестах зафіксовано.
- [x] Відповідь має `Cache-Control: no-store`; авторизація не потрібна; метод, відмінний від `POST`, → `404`/`405` за правилами роутера.
- [x] «День» береться за `Europe/Riga`: тест із підміненим часом 2026-11-02 22:30 UTC (уже 3 листопада в Ризі) записує в 2026-11-03; 2026-03-29 і 2026-10-25 (перехід на літній/зимовий час) не дають зсуву чи дублювання дня.
- [x] 50 паралельних запитів дають рівно +50 (лічильник не губить відкриття).
- [x] У БД після запитів немає жодних персональних даних: лише `(day, metric, count)`; IP і заголовки клієнта ніде не зберігаються й не логуються.
- [x] Помилка БД → `500 server_error` у єдиному форматі помилок, деталі в лог, нічого не виводиться клієнту.
- [x] Міграція застосовується на чистій БД і поверх поточної; `bin/build-schema.php --check` зелений; `reseed()` у тестах очищає `daily_stats` (сіду з історією немає: історію для звіту вантажить BE-013).
- [x] Тести в `tests/api.php` / `tests/run.php` для всіх рядків таблиці відповідей; smoke-скрипт (по HTTP) перевіряє `204`, але **за замовчуванням нічого не пише** у статистику (перевірка запису `POST /api/visit` вмикається явно, наприклад `SMOKE_WRITE=1`), щоб запуск проти прода не спотворював цифри; без запису перевіряються лише відповіді на запити, що нічого не рахують (наприклад `400` на порожнє тіло).
- [x] F-005 отримав відповідь у `docs/FRONT-TO-BACK.md`; нове D-xx в `decisions.md` (агрегати замість журналу подій, день за Ригою в PHP); оновлено `database.md`, `architecture.md`, `api-conventions.md`, `testing.md`, `docs/BACKEND.md`.
