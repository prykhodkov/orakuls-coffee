# BE-003 · `GET /api/message` — випадкове послання

| Поле | Значення |
|------|----------|
| Тип | Story |
| Пріоритет | High |
| Компонент | backend |
| Статус | Done (2026-11-01) |
| Залежить від | BE-001, BE-002 |

## Опис

Як відвідувач, що відсканував QR-код зі стаканчика і обрав мову, я хочу отримати випадкове послання своєю мовою, щоб побачити його на екрані.

Ендпоінт публічний (без авторизації). Це єдиний ендпоінт, який викликають користувачі, тож він має бути швидким і стійким до некоректного вводу. Фронт ніколи не отримує всю базу — випадковість обирає бекенд.

Прийняті рішення (докладно — `backend/docs/decisions.md`, D-17 … D-19):
- SQL виноситься з контролера в `Repository\PhraseRepository` (його ж використовуватимуть BE-005 … BE-008);
- `exclude` — підказка за принципом «найкращого зусилля»: сміття пропускається, зайве ігнорується, `400` дає лише `lang`;
- вибір — один SQL-запит `ORDER BY (id IN (…)) ASC, RAND() LIMIT 1`: спершу непереглянуті, а якщо їх нема — будь-яка доступна.

## Обсяг

- `GET /api/message?lang=lv|en|ru&exclude=1,2,3`
- Кандидати: фрази з `is_active = 1` і непорожнім текстом мовою `lang`; категорії рівноправні, усі разом. «Порожній» = `TRIM(колонка) = ''` у SQL (обрізаються лише пробіли); те саме визначення використовують BE-005 (`missing`) та BE-008 (статистика).
- Рівномірно випадковий вибір одного запису.
- `exclude` — ID через кому. Фронт передає їх від новішого до старішого (до 100 штук). Правила:
  - елемент, що не є невід'ємним цілим до 10 цифр (`abc`, порожній, `-5`, `1.5`, `+5`), мовчки пропускається; пробіли навколо числа толеруються;
  - повтори прибираються; враховуються перші 200 коректних ID, решта ігнорується; ліміту за довжиною в символах немає;
  - `exclude` не рядок (`exclude[]=1`) трактується як відсутній;
  - фрази з `exclude` не вибираються, поки є інші кандидати; якщо кандидатів, окрім виключених, немає — `exclude` ігнорується.
- Відповідь `200`: `{ "id": 42, "lang": "lv", "text": "…" }` — `id` числом, `text` як збережено в БД.
- Заголовок `Cache-Control: no-store`.
- Ліміту на кількість посланнь немає (F-002).

## Поза обсягом

Зміни `docs/API.md` (поведінка сумісна з контрактом: «бекенд намагається їх уникнути»); ліміт запитів; кешування.

## Acceptance criteria

- [x] `GET /api/message?lang=lv` повертає `200` з тілом рівно `{ id, lang, text }` (саме в такому порядку ключів), де `id` — число, `lang` збігається із запитаним, `text` непорожній.
- [x] Відповідь містить `Cache-Control: no-store`.
- [x] `lang` відсутній, порожній, невідомий (`de`), у неправильному регістрі (`LV`) або масив (`lang[]=lv`) → `400 bad_request` у стандартному форматі помилок.
- [x] Фраза з `is_active = 0` ніколи не повертається.
- [x] Фраза з порожнім або лише з пробілів перекладом мовою `lang` не повертається для цієї мови, але може повертатись для інших.
- [x] Якщо в БД немає жодної доступної фрази для `lang` → `404 not_found` (а для інших мов, де фрази є, — `200`).
- [x] ID із `exclude` не повертаються, поки є інші кандидати (перевірка на ≥ 200 запитах).
- [x] Якщо `exclude` покриває всі доступні фрази — повертається `200` із будь-якою доступною (а не `404`).
- [x] `exclude` ніколи не дає `400`: нечислові, порожні, від'ємні, дробові та задовгі елементи (`abc`, `1,,2`, `-5`, `1.5`, 11 цифр) пропускаються, а коректні елементи того ж списку продовжують діяти; `exclude[]=1` не ламає запит.
- [x] Враховуються лише перші 200 коректних ID: фраза, чий ID стоїть у списку на 201-му місці, може повертатись; фраза на 1-му місці — ні. Список із понад 1000 елементів обробляється без помилок. Ліміту за довжиною в символах немає.
- [x] Розподіл рівномірний: на тестовій БД `orakuls_test` (28 кандидатів для `lv`) за 3000 запитів без `exclude` кожна фраза з'являється, а її лічильник лежить у межах ±6σ від середнього; те саме для решти кандидатів, коли частину виключено через `exclude` (немає зсуву в бік менших ID).
- [x] `text` у відповіді точно дорівнює збереженому: латиська діакритика й кирилиця не екрануються, `\n` зберігається, HTML не екранується.
- [x] Вибір відбувається одним SQL-запитом, що повертає один рядок: на 600 фразах обсяг даних від сервера БД (`Bytes_sent`) для запиту щонайменше в 10 разів менший, ніж для вибірки всієї таблиці.
- [x] Час відповіді на 600 фразах із `exclude` зі 100 ID < 200 мс (медіана з 30 запитів, у процесі).
- [x] Ендпоінт не вимагає `Authorization` і не повертає полів `category`, `isActive`, дат; будь-який інший метод (`POST` тощо) → `404 not_found`.
- [x] Рішення D-17 … D-19 записані в `decisions.md`; документація (`architecture.md`, `database.md`, `testing.md`, `api-conventions.md`, `security.md`, `docs/BACKEND.md`) оновлена.


## Як перевірити

Усі команди — з папки `backend/`.

```
docker compose run --rm --no-deps php php tests/run.php        # юніт-перевірки (IdList, rawQuery, маршрут), 0 провалено
docker compose exec php php tests/api.php                      # ендпоінт на orakuls_test (tests/api/message.php); запустити двічі
docker compose exec php php tests/smoke.php                    # по HTTP; робоча БД порожня → /api/message дає 404, це норма
docker compose exec php php bin/build-schema.php --check       # schema.sql без змін
curl -s -i "http://localhost:8000/api/message?lang=lv"         # 404 not_found, поки робоча БД порожня (не 500)
curl -s -i "http://localhost:8000/api/message?lang=zz"         # 400 bad_request
```

Перевірка `200` по HTTP: запустити другий сервер на тестовій БД і прогнати smoke проти нього
(`docker compose exec -d -e DB_NAME=orakuls_test php php -S 127.0.0.1:8001 -t public public/index.php`,
потім `docker compose exec php php tests/smoke.php http://127.0.0.1:8001`; сервер зупинити після перевірки).
