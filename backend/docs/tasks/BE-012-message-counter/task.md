# BE-012 · Облік виданих послань (по днях і мовах)

| Поле | Значення |
|------|----------|
| Тип | Story |
| Пріоритет | High |
| Компонент | backend |
| Статус | Done (2026-11-03) |
| Залежить від | BE-003 (`GET /api/message`), BE-011 (таблиця лічильників і правило «дня за Ригою») |
| Походження | F-005, коміт `58f22a9` |

## Опис

Клієнту мало знати, скільки людей відкрили сайт: важливо, скільки з них **реально отримали послання** і якою мовою. Це показує, яка мова найпопулярніша (чи не даремно є латиська й англійська версії) і яка частка відвідувачів дійшла до кінця сценарію («відкрив → вибрав мову → отримав послання»).

Бекенд сам фіксує кожне видане послання в момент видачі — фронт для цього нічого не шле.

## Бізнес-правила

- **Рахується кожна успішна видача** (`GET /api/message` → `200`): `messages +1` і `+1` у мові, якою видано послання (`lv` / `en` / `ru`) — за сьогоднішній день за Ригою.
- **Не рахуються** відповіді `400` (невалідний запит) і `404` (немає доступних фраз) — послання не видано.
- **Пріоритет — користувач, а не статистика.** Якщо запис лічильника не вдався, користувач усе одно отримує послання; бекенд лише пише помилку в лог. Краще втратити одиницю статистики, ніж показати помилку замість послання.
- **`messages` менше за `visits` — це нормально.** Повторне сканування протягом 20 хвилин показує те саме послання з пам'яті пристрою і не звертається до бекенда, тож нове послання не рахується. Пояснення вже є в адмінці.
- Контракт відповіді `GET /api/message` **не змінюється**.

## Обсяг

- Після підготовки відповіді `200` в `GET /api/message` — збільшити лічильники `message_<мова>` (таблиця з BE-011) на сьогоднішню дату за Europe/Riga.
- Збій запису не перериває відповідь (перехоплюється, логується, видача триває).
- Видача не повільнішає помітно: один додатковий атомарний запис.

## Поза обсягом

- Облік видач по категоріях чи по конкретних фразах («яка фраза найпопулярніша») — не запитували; при потребі — окрема задача.
- Облік відкриттів — BE-011; звіт — BE-013.
- Зміна алгоритму вибору фрази чи логіки `exclude`.

## Acceptance criteria

- [x] Успішний `GET /api/message?lang=lv` збільшує на 1 `message_lv` за сьогоднішній день; те саме для `en` і `ru` у своїх лічильниках, інші мови не змінюються.
- [x] `400` (невідома або відсутня мова) і `404` (немає активних фраз цієї мови) лічильники **не** змінюють.
- [x] Видача фрази з `exclude` і без нього рахується однаково (одна видача — одна одиниця). Некоректний `exclude` ніколи не дає `400` (D-18), такий запит — звичайна видача й рахується як одна.
- [x] Якщо запис лічильника штучно ламається (недоступна таблиця / помилка БД у тесті), `GET /api/message` усе одно повертає `200` з посланням, а помилка потрапляє в лог.
- [x] Тіло і заголовки відповіді `GET /api/message` ідентичні тим, що були до задачі (регресійні перевірки BE-003 зелені).
- [x] День — за Ригою (той самий тест на «північ за Ригою», що й у BE-011).
- [x] Паралельні 50 видач → `messages` зростає рівно на 50.
- [x] Сума `message_lv + message_en + message_ru` за день дорівнює кількості успішних видач за цей день (звіряється наскрізним тестом через BE-013).
- [x] Час прогону `tests/api.php` заміряно: ≈ 22 с → ≈ 45 с після задачі; рішення — `--innodb-flush-log-at-trx-commit=2` у dev-`docker-compose.yml` (≈ 20 с), записане в `testing.md`.
- [x] Smoke-скрипт проти прода за замовчуванням не збільшує лічильники послань (запит `GET /api/message` у ньому або вимкнений за замовчуванням, або явно позначений як такий, що пише); факт описаний у `testing.md` і враховується в BE-014.
- [x] Тести в `tests/api.php`; документація (`architecture.md`, `database.md`, `testing.md`, `docs/BACKEND.md`) оновлена; рішення про «збій статистики не ламає видачу» записане в `decisions.md`.

## Як перевірити

Усі команди — з папки `backend/`.

```
docker compose up -d db                            # після зміни docker-compose.yml (flush-параметр dev-MySQL)
docker compose exec php php tests/run.php          # 112 перевірок
docker compose exec php php tests/api.php          # 177 перевірок на orakuls_test (tests/api/message-counter.php — лічильник); запустити двічі
docker compose exec php php tests/smoke.php        # по HTTP, 26 перевірок (+2 skip); SMOKE_WRITE=1 вмикає перевірки, що пишуть у статистику
```
