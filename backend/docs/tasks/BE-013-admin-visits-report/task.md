# BE-013 · Звіт зі статистики за період для адмінки (`GET /api/admin/visits`)

| Поле | Значення |
|------|----------|
| Тип | Story |
| Пріоритет | High |
| Компонент | backend |
| Статус | Done (2026-11-03) |
| Залежить від | BE-004 (авторизація адмінки), BE-011 (лічильники відкриттів), BE-012 (лічильники послань) |
| Походження | F-005, коміт `58f22a9` (вкладка «Статистика» в адмінці) |

## Опис

Запит клієнта: «подивитися статистику по кількості сканувань і звернень за період і по днях». Адмін відкриває вкладку «Статистика», обирає період («Сьогодні», «Вчора», 7 / 30 днів, цей / минулий місяць або свої дати) і бачить:

- плитки із загальними числами за період: **сканування QR**, **відкриття сайту**, **видані послання**, **послання по мовах**;
- графік відкриттів по днях;
- таблицю по днях з підсумковим рядком.

Фронт готовий і працює на моку (`frontend/src/shared/api/mock/visits.js` імітує контракт з F-005). Ця задача дає йому справжні дані.

## Бізнес-правила

- **Період** задається двома датами `from` і `to` (за ризьким часом), **обидві включно**. Обидва параметри обов'язкові.
- **Кожен день періоду присутній у відповіді**, навіть якщо в нього нічого не було (нулі): графік будується по днях і пропусків не очікує.
- **Підсумок за період рахує бекенд** (сума днів); фронт сам не перераховує, тож плитки й таблиця завжди збігаються.
- **Мови — завжди всі три** (`lv`, `en`, `ru`) у цьому порядку, навіть із нулями.
- **Максимальний період — 366 днів** (включно з кінцями): так само обмежує фронт, тож у інтерфейсі помилки не буде, але API захищається від надто важких запитів.
- Дати в майбутньому дозволені (нулі) — помилкою не вважаються.
- Доступ — лише для адміна (токен, як в усіх `/api/admin/*`); дані не кешуються, адмін завжди бачить актуальні числа.

## Обсяг

- `GET /api/admin/visits?from=YYYY-MM-DD&to=YYYY-MM-DD` → `200`, `Cache-Control: no-store`:

```json
{
  "from": "2026-10-05",
  "to": "2026-11-03",
  "timezone": "Europe/Riga",
  "total": { "visits": 1600, "scans": 1403, "messages": 1324, "byLang": { "lv": 674, "en": 254, "ru": 396 } },
  "days": [
    { "date": "2026-10-05", "visits": 38, "scans": 33, "messages": 30, "byLang": { "lv": 15, "en": 6, "ru": 9 } }
  ]
}
```

- `days` — по зростанню дати, без пропусків; `messages` = сума трьох мов цього дня; `total` = сума `days`; усі числа — JSON-числа.
- Читання — одним запитом по таблиці лічильників за діапазоном, порожні дні доповнює PHP.
- Помилки `400 bad_request` (без `fields`, як у фільтрах BE-005):

| Ситуація | Відповідь |
|----------|-----------|
| `from` або `to` відсутній, порожній, не `YYYY-MM-DD` | `400` |
| Неіснуюча дата (`2026-02-30`, `2026-13-01`) | `400` |
| `from > to` | `400` |
| Період довший за 366 днів включно | `400` |
| Без токена / з невалідним | `401` |

## Acceptance criteria

- [x] Без токена → `401`; з валідним токеном → `200`.
- [x] Відповідь — рівно ключі `from, to, timezone, total, days`; `timezone` = `"Europe/Riga"`; `from`/`to` повторюють запит.
- [x] Для періоду з N днів `days` містить рівно N елементів, по зростанню дати, включно з днями без даних (усі нулі); `byLang` у кожного дня й у `total` — об'єкт із ключами `lv, en, ru` у цьому порядку (у сирому JSON це `{…}`, не `[]`).
- [x] Усі значення — JSON-числа (не рядки); на порожній таблиці — нулі, а не `null`.
- [x] `total` дорівнює сумі `days` за кожним полем; `messages` кожного дня = `byLang.lv + byLang.en + byLang.ru`; `scans ≤ visits` для даних, створених через API.
- [x] Наскрізний тест: N викликів `POST /api/visit` (qr і direct) та `GET /api/message` по різних мовах → звіт за сьогодні показує точно ті числа.
- [x] Період один день (`from = to`) працює; `to` у майбутньому — `200` з нулями; період рівно 366 днів → `200`, 367 → `400`.
- [x] Усі «погані» рядки таблиці помилок → `400 bad_request` у єдиному форматі помилок; зайві query-параметри ігноруються.
- [x] Дні перетину зимового/літнього часу (2026-03-29, 2026-10-25) присутні рівно по одному разу; межі місяців і року (31.12 → 01.01) коректні.
- [x] Відповідь має `Cache-Control: no-store`; запит до БД — один; 366 днів повертаються швидко (< 200 мс на тестових даних).
- [x] Метод, відмінний від `GET`, → `404` (роутер).
- [x] Рік у `from`/`to` приймається в межах, які підтримує MySQL `DATE` (якщо `0000` не проходить — суворіше: 1000–9999, це свідоме уточнення, `400` для решти); `from`/`to` поза цим діапазоном → `400`, не `500`.
- [x] Тести в `tests/api/` (окремий файл для звіту), історія кількох днів лежить в окремій фікстурі, що завантажується на вимогу (не в загальному сіді, щоб не ламати точні лічильники BE-011/BE-012); документація (`architecture.md`, `api-conventions.md`, `database.md`, `testing.md`, `docs/BACKEND.md`) оновлена; рішення — в `decisions.md`.
- [x] Фронт із `VITE_API_MOCK=false` показує вкладку «Статистика» з реальними даними без помилок у консолі (періоди «Сегодня», «Вчера», 7/30 днів, місяці, довільні дати). _(2026-11-03: headless Chromium через Playwright, фронт через dev-проксі на бекенд з `orakuls_test` і фікстурою історії: 8 запитів `GET /api/admin/visits` — усі `200`; період 24–26.10.2026 = 94 / 72 / 62 (lv 30, en 11, ru 21); період > 366 днів — помилка в UI без запиту; 38 відповідей API без `≥ 400`, 0 помилок і попереджень у консолі. Перевірка на тестових даних, не на реальних.)_
