## Опис

Налаштувати хостинг GoDaddy Web Hosting (cPanel, Apache) так, щоб фронт і API працювали на одному домені без CORS: `/` і `/admin/` — статика фронта, `/api/*` — PHP. Закрити пункти 4 і 5 із запиту F-003 (заголовок `Authorization`, роздача статики).

Версії на хостингу: PHP 8.4 (потрібно вибрати вручну — типова 8.3), MySQL 5.7 ([BACKEND.md](../../../../docs/BACKEND.md)). Перед стартом звірити реальні версії в cPanel і виправити документацію, якщо вони відрізняються.

## Обсяг

- Вибрати PHP 8.4 для домену («Select PHP Version»), перевірити потрібні розширення: `pdo_mysql`, `mbstring`, `json`, `openssl`/`sodium`.
- Створити БД і користувача MySQL 5.7 у cPanel; застосувати схему (BE-002).
- Розкласти файли: статика `frontend/dist/` → корінь сайту, `dist/admin/` → `/admin/`; код бекенда й конфіг (`.env`) — поза веб-коренем, у `public_html` лише точка входу API.
- `.htaccess`:
  - передача `Authorization` у PHP (`RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]`);
  - `/api/*` → точка входу PHP; існуючі файли й папки (статика) не перехоплюються;
  - `/admin/` віддає `admin/index.html` (`DirectoryIndex`);
  - заборона доступу до службових файлів (`.env`, міграції, `.git`);
  - редирект на HTTPS.
- Налаштувати призначення `error_log()` (див. критерії нижче): без публічного файлу логів і без безмежного росту.
- **Боєві облікові дані адміна** (рішення користувача: робимо перед BE-009). Розробник генерує на сервері логін, надійний пароль і `TOKEN_SECRET`, записує в серверний `.env` лише хеш пароля й секрет, а пароль передає клієнту безпечним каналом (менеджер паролів або одноразове посилання; не поштою й не в месенджері відкритим текстом). Порядок і процедуру зміни пароля записати в `backend/docs/configuration.md`. Термін сесії за замовчуванням — 7 діб (`TOKEN_TTL_HOURS=168`).
- **Перевірка реального IP клієнта за проксі хостингу.** Лімітування спроб входу (BE-004) спирається на `REMOTE_ADDR`. Якщо GoDaddy ставить перед сайтом проксі, `REMOTE_ADDR` буде спільним для всіх відвідувачів, і 5 чужих невдалих спроб заблокують вхід самому адміну. Перевірити тимчасовим діагностичним скриптом (виводить `REMOTE_ADDR`, `HTTP_X_FORWARDED_FOR`, `HTTP_X_REAL_IP`, `HTTP_CF_CONNECTING_IP`, `HTTP_FORWARDED`), порівняти з реальною публічною адресою клієнта, потім видалити скрипт. Якщо `REMOTE_ADDR` — не справжній IP: **зупинитись і звернутись до користувача** за рішенням, якому заголовку довіряти (довіряти `X-Forwarded-For` без перевірки не можна: його підробляє будь-який клієнт), нічого не змінюючи в коді мовчки.
- Сторінка «деплой» у `docs/BACKEND.md`: покроковий порядок оновлення (файли, міграції, перевірка).

## Acceptance criteria

- [ ] У cPanel для домену вибрано PHP 8.4; `phpinfo()` (тимчасово) або службова перевірка підтверджує версію, після чого тимчасовий файл видалено. _(⏳ хостинг; діагностичний скрипт `deploy/diagnostics/diag.php` готовий)_
- [ ] Реальні версії PHP і MySQL на хостингу збігаються з `docs/BACKEND.md` (або документацію виправлено). _(⏳ хостинг: версії покаже `diag.php`)_
- [ ] `GET https://<домен>/` віддає сторінку користувача, `GET https://<домен>/admin/` — адмінку (статика, без участі PHP). _(локально ✔ 2026-11-03: `tests/hosting-check.php --local`, статика без PHP; на хостингу ⏳)_
- [ ] `GET https://<домен>/api/message?lang=lv` обробляється PHP і повертає JSON за контрактом; запит на неіснуючий `/api/…` повертає JSON-помилку `404`, а не HTML-сторінку Apache. _(локально ✔: PHP через `.htaccess`, JSON-`404` на невідомий `/api/…`; на хостингу ⏳)_
- [ ] Статичні файли (JS/CSS/зображення) віддаються напряму, правила `/api` їх не перехоплюють. _(локально ✔: файл із `/assets/` віддається напряму, лістинг вимкнено; на хостингу ⏳)_
- [ ] Довгий `exclude` проходить через сервер хостингу: `GET /api/message?lang=lv&exclude=<100 ID по 10 цифр>` (≈1300 символів у query, кома кодується як `%2C`) повертає `200` або `404 not_found` у JSON, а не `414`/`400`/HTML від Apache. Так само запит із 200 ID. Якщо ліміт хостингу менший за 1300 символів — повідомити користувача (потрібне рішення про зменшення списку на фронті, `API.md` не змінювати односторонньо). _(локально ✔ на Apache за замовчуванням: 100 ID — 1313 символів, 200 ID — 2613 символів, обидва 200/404 JSON; на хостингу ⏳ — його ліміти невідомі)_
- [ ] Заголовок `Authorization: Bearer …` доходить до PHP: `login` → `me` з отриманим токеном повертає `200`, а не `401` (перевірено на хостингу, не лише локально). _(локально ✔ на Apache + mod_php: `login` → `me` = 200; **без правила в `.htaccess` токен до PHP не доходить** — перевірено мутацією; на хостингу ⏳, можливо FastCGI)_
- [ ] На хостингу `REMOTE_ADDR` збігається з реальною публічною адресою клієнта (перевірено діагностичним скриптом з двох різних мереж, скрипт видалено). Якщо ні — вхід заблоковано до рішення користувача (див. вище); результат перевірки записано в `docs/BACKEND.md`. _(⏳ хостинг: `diag.php` з двох мереж; процедуру й зупинку «якщо не справжній — до користувача» описано в `deployment.md`)_
- [ ] Ліміт спроб входу працює на хостингу наскрізно: 5 невдалих входів з однієї адреси → `429` із `Retry-After`; вхід з іншої адреси (напр. з телефону через мобільну мережу) при цьому проходить; після вікна (15 хв) вхід знову можливий. _(⏳ хостинг; логіку ліміту покрито `tests/api/auth.php` локально)_
- [ ] Боєві облікові дані створено за описаною процедурою: у серверному `.env` лише хеш пароля й `TOKEN_SECRET` (≥ 32 символи, згенерований випадково на сервері); пароль передано клієнту безпечним каналом і не лишився в історії команд, чатах і файлах репозиторію; вхід у боєву адмінку виконано, термін токена — 7 діб (`expiresAt` ≈ +168 год). _(частково: **процедуру й скрипт `bin/generate-admin-credentials.php` готово й перевірено локально** — пароль лише в STDERR, хеш відповідає паролю, `AuthConfig` приймає конфіг; ⏳ створення боєвих даних на сервері й передача пароля клієнту)_
- [ ] `.env`, файли міграцій, `.git`, `vendor`/службові папки недоступні по HTTP (`403`/`404`). _(локально ✔: 14 службових шляхів → 403/404 без вмісту; на хостингу ⏳)_
- [ ] HTTP автоматично редиректить на HTTPS. _(локально ✔: `301` на `https://` зі збереженням query, умова `X-Forwarded-Proto` проти циклу за проксі; на хостингу ⏳)_
- [ ] Секрети (пароль БД, ключ токена, хеш пароля адміна) лише на сервері, не в репозиторії; права на `.env` обмежені. _(⏳ хостинг: розкладка `~/orakuls/.env` вище `public_html` описана, права на файл виставляються на сервері)_
- [ ] Помилки PHP не виводяться клієнту (`display_errors=Off`), лог помилок пишеться. _(частково: `api/.user.ini` з `display_errors=Off` готовий; `ErrorHandler` не віддає деталей клієнту — покрито тестами; ⏳ чи діє `.user.ini` на хостингу)_
- [ ] Перевірено ліміти PHP на хостингу (`post_max_size`, `memory_limit`, `max_execution_time`, а в MySQL — `max_allowed_packet`: пакет імпорту з 100 найдовших фраз ≈ 600 КБ, у розробці — 4 МБ): найгірший запит імпорту (BE-007: 1000 елементів × 3 × 500 чотирибайтних символів ≈ 6 МБ) проходить; якщо `post_max_size` менший за 8 МБ — підняти через `.user.ini` / cPanel або зафіксувати в `docs/BACKEND.md`, що фронт має слати менші шматки. _(⏳ хостинг: `.user.ini` із `post_max_size=8M`, `memory_limit=128M` готовий, `diag.php` покаже реальні значення й `max_allowed_packet`)_
- [ ] З'ясовано, куди на цьому хостингу йде `error_log()` (`ini_get('error_log')`): якщо це файл `error_log` у `public_html`, він недоступний по HTTP (`403`/`404`) або перенаправлений поза веб-корінь (`.user.ini` / cPanel). _(⏳ хостинг: `diag.php` показує `error_log`)_
- [ ] Лог не росте безмежно: він іде в лог, який ротує сам хостинг, або є інше рішення, що не потребує ручного обслуговування (клієнт хостинг не доглядає). Підхід записано в `docs/BACKEND.md`. _(⏳ хостинг)_
- [x] Порядок розгортання і відкату описаний у `docs/BACKEND.md` так, що його може повторити інший розробник. _(2026-11-03: описано в `backend/docs/deployment.md` (пакет, порядок оновлення, резервна копія, відкат) із посиланням у `docs/BACKEND.md`; фактичне проходження — на хостингу)_
