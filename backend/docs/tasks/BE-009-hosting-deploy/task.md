# BE-009 · Розгортання на GoDaddy (cPanel)

| Поле | Значення |
|------|----------|
| Тип | Task |
| Пріоритет | High |
| Компонент | backend, devops |
| Залежить від | BE-001 (правила `.htaccess`); повна перевірка — після BE-003 і BE-004 (боєві облікові дані адміна й перевірка IP потребують готової авторизації) |

## Опис

Налаштувати хостинг GoDaddy Web Hosting (cPanel, Apache) так, щоб фронт і API працювали на одному домені без CORS: `/` і `/admin/` — статика фронта, `/api/*` — PHP. Закрити пункти 4 і 5 із запиту F-003 (заголовок `Authorization`, роздача статики).

Версії на хостингу: PHP 8.4 (потрібно вибрати вручну — типова 8.3), MySQL 5.7 ([BACKEND.md](../../../../docs/BACKEND.md)). Перед стартом звірити реальні версії в cPanel і виправити документацію, якщо вони відрізняються.

## Обсяг

- Вибрати PHP 8.4 для домену («Select PHP Version»), перевірити потрібні розширення: `pdo_mysql`, `mbstring`, `json`, `openssl`/`sodium`.
- Створити БД і користувача MySQL 5.7 у cPanel; застосувати схему (BE-002).
- Розкласти файли: статика `frontend/dist/` → корінь сайту, `dist/admin/` → `/admin/`; код бекенда й конфіг (`.env`) — поза веб-коренем, у `public_html` лише точка входу API.
- `.htaccess`:
  - передача `Authorization` у PHP (`RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]`);
  - `/api/*` → точка входу PHP; існуючі файли й папки (статика) не перехоплюються;
  - `/admin/` віддає `admin/index.html` (`DirectoryIndex`);
  - заборона доступу до службових файлів (`.env`, міграції, `.git`);
  - редирект на HTTPS.
- Налаштувати призначення `error_log()` (див. критерії нижче): без публічного файлу логів і без безмежного росту.
- **Боєві облікові дані адміна** (рішення користувача: робимо перед BE-009). Розробник генерує на сервері логін, надійний пароль і `TOKEN_SECRET`, записує в серверний `.env` лише хеш пароля й секрет, а пароль передає клієнту безпечним каналом (менеджер паролів або одноразове посилання; не поштою й не в месенджері відкритим текстом). Порядок і процедуру зміни пароля записати в `backend/docs/configuration.md`. Термін сесії за замовчуванням — 7 діб (`TOKEN_TTL_HOURS=168`).
- **Перевірка реального IP клієнта за проксі хостингу.** Лімітування спроб входу (BE-004) спирається на `REMOTE_ADDR`. Якщо GoDaddy ставить перед сайтом проксі, `REMOTE_ADDR` буде спільним для всіх відвідувачів, і 5 чужих невдалих спроб заблокують вхід самому адміну. Перевірити тимчасовим діагностичним скриптом (виводить `REMOTE_ADDR`, `HTTP_X_FORWARDED_FOR`, `HTTP_X_REAL_IP`, `HTTP_CF_CONNECTING_IP`, `HTTP_FORWARDED`), порівняти з реальною публічною адресою клієнта, потім видалити скрипт. Якщо `REMOTE_ADDR` — не справжній IP: **зупинитись і звернутись до користувача** за рішенням, якому заголовку довіряти (довіряти `X-Forwarded-For` без перевірки не можна: його підробляє будь-який клієнт), нічого не змінюючи в коді мовчки.
- Сторінка «деплой» у `docs/BACKEND.md`: покроковий порядок оновлення (файли, міграції, перевірка).

## Acceptance criteria

- [ ] У cPanel для домену вибрано PHP 8.4; `phpinfo()` (тимчасово) або службова перевірка підтверджує версію, після чого тимчасовий файл видалено.
- [ ] Реальні версії PHP і MySQL на хостингу збігаються з `docs/BACKEND.md` (або документацію виправлено).
- [ ] `GET https://<домен>/` віддає сторінку користувача, `GET https://<домен>/admin/` — адмінку (статика, без участі PHP).
- [ ] `GET https://<домен>/api/message?lang=lv` обробляється PHP і повертає JSON за контрактом; запит на неіснуючий `/api/…` повертає JSON-помилку `404`, а не HTML-сторінку Apache.
- [ ] Статичні файли (JS/CSS/зображення) віддаються напряму, правила `/api` їх не перехоплюють.
- [ ] Довгий `exclude` проходить через сервер хостингу: `GET /api/message?lang=lv&exclude=<100 ID по 10 цифр>` (≈1300 символів у query, кома кодується як `%2C`) повертає `200` або `404 not_found` у JSON, а не `414`/`400`/HTML від Apache. Так само запит із 200 ID. Якщо ліміт хостингу менший за 1300 символів — повідомити користувача (потрібне рішення про зменшення списку на фронті, `API.md` не змінювати односторонньо).
- [ ] Заголовок `Authorization: Bearer …` доходить до PHP: `login` → `me` з отриманим токеном повертає `200`, а не `401` (перевірено на хостингу, не лише локально).
- [ ] На хостингу `REMOTE_ADDR` збігається з реальною публічною адресою клієнта (перевірено діагностичним скриптом з двох різних мереж, скрипт видалено). Якщо ні — вхід заблоковано до рішення користувача (див. вище); результат перевірки записано в `docs/BACKEND.md`.
- [ ] Ліміт спроб входу працює на хостингу наскрізно: 5 невдалих входів з однієї адреси → `429` із `Retry-After`; вхід з іншої адреси (напр. з телефону через мобільну мережу) при цьому проходить; після вікна (15 хв) вхід знову можливий.
- [ ] Боєві облікові дані створено за описаною процедурою: у серверному `.env` лише хеш пароля й `TOKEN_SECRET` (≥ 32 символи, згенерований випадково на сервері); пароль передано клієнту безпечним каналом і не лишився в історії команд, чатах і файлах репозиторію; вхід у боєву адмінку виконано, термін токена — 7 діб (`expiresAt` ≈ +168 год).
- [ ] `.env`, файли міграцій, `.git`, `vendor`/службові папки недоступні по HTTP (`403`/`404`).
- [ ] HTTP автоматично редиректить на HTTPS.
- [ ] Секрети (пароль БД, ключ токена, хеш пароля адміна) лише на сервері, не в репозиторії; права на `.env` обмежені.
- [ ] Помилки PHP не виводяться клієнту (`display_errors=Off`), лог помилок пишеться.
- [ ] З'ясовано, куди на цьому хостингу йде `error_log()` (`ini_get('error_log')`): якщо це файл `error_log` у `public_html`, він недоступний по HTTP (`403`/`404`) або перенаправлений поза веб-корінь (`.user.ini` / cPanel).
- [ ] Лог не росте безмежно: він іде в лог, який ротує сам хостинг, або є інше рішення, що не потребує ручного обслуговування (клієнт хостинг не доглядає). Підхід записано в `docs/BACKEND.md`.
- [ ] Порядок розгортання і відкату описаний у `docs/BACKEND.md` так, що його може повторити інший розробник.
