# BE-004 · Авторизація адміна

| Поле | Значення |
|------|----------|
| Тип | Story |
| Пріоритет | High |
| Компонент | backend, security |
| Залежить від | BE-001, BE-002 |
| Блокує | BE-005 … BE-008 |

## Опис

Як адмін, я хочу увійти в адмінку за логіном і паролем та залишатись залогіненим, поки токен дійсний, щоб керувати фразами. Решта світу не повинна мати доступу до `/api/admin/*`.

Адмін **один**, без ролей. Логін і пароль задаються в конфігурації бекенда; ендпоінтів створення/зміни акаунта немає. Формат токена — на розсуд бекенду (фронт його не розбирає).

## Обсяг

- `POST /api/admin/auth/login` — тіло `{ "login", "password" }` → `200 { "token", "expiresAt" }`.
- `GET /api/admin/auth/me` → `200 { "login": "admin" }`.
- Middleware для всіх `/api/admin/*`, окрім `login`: перевірка `Authorization: Bearer <token>`.
- Облікові дані: логін і **хеш** пароля (`password_hash`, Argon2id/bcrypt) у конфігурації; порівняння через `password_verify`.
- Токен: підписаний (HMAC-SHA256, ключ у конфігурації) із терміном дії — стандартно 24 год (за прикладом у `API.md`); stateless, без таблиці сесій. `expiresAt` — ISO 8601 UTC.
- Rate limit спроб входу за IP через таблицю `login_attempts` (напр. 5 невдалих за 15 хв → `429 rate_limited`). Таблицю створює **ця задача** власною міграцією (`ip`, `attempted_at`, індекс по `(ip, attempted_at)`) і додає її в `schema.sql`; BE-002 дає лише runner міграцій.
- Старі записи `login_attempts` не накопичуються: прострочені (поза вікном) видаляються під час перевірки — таблиця не росте безмежно, обслуговування не потрібне.
- Утиліта для генерації хеша пароля (CLI-скрипт) — описана в `docs/BACKEND.md`.

## Acceptance criteria

- [ ] Правильні логін і пароль → `200` з `token` (рядок) та `expiresAt` (ISO 8601, UTC, у майбутньому).
- [ ] Невірний логін **або** невірний пароль → `401 unauthorized` з однаковим повідомленням (не видно, що саме невірне); час відповіді не розкриває існування логіна.
- [ ] Відсутнє/некоректне тіло або порожні поля `login`/`password` → `400 bad_request` або `422 validation_error` (рішення зафіксоване в `BACKEND.md`), але не `500`.
- [ ] `GET /api/admin/auth/me` з дійсним токеном → `200 { "login": "admin" }`.
- [ ] Будь-який `/api/admin/*` (крім `login`) без заголовка `Authorization` → `401 unauthorized` у стандартному форматі помилок.
- [ ] Прострочений токен, токен із зміненим підписом чи зміненим payload, а також токен із чужим ключем → `401`.
- [ ] Заголовок з іншою схемою (`Basic …`) або без токена після `Bearer` → `401`.
- [ ] Після N невдалих спроб входу з одного IP наступна спроба (навіть із правильним паролем) → `429 rate_limited` до закінчення вікна; після вікна вхід знову можливий.
- [ ] Успішний вхід не збільшує лічильник невдалих спроб.
- [ ] Таблиця `login_attempts` створюється окремою нумерованою міграцією (ідемпотентно через runner з BE-002) і присутня в `schema.sql`; застосування `schema.sql` на чистій БД дає ту саму схему.
- [ ] Записи старші за вікно обмеження видаляються, таблиця не росте безмежно.
- [ ] Пароль у конфігурації зберігається лише як хеш; пароль, токен і ключ не потрапляють у логи.
- [ ] Ключ підпису токена, логін і хеш пароля читаються з конфігурації поза репозиторієм; у `.env.example` — лише заглушки.
- [ ] Відповіді логіну мають `Cache-Control: no-store`.
