## Опис

Як адмін, я хочу увійти в адмінку за логіном і паролем та залишатись залогіненим, поки токен дійсний, щоб керувати фразами. Решта світу не повинна мати доступу до `/api/admin/*`.

Адмін **один**, без ролей. Логін і пароль задаються в конфігурації бекенда; ендпоінтів створення/зміни акаунта немає. Формат токена — на розсуд бекенду (фронт його не розбирає). Фронт уже вміє показувати окремі повідомлення для `401` («Неверный логин или пароль») і `429` («Слишком много попыток…»), не відправляє порожні поля, а при `401` на будь-якому запиті очищає токен і повертає на форму входу.

Прийняті рішення (докладно — `backend/docs/decisions.md`, D-20 … D-23):
- **Захист за замовчуванням закритий (fail-closed).** Перевірка токена виконується в `Kernel` **до** маршрутизації для будь-якого шляху під `/api/admin/`, окрім `POST /api/admin/auth/login`. Майбутній адмін-ендпоінт неможливо «забути» захистити; невідомий адмін-шлях без токена дає `401`, а не `404`.
- **Токен — JWT HS256 без бібліотек.** Підпис HMAC-SHA256. Ключ підпису виводиться з `TOKEN_SECRET` **і** хеша пароля: зміна пароля або секрету автоматично анулює всі видані токени, окремий список відкликаних не потрібен.
- **Ліміт спроб — за IP**, а не за логіном: ліміт за логіном дозволив би будь-кому заблокувати адміна. IP береться лише з `REMOTE_ADDR` (заголовок `X-Forwarded-For` підробляється, йому не довіряємо).
- **Порожні/некоректні поля логіна — `422`**, некоректний JSON — `400`; такі запити не рахуються як спроби входу.

## Обсяг

- `POST /api/admin/auth/login` — тіло `{ "login", "password" }` → `200 { "token", "expiresAt" }`.
- `GET /api/admin/auth/me` → `200 { "login": "admin" }`.
- **Guard у `Kernel`** (клас `Http\AdminGuard` або подібний): шлях, що починається з `/api/admin/`, окрім `POST /api/admin/auth/login`, вимагає `Authorization: Bearer <token>`; без дійсного токена — `401 unauthorized` ще до пошуку маршруту. Схема `Bearer` нечутлива до регістру; зайві пробіли, інші схеми, порожній токен → `401`.
- **Облікові дані** з конфігурації: `ADMIN_LOGIN`, `ADMIN_PASSWORD_HASH` (результат `password_hash`, `PASSWORD_DEFAULT`; `password_verify` підтримує й argon2id, якщо хеш зроблено ним), `TOKEN_SECRET` (не коротший за 32 символи), `TOKEN_TTL_HOURS` (за замовчуванням **168 — 7 діб**, рішення користувача; діапазон 1…720; порожнє значення = за замовчуванням). Приклад в `API.md` показує добу, але це лише приклад: контракт термін не фіксує.
- **Fail-closed при помилці конфігурації**: порожній чи некоректний `ADMIN_PASSWORD_HASH` (`password_get_info()['algo']` порожній), `TOKEN_SECRET` коротший за 32 символи або відсутній `ADMIN_LOGIN` → `500 server_error` на логіні **та** на guard'і (доступ ніколи не відкривається), причина — один рядок у `error_log`.
- **Токен** — `base64url(header).base64url(payload).base64url(signature)`; header рівно `{"alg":"HS256","typ":"JWT"}` (порівнюється як рядок, поле `alg` з токена не довіряється); payload `{"sub": <логін>, "iat": <unix>, "exp": <unix>}`; підпис = `HMAC-SHA256(header.payload, ключ)`, де ключ = `HMAC-SHA256(TOKEN_SECRET, ADMIN_PASSWORD_HASH)`. Перевірка: рівно три частини → точний header → `hash_equals` для підпису → JSON payload → `exp` у майбутньому → `sub` збігається з `ADMIN_LOGIN`. `expiresAt` — ISO 8601 UTC (потрібен новий `Iso8601::fromTimestamp(int)`).
- **Логін**: некоректний JSON/порожнє тіло → `400`; `login` і `password` мають бути непорожніми рядками, пароль ≤ 1024 байт (bcrypt усе одно ігнорує байти після 72-го, але довгі рядки не обробляємо) → інакше `422` з `fields` (`login: required`, `password: required | too_long`), у спроби не рахується. Далі: перевірка ліміту (дешевий запит до БД) **до** `password_verify`; потім `password_verify` виконується **завжди**, навіть якщо логін не збігся (логін порівнюється через `hash_equals`), щоб час відповіді не розкривав існування логіна. Невдача → запис спроби й `401` з однаковим повідомленням; успіх → `200`.
- **Rate limit** за IP через таблицю `login_attempts`: 5 невдалих спроб за 15 хв → `429 rate_limited` із заголовком `Retry-After` (секунди до виходу найстарішої спроби з вікна). Заблоковані запити в таблицю не записуються і `password_verify` не запускають (bcrypt у PHP 8.4 коштує ≈170 мс CPU на запит). Успішний вхід лічильник не збільшує. Прострочені записи видаляються під час перевірки.
- **IP клієнта**: `Request` отримує поле `ip` (з `REMOTE_ADDR`; якщо немає, наприклад у тестах, — `'unknown'`); конструктор лишається сумісним (новий параметр у кінці зі значенням за замовчуванням).
- **Міграція** `database/migrations/002_create_login_attempts.sql`: `id BIGINT UNSIGNED AUTO_INCREMENT`, `ip VARCHAR(45) NOT NULL`, `attempted_at DATETIME NOT NULL` (UTC, без DEFAULT, пишеться через `UTC_TIMESTAMP()`), індекс по `(ip, attempted_at)`, `utf8mb4_unicode_ci`, InnoDB. Після неї — `php bin/build-schema.php` (оновлює `schema.sql`).
- **Інструменти**: `bin/hash-password.php` — читає пароль зі stdin (у терміналі без відлуння, пароль **ніколи** не передається аргументом: він лишився б в історії оболонки), друкує хеш. Порядок задання облікових даних і генерація `TOKEN_SECRET` (`php -r "echo bin2hex(random_bytes(32));"`) описані в `backend/docs/configuration.md`. Хеш містить `$` — у `.env` його беруть **в одинарні лапки** (у подвійних `docker compose` вважає `$…` змінною й сипле попередженнями; перевірено).
- **Відповіді** логіну та `me` мають `Cache-Control: no-store` (помилки його вже мають).
- **Тести**: облікові дані для тестів задає `tests/api.php` через `putenv` **до** `bootstrap` (`ADMIN_LOGIN`, `ADMIN_PASSWORD_HASH` з `password_hash(..., ['cost' => 4])` для швидкості, `TOKEN_SECRET`), тож тести не залежать від `.env`. Для перевірки терміну дії `TokenService` приймає «поточний час» параметром. Наявні тести `tests/api/database.php` **доведеться оновити**: вони жорстко прописують список таблиць `['migrations','phrases']`, єдину міграцію `001…`, `COUNT(*) = 1` і застосовані `['001…']`; тест невдалої міграції використовує файл `002_probe.sql` (перейменувати на `900_probe.sql`, щоб не плутати з реальною `002`).

## Поза обсягом

- Ендпоінт виходу (`logout`): його немає в контракті, токен stateless, фронт просто видаляє його локально.
- Оновлення токена (refresh), кілька адмінів, зміна пароля через API, двофакторна автентифікація, CAPTCHA, білий список IP.
- Блокування за логіном (дозволило б зловмиснику заблокувати адміна).
- `X-Forwarded-For` (підробляється); чи є `REMOTE_ADDR` на хостингу справжнім IP клієнта, перевіряється в BE-009.
- Логування кожної невдалої спроби входу (за D-06 4xx не логуються; інакше лог ріс би під атакою).

## Acceptance criteria

- [x] Правильні логін і пароль → `200` з `token` (рядок із трьох частин через крапку) та `expiresAt` (ISO 8601, UTC, закінчується на `Z`, у майбутньому; різниця з поточним часом = `TOKEN_TTL_HOURS`). Без `TOKEN_TTL_HOURS` (змінна відсутня або порожня) термін дорівнює 168 годинам; значення поза 1…720 або нечислове → `500` як некоректна конфігурація.
- [x] Невірний логін **або** невірний пароль → `401 unauthorized` з однаковим повідомленням і однаковим тілом (не видно, що саме невірне); `password_verify` виконується в обох випадках.
- [x] Некоректний JSON або порожнє тіло → `400 bad_request`. Відсутні, не рядкові чи порожні `login`/`password`, а також пароль довший за 1024 байти → `422 validation_error` з відповідним полем у `fields`. Жоден із цих запитів не дає `500` і не рахується як спроба входу.
- [x] `GET /api/admin/auth/me` з дійсним токеном → `200 { "login": "<ADMIN_LOGIN>" }` і `Cache-Control: no-store`.
- [x] Будь-який шлях під `/api/admin/` (у тому числі неіснуючий і з «неправильним» методом, напр. `GET /api/admin/auth/login`) без заголовка `Authorization` → `401 unauthorized` у стандартному форматі; з дійсним токеном неіснуючий шлях → `404`. Єдиний виняток — `POST /api/admin/auth/login`.
- [x] Прострочений токен, токен зі зміненим підписом чи payload, токен, підписаний іншим ключем, токен з двома або чотирма частинами → `401`.
- [x] Токен із підміненим header (`alg: none`, `alg: HS512`, зайві поля) → `401`, навіть якщо підпис «сходиться».
- [x] Схема не `Bearer` (`Basic …`), порожній токен після `Bearer`, зайві пробіли, `Bearer` без пробілу → `401`; `bearer` у нижньому регістрі приймається.
- [x] Після зміни `ADMIN_PASSWORD_HASH` або `TOKEN_SECRET` раніше видані токени перестають діяти (`401`); після зміни `ADMIN_LOGIN` теж.
- [x] Некоректна конфігурація (порожній/невалідний `ADMIN_PASSWORD_HASH`, `TOKEN_SECRET` коротший за 32 символи, відсутній `ADMIN_LOGIN`) → `500 server_error` на логіні й на будь-якому адмін-шляху (доступ не відкривається), причина лише в `error_log`, без значень секретів.
- [x] Після 5 невдалих спроб входу з одного IP наступна (навіть із правильним паролем) → `429 rate_limited` із заголовком `Retry-After` (ціле число секунд, 1…900); заблокований запит не збільшує лічильник і не продовжує блокування; після закінчення вікна вхід знову можливий; інший IP не заблоковано.
- [x] Успішний вхід не збільшує лічильник невдалих спроб; `X-Forwarded-For` не обходить і не підміняє ліміт.
- [x] Таблиця `login_attempts` створюється окремою нумерованою міграцією `002_…` (ідемпотентно через runner) і присутня в `schema.sql`; тести актуальності та паритету `schema.sql` зелені.
- [x] Записи старші за вікно обмеження видаляються під час перевірки; таблиця не росте безмежно.
- [x] `bin/hash-password.php` видає хеш, який проходить `password_verify`; пароль не потрапляє в аргументи командного рядка; інструкція (з одинарними лапками для `$`) є в `configuration.md`.
- [x] Пароль у конфігурації зберігається лише як хеш; пароль, токен, ключ підпису і заголовок `Authorization` не потрапляють у логи й повідомлення про помилки.
- [x] Секрети читаються з конфігурації поза репозиторієм; у `.env.example` — лише заглушки (`ADMIN_PASSWORD_HASH=''`, `TOKEN_SECRET=''`).
- [x] Відповіді логіну й `me` мають `Cache-Control: no-store`.
- [x] Наявні тести (`run.php`, `api.php`, `smoke.php`) лишаються зеленими після додавання міграції `002` (тести `database.php` оновлено, як описано в обсязі).
- [x] Рішення D-20 … D-23 записані в `decisions.md`; документація (`security.md`, `configuration.md`, `architecture.md`, `api-conventions.md`, `error-handling.md`, `database.md`, `testing.md`, `development.md`, `docs/BACKEND.md`) оновлена.

## Як перевірити

Усі команди — з папки `backend/`.

```
docker compose run --rm --no-deps php php tests/run.php        # 74 перевірки: токен, AuthConfig, guard, hash-password, Request::ip …
docker compose exec php php tests/api.php                      # 61 перевірка на orakuls_test (tests/api/auth.php — авторизація); запустити двічі
docker compose exec php php tests/smoke.php                    # по HTTP; неправильних облікових даних не відправляє
docker compose exec php php bin/build-schema.php --check       # schema.sql актуальний (з login_attempts)
docker compose -f docker-compose.yml config -q                 # без попереджень про змінні ($ у хеші — в одинарних лапках)
docker compose exec php php bin/migrate.php                    # Applied: 002_create_login_attempts.sql (одноразово для робочої БД)
```

Вхід по HTTP (локально `admin` / пароль, заданий у `backend/.env`, див. [development.md](../../development.md)):

```
curl -s -i -X POST localhost:8000/api/admin/auth/login -H 'Content-Type: application/json' -d '{"login":"admin","password":"<пароль>"}'
curl -s -i localhost:8000/api/admin/auth/me -H "Authorization: Bearer <token>"      # 200 {"login":"admin"}
curl -s -i localhost:8000/api/admin/anything                                        # 401 (а не 404)
```

Після ручних перевірок ліміту очистити спроби: `DELETE FROM login_attempts` у робочій БД.
