# Тестування

PHPUnit не використовуємо (немає Composer), тож перевірки — невеликі скрипти без залежностей. Усі повертають код виходу `0` при успіху й `1` при провалі, тому підходять для CI.

## Рівні

| Скрипт | Що перевіряє | Потрібна БД | Команда |
|--------|--------------|-------------|---------|
| `tests/run.php` | Логіку напряму, без HTTP: роутер, `Request`, `Json`, формат помилок, `Config`, `SqlSplitter`, `Categories`/`Languages`/`Iso8601`, `DatabaseGuard`, `Migrator::files()`, `SchemaBuilder`, актуальність `schema.sql`, дані сіду | ні | `docker compose run --rm --no-deps php php tests/run.php` |
| `tests/api.php` | Схему, міграції, сід і (з BE-003) ендпоінти на відомих даних тестової БД | `orakuls_test` | `docker compose exec php php tests/api.php` |
| `tests/smoke.php` | Запущений API по HTTP: статуси, заголовки, тіла відповідей; з `SMOKE_ADMIN_LOGIN`/`SMOKE_ADMIN_PASSWORD` — ще й авторизовані ендпоінти з перевіркою типів полів за `API.md` | так | `docker compose exec php php tests/smoke.php [base-url]` |
| `tests/hosting-check.php` | Розгортання по HTTP: правила `.htaccess`, статика, `/api/*`, `Authorization`, службові файли, редиректи з `?qr`; локально проти Apache-контейнера і проти справжнього хостингу | так | `docker compose exec php php tests/hosting-check.php http://apache --local` |

Спільна обв'язка (`test()`, `assertSame()`, `assertTrue()`, `assertThrows()`, `decode()`, `kernelWith()`, `runTests()`) лежить у `tests/lib.php`; її підключають `run.php` і `api.php`. Для перевірок ендпоінтів там же: `apiRequest($method, $path, $query = [], $headers = [], $body = '', $ip = 'unknown')` — виклик API в процесі через спільний `apiKernel()` (маршрути завантажуються один раз, а не на кожен із тисяч запитів; `$query` — уже розібраний масив, `lang[]=lv` задається як `['lang' => ['lv']]`) і `assertUniform()` (див. нижче). Там само `withEnv($vars, $fn)`: тимчасово задає змінні процесу (`putenv`) і в `finally` повертає попередні значення; `null` прибирає змінну (тоді `Config` знову бачить значення з `.env`), порожній рядок — це значення.

### `tests/run.php` — юніт-перевірки

Невелика власна обв'язка:

```php
test('опис того, що перевіряємо', function () {
    $kernel = kernelWith(fn (Router $r) => $r->get('/api/x', fn () => Response::json(['ok' => true])));

    $response = $kernel->handle(new Request('GET', '/api/x'));

    assertSame(200, $response->status);
});
```

- `test($name, $fn)` реєструє перевірку; будь-який виняток усередині — провал.
- `assertSame($expected, $actual)` — сувора рівність (`===`), `assertTrue($cond)`, `assertThrows($fn, $class)` — перевіряє клас винятку й повертає його.
- `kernelWith(fn (Router $r) => …)` створює `Kernel` з довільними маршрутами, не торкаючись `routes.php`.
- `decode($response)` розбирає тіло відповіді в масив.
- `error_log()` перенаправлено в тимчасовий файл, тож можна перевірити, що деталі помилки потрапили в лог, а не у відповідь.

Зараз покрито: параметри шляху; `404` для невідомого шляху й методу; `400` на некоректне тіло й параметр-масив; кодування JSON (юнікод, числа, `{}` замість `[]`); формат кожної помилки й відповідність кодів `API.md`; `500` без витоку деталей; перетворення PHP warning на `500`; розбір `.env`; розбирач SQL (рядки, коментарі, `/*! */`, `DELIMITER`, CRLF); єдині списки категорій і мов; формат дат; запобіжник за іменем БД; перевірку імен міграцій; точний вигляд згенерованого `schema.sql` і його актуальність; цілісність даних сіду; `IdList::parse()` (таблиця «вхід → результат», ліміт 200, гігантські рядки), `Request::rawQuery()` і те, що `GET /api/message` перевіряє `lang` до звернення до БД (`400` без БД).

Авторизація (BE-004, без БД): `ApiException::rateLimited` і `Retry-After` у відповіді `ErrorHandler`; `Request::fromGlobals()` бере `ip` лише з `REMOTE_ADDR` (`X-Forwarded-For` ігнорується); `Iso8601::fromTimestamp()`; **`TokenService`** — межі терміну (`exp > now` суворо), залежність ключа від хеша/секрету/логіна, зміна кожного символу кожної з трьох частин, підміна header (`none`, `HS512`, зайве поле — навіть коли підпис пораховано «правильно»), неканонічний base64url (паддінг, `+`/`/`, зайві біти), токен > 2048 символів, нерядкові/відсутні поля payload (кожен негативний випадок має позитивний контроль: коректно підписаний токен проходить); **`AuthConfig::fromEnv`** — кожна некоректна конфігурація дає `500`, у лозі є назва змінної і немає значень; **`AdminGuard`** — публічні шляхи не викликають провайдер конфігурації, помилка конфігурації на адмін-шляху дає `500`, боєвий `Kernel::create()` містить guard; **`bin/hash-password.php`** через `proc_open` (pipe-гілка: валідний пароль, межі 12 символів / 72 байти, порожній ввід, `NUL`, пароль в аргументах ігнорується).

Список фраз (BE-005, без БД): `Domain\Phrase::fromRow()`/`toArray()` (типи, порядок ключів у JSON, `'1'`/`'0'` рядками, некоректна дата → виняток), `PhraseFilter::offset()`, `PhraseRepository::escapeLike()` і `lacksTextSql()`, `PhraseController::parseFilter()` — таблиця «query → результат або `400`» для кожного параметра (порожні значення, межі `page` 999 999 999 / `perPage` 100, `"1\n"`, `050`, масиви, 200 символів кирилиці, повідомлення без значення, що прийшло).

Запис фраз (BE-006, без БД): **`Domain\PhraseValidator`** (13 перевірок, `pv*`-хелпери) — таблиця «вхід → точні `fields`» (порядок ключів значущий): валідне тіло і trimmed тексти; `category` (`required`/`invalid`: `LOVE`, `love `, `5`, `["love"]`, `""`, `true`); `text` (немає → `required`, не об'єкт → `invalid`, `{}`/`[]` → `empty`); `text.xx` (немає ключа або `null` → порожній переклад `""` без помилки, не рядок → `invalid`, невалідний UTF-8; D-30); довжина 500/501 для `a`, `š`, `я`, `😀` і пробіли навколо; `text = empty` (пробіли, `\n`, `\t`, `U+00A0`, `U+3000`, `U+FEFF`, `U+2028`; не `empty` для `U+200B` / `U+0085`; не `empty` разом із помилкою `text.xx`; усі три мови `null`/відсутні → `empty`; єдина непорожня мова за відсутніх решти → успіх); керівні символи (`\0`, `\x01`, `\x02`, `\x7F`, `\x0B`… всередині й на краю; `\n`, `\r\n`, `\t`, C1 проходять); `isActive`; кілька помилок разом; зайві ключі; `trim()` (що обрізається, що ні, `😀 `); відсутність `use App\Http` / `use App\Repository` у файлах домену; лінійність `trim()` на 500 000 пробілів усередині тексту.

### `tests/smoke.php` — перевірка по HTTP

Бере базову адресу з аргументу, змінної `BASE_URL` або `http://localhost:8000`. Перевіряє `/api/health`, формат `404`, метод, якого немає для шляху, кінцевий слеш, `GET /api/admin/stats` без токена (`401`, `no-store`) та `GET /api/message`: `400` без `lang` і з `lang=de`; `lang=lv` (з `exclude` і без) дає **або** `200` з ключами рівно `id`, `lang`, `text` і `no-store`, **або** `404 not_found` (робоча БД може бути порожньою), але не `400`/`500`; `POST` → `404`.

Те саме можна запустити проти хостингу (з контейнера, бо PHP на машині немає):

```
docker compose run --rm --no-deps php php tests/smoke.php https://<домен>
```

Поточні перевірки лише читають, тож безпечні для прода; **з'явилися дві групи, що пишуть**: перевірки статистики та CRUD тимчасової фрази (нижче).

**Змінні оточення smoke** (усі необов'язкові): `SMOKE_ADMIN_LOGIN` + `SMOKE_ADMIN_PASSWORD` — **правильні** облікові дані: вмикають авторизовані перевірки (`login` → типи `token`/`expiresAt`; `me`; список фраз і `Phrase` — `id` число, `isActive` boolean, дати ISO UTC, `text` з `lv`/`en`/`ru`; `400` на погані фільтри; `404` на неіснуючий `id`; `422` на порожнє тіло; `stats` і `visits` — усі числа `int`, `byCategory`/`missing`/`byLang` — об'єкти з усіма ключами; порожній імпорт). Неправильні дані скрипт не шле ніколи. `SMOKE_WRITE=1` додає запис: див. нижче. Без облікових даних ці перевірки пропускаються (`skip`).

**Групи, що пишуть** вмикаються лише `SMOKE_WRITE=1`: (1) статистика (BE-011: `POST /api/visit` → `204` додає +1 `visit`; BE-012: дві видачі `GET /api/message?lang=lv` → `200` додають +2 до `message_lv`); (2) повний цикл CRUD однієї тимчасової фрази (`POST` → `GET` → `PUT` → `DELETE`, наприкінці фраза видаляється навіть при збої посеред; змінює лише `AUTO_INCREMENT`). Проти прода перед друком QR цей прапорець не вмикати: скинути лічильники нічим. Імпорт у smoke перевіряється лише порожнім `items` (нічого не створює). Окремо для адмінки: smoke **не відправляє неправильних облікових даних** — вони рахуються в ліміт спроб входу, і на хостингу smoke заблокував би IP розробника на 15 хвилин. Дозволено лише запити, що відхиляються до перевірки пароля: без токена (`401`), `{}` (`422`), не-JSON (`400`). З BE-005: `GET /api/admin/phrases`, `/api/admin/phrases/1` і `/api/admin/phrases?perPage=0` без токена → `401` (guard раніше за валідацію). З BE-006: `POST /api/admin/phrases`, `PUT /api/admin/phrases/1`, `DELETE /api/admin/phrases/1` без токена → `401` — нічого не пишеться, тож безпечно для прода (23 перевірки в smoke). З BE-007: `POST /api/admin/phrases/import` без токена, з порожнім тілом → `401` (24 перевірки в smoke).

## Як додати перевірку

1. Нова логіка без БД → `test(…)` у `tests/run.php`.
2. Поведінка запущеного сервера «знизу вгору» (статус, заголовки), безпечна для прода → блок у `tests/smoke.php`.
3. Ендпоінт, що читає чи пише в БД → новий файл `tests/api/<назва>.php` (його підхоплює `tests/api.php`, сам скрипт міняти не треба) на відомих даних сіду; новий випадок — в кінець сіду.
4. Перевіряти і щасливий шлях, і помилки (`400`, `401`, `404`, `422`) разом із **типами полів** (`42`, а не `"42"`; `true`, а не `1`).

## Третій рівень: перевірки проти тестової БД

Перевірки, що потребують відомих даних (схема, міграції, випадковий вибір без повторів, фільтри та пагінація, валідація, імпорт), виконуються на окремій базі `orakuls_test` ([D-14](decisions.md)).

```
docker compose exec php php tests/api.php
```

Що робить скрипт на старті, щоразу:

1. фіксує `DB_NAME=orakuls_test` (`putenv` до `bootstrap`, тож `DB_NAME` з `.env` ігнорується);
2. `DatabaseGuard::assertTestDatabase()` — не `*_test` → повідомлення в STDERR, код `1`, нічого не змінено;
3. `resetTestDatabase()` — видаляє всі таблиці; `Migrator::up()` — накочує міграції з нуля; `reseed()` — заливає сід;
4. підключає `tests/api/*.php` і виконує перевірки; ендпоінти викликає через `Kernel` у процесі, без HTTP.

Чому в процесі, а не по HTTP: запущений на :8000 сервер працює з робочою БД з `.env`, тож HTTP-тести не мали б відомих даних. Через це ж `tests/api.php` не торкається `orakuls`.

| Файл | Що |
|------|----|
| `tests/api.php` | Підготовка БД і запуск; змінювати не треба |
| `tests/db-lib.php` | `testPdo()`, `testMigrator()`, `resetTestDatabase()`, `reseed()` (повертає карту `key → id`; після BE-011 ще й очищає `daily_stats`), `phraseCount()`, `schemaSignature()`, `keepOnlyActive()`, `bytesSent()`, `withBigTable($fn)` (600 фраз у транзакції, що відкочується, потім `reseed()`), `withFreshSeed($fn)` (`reseed()` до і після `$fn`, у `finally`; для тестів, що пишуть), `tableDump()` (усі рядки `phrases` за `id` — для перевірок «БД не змінилась»), `statementCount($fn)` (див. нижче) |

Підключається з `tests/api.php` після `db-lib.php`, тож тест-файли не залежать від порядку підключення один одного |

| `tests/api/stats.php` | Зведення для адмінки (BE-008): типи й форма, оракул сіду, порожня БД, збіг зі списком, миттєве відображення змін, один SQL-запит, 600 фраз |

Правила:

- **Тест, що пише в БД (`POST`/`PUT`/`DELETE`, прямі `INSERT`/`UPDATE`), обгортається в `withFreshSeed(function () { … })`**: `reseed()` до і після (у `finally`), тож тест не залежить від сусідніх і нічого їм не лишає (`TRUNCATE` повертає і дані, і `AUTO_INCREMENT`: новий `POST` на свіжому сіді дає `id` 31). Не викликати `withFreshSeed` усередині `withBigTable` і навпаки: `TRUNCATE` комітить транзакцію. Двічі поспіль запущений `tests/api.php` має бути зеленим.
- Тести не покладаються на порядок виконання файлів між собою; перевірка **паритету схеми** (`tests/api/database.php`) скидає БД і сама відновлює стан, тому стоїть останньою у своєму файлі.
- Сід лежить у `database/seed/phrases.php`. Порядок рядків = `id`; нові випадки додаються **лише в кінець**.
- У `Seeder::CREATED_AT` дата фіксована, тож `createdAt` у відповідях можна порівнювати зі сталим значенням.

### Що покриває `tests/api/database.php`

Міграції на порожній БД; ідемпотентність повторного `up()`; `status()`; помилка в другому операторі міграції (не ковтається, міграція не записується, повтор доробляє решту); InnoDB і колації; типи й default колонок (дати без `DEFAULT`); round-trip діакритики, кирилиці, емодзі та переносів рядка; рівно 500 символів; 501-й → помилка `1406` замість мовчазного обрізання; індекси; `UTC_TIMESTAMP()` і `Iso8601`; типи `int` для `id` і `is_active`; детермінізм сіду (`reseed()` двічі → та сама карта `key → id`) і його склад; пошук без урахування регістру й діакритики; **паритет**: імпорт `schema.sql` дає ту саму схему (за `information_schema`), що й міграції, і після нього `Migrator::up()` нічого не застосовує.

### Що покриває `tests/api/message.php`

Форма відповіді (ключі `id`, `lang`, `text` у цьому порядку, `id` — число); `Cache-Control: no-store` у `200`, `400`, `404`; некоректний `lang` (відсутній, порожній, `de`, `LV`, `lv `, масив) → `400` без `fields`; неактивні фрази не видаються; порожні й «лише пробіли» переклади не видаються для своєї мови (множина виданих ID за 3000 запитів = кандидати, виведені з сіду); `404`, коли кандидатів немає; `exclude` (8 ID — 0 влучань і рівномірність решти), «усе виключено» → `200`, «лишилась одна» → вона; терпимість `exclude` до сміття, масиву, ін'єкцій, 1500 ID і 1 МБ сміття; ліміт 200 коректних ID (межі 1, 200, 201); рівномірність без `exclude`; точність тексту (діакритика, кирилиця, `\n`, HTML, емодзі, `len500`) за сирим тілом відповіді; «один запит — один рядок»; швидкодія на 600 фразах; відсутність авторизації й зайвих полів; `POST`/`PUT`/`DELETE`/`HEAD`/`PATCH` → `404`.

**Статистичні перевірки.** Рівномірність перевіряє `assertUniform($candidates, $counts, $draws)`: кожен кандидат зустрівся, жоден сторонній ID не випав, а лічильник кожного лежить у межах ±6σ від середнього (`σ = √(n·p·(1−p))`, `p = 1/N`). - **Мутаційна перевірка** (BE-008; перелік мутацій): `SUM` без `(int)`; `active` рахує `is_active = 0`; `missing` через `hasTextSql`; `missing` лише активні; `byCategory` без останньої категорії; `total` = `active`; без `Cache-Control`; `missing` як список (`array_values`); зайвий `SELECT 1` до основного запиту; ключі `missing.en` і `missing.ru` поміняні місцями; контролер читає `category` з query і фільтрує; `lacksTextSql` без `TRIM` — кожна червонить принаймні один тест. Остання мутація **поведінково еквівалентна** у колації `utf8mb4_unicode_ci` (PAD SPACE: `'   ' = ''` істинне й без `TRIM`), тому її ловить лише перевірка вигляду умови (`lacksTextSql('en')` дорівнює `` TRIM(`text_en`) = '' ``) у тесті про `blank_en`.

### Що покриває `tests/api/visit.php` і `tests/run.php` (BE-011)

Файл самодостатній: помічники з префіксом `visit*` (`visitKernel()`, `visitPost()`, `visitSnapshot()`, `visitDiff()`, `visitTotal()`). Тести **не залежать від вмісту `daily_stats`**: порівнюють знімки «до/після» (`visitDiff` повертає лише зміни й падає, якщо лічильник зменшився), тож `assertSame(['2026-11-03|scan' => 1, '2026-11-03|visit' => 1], …)` одразу перевіряє і що зросло, і що більше нічого не змінилось.

- **Підміна часу:** `visitKernel('2026-11-02T22:30:00Z')` збирає `Kernel` із `VisitController(new RigaClock(fn () => …))` — «зараз» задається моментом UTC, зокрема межі 2026-03-29 (доба 23 год), 2026-10-25 (25 год, година 03:xx повторюється) і 2026-12-31 → 2027-01-01. Реальний годинник використовують лише перевірки, нечутливі до півночі (сума по всіх днях).
- **Покрито:** `increment`/`incrementMany` (арифметика 1, 2, 3; незалежні метрики й дні; день за моментом у будь-якій зоні; невідома метрика → виняток і 0 SQL; дублікати; порожній список), `rangeTotals` (форма й типи `string/string/int`, порядок, межі включно, порожні дні відсутні, невалідні аргументи без SQL, рівно 1 запит), `POST /api/visit` (`qr`, `direct`, 18 «дивних» тіл → `direct`, `400` без SQL і без змін, 1 SQL на успіх, боєвий маршрут без авторизації, адреса/`Referer`/`User-Agent` не впливають), випадкова серія з 120 запитів проти оракулу, відсутність персональних даних (сентинели IP/UA/Referer не потрапляють ні в таблиці, ні в лог), збій БД (`RENAME TABLE` у `finally`) → `500` без подробиць, `reseed()` очищає `daily_stats`.
- **50 паралельних запитів** — 50 окремих CLI-процесів (`tests/workers/visit-worker.php`, `proc_open`): кожен підключається до БД, друкує `ready` і чекає на сигнал на STDIN; тест чекає на всіх, потім дає старт одним махом — запити справді одночасні, а не залежать від швидкості старту процесів. Воркер відмовляється працювати з не-`_test` БД (`DatabaseGuard`).
- **У `tests/run.php` (без БД):** `RigaClock::dayOf`/`isDay`/`now`/`today`, `StatMetrics`, порядок «розбір тіла → БД» для `POST /api/visit` (недосяжний `DB_HOST` усе одно дає `400`, а не `500`).
- **Мутаційна перевірка** (BE-011): день за UTC; фіксований зсув `+02:00`; `direct` теж збільшує `scan`; порівняння `source` без урахування регістру; `count = 1` замість `+ 1`; прибрано `Cache-Control`; без перевірки метрики; без `array_unique`; без перевірки `from > to`; `isDay` приймає рік `0000`; `count` рядком; звернення до БД до розбору тіла — кожна червонить принаймні один тест.
- Кінцевий слеш (`/api/visit/`) на рівні `Kernel` не обробляється (його прибирає `Request::fromGlobals()`), тож перевіряється лише по HTTP.

### Що покриває `tests/api/message-counter.php` (BE-012)

Файл самодостатній: помічники з префіксом `counter*` (`counterTotals()` — суми по **всіх** днях, нечутливі до півночі; `counterDelta($fn)` — лише ненульові зміни, зменшення = провал; `counterKernel($source)`; `counterParallel($jobs)`). Тести порівнюють **дельти**, а не припускають порожню `daily_stats`.

- **Покрито:** `200` по кожній мові (+1 лише потрібної метрики), рядок за сьогодні за Ригою, назви метрик; `400` (6 варіантів) і `404` (порожній переклад, усе вимкнено, не-`GET`) нічого не рахують; `exclude` (валідний, сміття, масив, 40 видач із запасним варіантом) — одна видача = +1; кількість SQL (`200` = 2, `404` = 1, `400` = 0); сума `message_*` = кількість відповідей `200`; регресія BE-003 (тіло й порядок заголовків байт у байт, **лог успішних видач порожній**); у таблиці лише `(day, metric, count)`.
- **Збій лічильника:** `RENAME TABLE daily_stats` (5 запитів → `200`, тіло й заголовки ідентичні, у лозі `Message counter failed` без IP/`User-Agent`, після відновлення лічильник працює), тригер `BEFORE INSERT … SIGNAL` (і коли рядка за день немає, і коли він є; `DROP TRIGGER` у `finally`), будь-який `Throwable` через годинник (`RuntimeException`, `PDOException`, `TypeError`, `DivisionByZeroError`, `Error`, PHP warning → `ErrorException`) — це єдиний тест, що відрізняє `catch (Throwable)` від `catch (Exception)`. DDL (`RENAME`, `CREATE TRIGGER`) не виконувати всередині транзакції (`withBigTable`) і завжди відновлювати у `finally`.
- **День за Ригою через контролер:** `kernelWith` + `MessageController(new RigaClock($source))` для моментів із переходами 2026-03-29/2026-10-25 і межі року; той самий момент у різних поясах → той самий день; годинник викликається рівно раз і лише на `200`.
- **Паралельні видачі:** 50 процесів `tests/workers/message-worker.php` з барʼєром на STDIN (гонка **першої вставки** рядка за далекий день `2031-06-15`; бойовий `Kernel::create()` — 20 `lv` + 15 `en` + 15 `ru`). Воркер відмовляється працювати з не-`_test` БД.
- **У `tests/run.php` (без БД):** некоректний `lang` не доходить ні до БД, ні до годинника; сторожовий тест `MessageController` (є `catch (Throwable`, немає `catch (Exception`/`PDOException`, немає функцій дати/часу й SQL — день і SQL живуть у `DailyStatsRepository`).
- **Мутаційна перевірка** (BE-012): без перехоплення; `catch (Exception)`; без логу; рахує й `400`; метрика завжди `message_lv`; лічильник двічі; збій ламає відповідь; лічильник не викликається; неатомарний `increment` — кожна червонить принаймні один тест.

> **Час `tests/api.php`.** Кожна з ~24 000 видач у статистичних тестах `message.php` тепер пише лічильник (`COMMIT` з fsync): прогін подовжився з ≈ 22 до ≈ 45 с. У dev-`docker-compose.yml` MySQL запущено з `--innodb-flush-log-at-trx-commit=2` (довговічність у тестах не потрібна, на хостингу параметр не діє) — прогін ≈ 20 с. Після зміни compose-файлу: `docker compose up -d db`.

### Що покриває `tests/api/visits-report.php` і `tests/run.php` (BE-013)

Файл самодостатній: помічники з префіксом `vr*` (`vrGet()`, `vrOf()`, `vrOracle()`, `vrWithHistory()`, `vrInsert()`, `vrWithStableDay()`). **Оракул** `vrOracle` не використовує `ReportPeriod`/`VisitReport`: ряд дат — `gmmktime` (UTC, без DST), суми — прості цикли над рядками фікстури; додатково ключові перевірки звіряються з **ручними константами** (`VR_MANUAL`), щоб помилка в самому оракулі не лишилась непоміченою. Історію вантажить `vrWithHistory()` (фікстура `database/seed/daily_stats.php`), у `finally` — `reseed()`.

- **Покрито:** `401` (і з поганими параметрами, 0 SQL); форма й порядок ключів, `byLang` — об'єкт у сирому JSON, `int`, `no-store`; порожня таблиця — нулі; історія проти оракулу й ручних чисел (перехід року, місяця, дні без даних, без послань, без однієї мови); кожен день присутній для N = 1…366; інваріанти (`total` = сума днів, `messages` = `lv + en + ru`, `scans ≤ visits`); один день, майбутнє, `9999-12-31`; межі 366/367, високосний рік, `from > to`, `0001…9999` (400 швидко й без SQL); 19 поганих значень × `from`/`to` + відсутні/порожні/масиви + ін'єкція (`400`, без `fields`, без вводу у повідомленні, 0 SQL; рік `0000` — `400`, а не `500`); зайві параметри (байт у байт); методи; переходи часу (2026-03-29, 2026-10-25 по одному разу, 245 днів, **той самий результат при зміненому поясі за замовчуванням**); невідома метрика, нульовий рядок, `count = 4294967295` двічі; рівно 1 SQL; швидкодія (1830 рядків, медіана < 200 мс); наскрізні сценарії.

### `tests/hosting-check.php` — перевірка розгортання (BE-009, BE-014)

Той самий скрипт для Apache-контейнера (`--local`) і для справжнього хостингу: 38 перевірок — статика (`/`, `/admin/`, файл із `/assets/`, лістинг вимкнено), `/api/*` (`health`, `message`, JSON-`404`, `400`, довгий `exclude` 100 і 200 ID), `login` → `me` з Bearer-токеном і термін токена ≈ 7 діб, 14 службових шляхів (`.env`, `.git`, міграції, `src/`, `bin/` …) → `403/404` без вмісту, редиректи `http→https` та `www→без www` зі збереженням `?qr` (точне порівняння `Location`). У `--local` запити йдуть із `X-Forwarded-Proto: https` (інакше Apache без TLS перенаправляє все), а перевірки, що потребують справжнього HTTPS, пропускаються (`skip`); логін за замовчуванням — тестовий із `deploy/apache-test/test.env`.

Мутаційна перевірка `.htaccess` (на зібраному пакеті): без правила `Authorization` — червоніють `me` і `stats` (Bearer не доходить до PHP); без маршрутизації `/api` — 11 провалів; редирект із втратою query — червоніють обидві перевірки `?qr`. Інфраструктура: `docker-compose.hosting.yml` (сервіс `apache` на `php:8.4-apache`, порт 8080, тестова БД) і `deploy/apache-test/`.

### Одноразовий крок для наявного Docker-volume

Init-скрипти MySQL виконуються лише при створенні volume, тому якщо volume створено до BE-002, `orakuls_test` у ньому немає і `tests/api.php` скаже про це. Один раз:

```
docker compose down -v        # ВИДАЛЯЄ дані локальної БД — переконайся, що там немає потрібного
docker compose up -d --wait
docker compose exec php php bin/migrate.php     # міграції до робочої БД (вона після down -v порожня)
```
