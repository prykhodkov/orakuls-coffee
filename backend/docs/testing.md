# Тестування

PHPUnit не використовуємо (немає Composer), тож перевірки — два невеликих скрипти без залежностей. Обидва повертають код виходу `0` при успіху й `1` при провалі, тому підходять для CI.

## Два рівні

| Скрипт | Що перевіряє | Потрібна БД | Команда |
|--------|--------------|-------------|---------|
| `tests/run.php` | Логіку каркаса напряму, без HTTP: роутер, `Request`, `Json`, формат помилок, `Config` | ні | `docker compose run --rm --no-deps php php tests/run.php` |
| `tests/smoke.php` | Запущений API по HTTP: статуси, заголовки, тіла відповідей | так | `docker compose exec php php tests/smoke.php [base-url]` |

### `tests/run.php` — юніт-перевірки

Невелика власна обв'язка:

```php
test('опис того, що перевіряємо', function () {
    $kernel = kernelWith(fn (Router $r) => $r->get('/api/x', fn () => Response::json(['ok' => true])));

    $response = $kernel->handle(new Request('GET', '/api/x'));

    assertSame(200, $response->status);
});
```

- `test($name, $fn)` реєструє перевірку; будь-який виняток усередині — провал.
- `assertSame($expected, $actual)` — сувора рівність (`===`), `assertTrue($cond)`.
- `kernelWith(fn (Router $r) => …)` створює `Kernel` з довільними маршрутами, не торкаючись `routes.php`.
- `decode($response)` розбирає тіло відповіді в масив.
- `error_log()` перенаправлено в тимчасовий файл, тож можна перевірити, що деталі помилки потрапили в лог, а не у відповідь.

Зараз покрито: параметри шляху; `404` для невідомого шляху й методу; `400` на некоректне тіло й параметр-масив; кодування JSON (юнікод, числа, `{}` замість `[]`); формат кожної помилки й відповідність кодів `API.md`; `500` без витоку деталей; перетворення PHP warning на `500`; розбір `.env`.

### `tests/smoke.php` — перевірка по HTTP

Бере базову адресу з аргументу, змінної `BASE_URL` або `http://localhost:8000`. Перевіряє `/api/health`, формат `404`, метод, якого немає для шляху, кінцевий слеш.

Те саме можна запустити проти хостингу (з контейнера, бо PHP на машині немає):

```
docker compose run --rm --no-deps php php tests/smoke.php https://<домен>
```

Поточні перевірки лише читають, тож безпечні для прода. Smoke-перевірки, що створюють або видаляють дані (CRUD фраз, імпорт), у прод запускати не можна без окремого рішення.

## Як додати перевірку

1. Нова логіка без БД → `test(…)` у `tests/run.php`.
2. Поведінка ендпоінта «знизу вгору» (статус, заголовки, типи полів) → блок у `tests/smoke.php`.
3. Перевіряти і щасливий шлях, і помилки (`400`, `401`, `404`, `422`) разом із **типами полів** (`42`, а не `"42"`; `true`, а не `1`).

## Що буде додано

Перевірки ендпоінтів з БД (випадковий вибір без повторів, фільтри та пагінація, валідація, імпорт) з'являться разом із відповідними задачами BE-003 … BE-008 — їм потрібна тестова БД із відомими даними (сід з BE-002). Наскрізний прогін фронта проти бекенда — BE-010.
