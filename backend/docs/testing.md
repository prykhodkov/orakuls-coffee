# Тестування

PHPUnit не використовуємо (немає Composer), тож перевірки — невеликі скрипти без залежностей. Усі повертають код виходу `0` при успіху й `1` при провалі, тому підходять для CI.

## Рівні

| Скрипт | Що перевіряє | Потрібна БД | Команда |
|--------|--------------|-------------|---------|
| `tests/run.php` | Логіку напряму, без HTTP: роутер, `Request`, `Json`, формат помилок, `Config`, `SqlSplitter`, `Categories`/`Languages`/`Iso8601`, `DatabaseGuard`, `Migrator::files()`, `SchemaBuilder`, актуальність `schema.sql`, дані сіду | ні | `docker compose run --rm --no-deps php php tests/run.php` |
| `tests/api.php` | Схему, міграції, сід і (з BE-003) ендпоінти на відомих даних тестової БД | `orakuls_test` | `docker compose exec php php tests/api.php` |
| `tests/smoke.php` | Запущений API по HTTP: статуси, заголовки, тіла відповідей | так | `docker compose exec php php tests/smoke.php [base-url]` |

Спільна обв'язка (`test()`, `assertSame()`, `assertTrue()`, `assertThrows()`, `decode()`, `kernelWith()`, `runTests()`) лежить у `tests/lib.php`; її підключають `run.php` і `api.php`. Для перевірок ендпоінтів там же: `apiRequest($method, $path, $query = [], $headers = [], $body = '', $ip = 'unknown')` — виклик API в процесі через спільний `apiKernel()` (маршрути завантажуються один раз, а не на кожен із тисяч запитів; `$query` — уже розібраний масив, `lang[]=lv` задається як `['lang' => ['lv']]`) і `assertUniform()` (див. нижче). Там само `withEnv($vars, $fn)`: тимчасово задає змінні процесу (`putenv`) і в `finally` повертає попередні значення; `null` прибирає змінну (тоді `Config` знову бачить значення з `.env`), порожній рядок — це значення.

### `tests/run.php` — юніт-перевірки

Невелика власна обв'язка:

```php
test('опис того, що перевіряємо', function () {
    $kernel = kernelWith(fn (Router $r) => $r->get('/api/x', fn () => Response::json(['ok' => true])));

    $response = $kernel->handle(new Request('GET', '/api/x'));

    assertSame(200, $response->status);
});
```

- `test($name, $fn)` реєструє перевірку; будь-який виняток усередині — провал.
- `assertSame($expected, $actual)` — сувора рівність (`===`), `assertTrue($cond)`, `assertThrows($fn, $class)` — перевіряє клас винятку й повертає його.
- `kernelWith(fn (Router $r) => …)` створює `Kernel` з довільними маршрутами, не торкаючись `routes.php`.
- `decode($response)` розбирає тіло відповіді в масив.
- `error_log()` перенаправлено в тимчасовий файл, тож можна перевірити, що деталі помилки потрапили в лог, а не у відповідь.

Зараз покрито: параметри шляху; `404` для невідомого шляху й методу; `400` на некоректне тіло й параметр-масив; кодування JSON (юнікод, числа, `{}` замість `[]`); формат кожної помилки й відповідність кодів `API.md`; `500` без витоку деталей; перетворення PHP warning на `500`; розбір `.env`; розбирач SQL (рядки, коментарі, `/*! */`, `DELIMITER`, CRLF); єдині списки категорій і мов; формат дат; запобіжник за іменем БД; перевірку імен міграцій; точний вигляд згенерованого `schema.sql` і його актуальність; цілісність даних сіду; `IdList::parse()` (таблиця «вхід → результат», ліміт 200, гігантські рядки), `Request::rawQuery()` і те, що `GET /api/message` перевіряє `lang` до звернення до БД (`400` без БД).

Авторизація (BE-004, без БД): `ApiException::rateLimited` і `Retry-After` у відповіді `ErrorHandler`; `Request::fromGlobals()` бере `ip` лише з `REMOTE_ADDR` (`X-Forwarded-For` ігнорується); `Iso8601::fromTimestamp()`; **`TokenService`** — межі терміну (`exp > now` суворо), залежність ключа від хеша/секрету/логіна, зміна кожного символу кожної з трьох частин, підміна header (`none`, `HS512`, зайве поле — навіть коли підпис пораховано «правильно»), неканонічний base64url (паддінг, `+`/`/`, зайві біти), токен > 2048 символів, нерядкові/відсутні поля payload (кожен негативний випадок має позитивний контроль: коректно підписаний токен проходить); **`AuthConfig::fromEnv`** — кожна некоректна конфігурація дає `500`, у лозі є назва змінної і немає значень; **`AdminGuard`** — публічні шляхи не викликають провайдер конфігурації, помилка конфігурації на адмін-шляху дає `500`, боєвий `Kernel::create()` містить guard; **`bin/hash-password.php`** через `proc_open` (pipe-гілка: валідний пароль, межі 12 символів / 72 байти, порожній ввід, `NUL`, пароль в аргументах ігнорується).

Список фраз (BE-005, без БД): `Domain\Phrase::fromRow()`/`toArray()` (типи, порядок ключів у JSON, `'1'`/`'0'` рядками, некоректна дата → виняток), `PhraseFilter::offset()`, `PhraseRepository::escapeLike()` і `lacksTextSql()`, `PhraseController::parseFilter()` — таблиця «query → результат або `400`» для кожного параметра (порожні значення, межі `page` 999 999 999 / `perPage` 100, `"1\n"`, `050`, масиви, 200 символів кирилиці, повідомлення без значення, що прийшло).

Запис фраз (BE-006, без БД): **`Domain\PhraseValidator`** (13 перевірок, `pv*`-хелпери) — таблиця «вхід → точні `fields`» (порядок ключів значущий): валідне тіло і trimmed тексти; `category` (`required`/`invalid`: `LOVE`, `love `, `5`, `["love"]`, `""`, `true`); `text` (немає → `required`, не об'єкт → `invalid`, `{}`/`[]` → `empty`); `text.xx` (немає ключа або `null` → порожній переклад `""` без помилки, не рядок → `invalid`, невалідний UTF-8; D-30); довжина 500/501 для `a`, `š`, `я`, `😀` і пробіли навколо; `text = empty` (пробіли, `\n`, `\t`, `U+00A0`, `U+3000`, `U+FEFF`, `U+2028`; не `empty` для `U+200B` / `U+0085`; не `empty` разом із помилкою `text.xx`; усі три мови `null`/відсутні → `empty`; єдина непорожня мова за відсутніх решти → успіх); керівні символи (`\0`, `\x01`, `\x02`, `\x7F`, `\x0B`… всередині й на краю; `\n`, `\r\n`, `\t`, C1 проходять); `isActive`; кілька помилок разом; зайві ключі; `trim()` (що обрізається, що ні, `😀 `); відсутність `use App\Http` / `use App\Repository` у файлах домену; лінійність `trim()` на 500 000 пробілів усередині тексту.

### `tests/smoke.php` — перевірка по HTTP

Бере базову адресу з аргументу, змінної `BASE_URL` або `http://localhost:8000`. Перевіряє `/api/health`, формат `404`, метод, якого немає для шляху, кінцевий слеш, `GET /api/admin/stats` без токена (`401`, `no-store`) та `GET /api/message`: `400` без `lang` і з `lang=de`; `lang=lv` (з `exclude` і без) дає **або** `200` з ключами рівно `id`, `lang`, `text` і `no-store`, **або** `404 not_found` (робоча БД може бути порожньою), але не `400`/`500`; `POST` → `404`.

Те саме можна запустити проти хостингу (з контейнера, бо PHP на машині немає):

```
docker compose run --rm --no-deps php php tests/smoke.php https://<домен>
```

Поточні перевірки лише читають, тож безпечні для прода. Smoke-перевірки, що створюють або видаляють дані (CRUD фраз, імпорт), у прод запускати не можна без окремого рішення. Окремо для адмінки: smoke **не відправляє неправильних облікових даних** — вони рахуються в ліміт спроб входу, і на хостингу smoke заблокував би IP розробника на 15 хвилин. Дозволено лише запити, що відхиляються до перевірки пароля: без токена (`401`), `{}` (`422`), не-JSON (`400`). З BE-005: `GET /api/admin/phrases`, `/api/admin/phrases/1` і `/api/admin/phrases?perPage=0` без токена → `401` (guard раніше за валідацію). З BE-006: `POST /api/admin/phrases`, `PUT /api/admin/phrases/1`, `DELETE /api/admin/phrases/1` без токена → `401` — нічого не пишеться, тож безпечно для прода (23 перевірки в smoke). З BE-007: `POST /api/admin/phrases/import` без токена, з порожнім тілом → `401` (24 перевірки в smoke).

## Як додати перевірку

1. Нова логіка без БД → `test(…)` у `tests/run.php`.
2. Поведінка запущеного сервера «знизу вгору» (статус, заголовки), безпечна для прода → блок у `tests/smoke.php`.
3. Ендпоінт, що читає чи пише в БД → новий файл `tests/api/<назва>.php` (його підхоплює `tests/api.php`, сам скрипт міняти не треба) на відомих даних сіду; новий випадок — в кінець сіду.
4. Перевіряти і щасливий шлях, і помилки (`400`, `401`, `404`, `422`) разом із **типами полів** (`42`, а не `"42"`; `true`, а не `1`).

## Третій рівень: перевірки проти тестової БД

Перевірки, що потребують відомих даних (схема, міграції, випадковий вибір без повторів, фільтри та пагінація, валідація, імпорт), виконуються на окремій базі `orakuls_test` ([D-14](decisions.md)).

```
docker compose exec php php tests/api.php
```

Що робить скрипт на старті, щоразу:

1. фіксує `DB_NAME=orakuls_test` (`putenv` до `bootstrap`, тож `DB_NAME` з `.env` ігнорується);
2. `DatabaseGuard::assertTestDatabase()` — не `*_test` → повідомлення в STDERR, код `1`, нічого не змінено;
3. `resetTestDatabase()` — видаляє всі таблиці; `Migrator::up()` — накочує міграції з нуля; `reseed()` — заливає сід;
4. підключає `tests/api/*.php` і виконує перевірки; ендпоінти викликає через `Kernel` у процесі, без HTTP.

Чому в процесі, а не по HTTP: запущений на :8000 сервер працює з робочою БД з `.env`, тож HTTP-тести не мали б відомих даних. Через це ж `tests/api.php` не торкається `orakuls`.

| Файл | Що |
|------|----|
| `tests/api.php` | Підготовка БД і запуск; змінювати не треба |
| `tests/db-lib.php` | `testPdo()`, `testMigrator()`, `resetTestDatabase()`, `reseed()` (повертає карту `key → id`), `phraseCount()`, `schemaSignature()`, `keepOnlyActive()`, `bytesSent()`, `withBigTable($fn)` (600 фраз у транзакції, що відкочується, потім `reseed()`), `withFreshSeed($fn)` (`reseed()` до і після `$fn`, у `finally`; для тестів, що пишуть), `tableDump()` (усі рядки `phrases` за `id` — для перевірок «БД не змінилась»), `statementCount($fn)` (див. нижче) |
| `tests/auth-lib.php` | Спільні хелпери входу й токенів: `authLogin()`, `authToken()`, `authAs()`, `authClearAttempts()`, `forgeToken()`, `authCaptureLog()` … і константи `AUTH_*_BODY`. Підключається з `tests/api.php` після `db-lib.php`, тож тест-файли не залежать від порядку підключення один одного |
| `tests/api/database.php` | Схема, міграції, сід (BE-002); нові задачі додають власні файли `tests/api/<назва>.php` |
| `tests/api/message.php` | `GET /api/message` (BE-003) |
| `tests/api/auth.php` | Авторизація адміна (BE-004): вхід, токен, guard, ліміт спроб, конфігурація |
| `tests/api/phrases.php` | Список і перегляд фраз (BE-005): фільтри, пошук, пагінація, типи, кількість SQL-запитів, швидкодія |
| `tests/api/phrases-write.php` | Створення, оновлення, видалення фраз (BE-006): валідація, `PUT`/`DELETE`, видимість у `/api/message`, кількість SQL-запитів, чистота сіду |
| `tests/api/phrases-import.php` | Масовий імпорт фраз (BE-007): частковий успіх, `index`, м'яке правило мов, межі, ліміт 1000, відкат при збої БД, кількість запитів, швидкодія |
| `tests/api/stats.php` | Зведення для адмінки (BE-008): типи й форма, оракул сіду, порожня БД, збіг зі списком, миттєве відображення змін, один SQL-запит, 600 фраз |

Правила:

- **Тест, що пише в БД (`POST`/`PUT`/`DELETE`, прямі `INSERT`/`UPDATE`), обгортається в `withFreshSeed(function () { … })`**: `reseed()` до і після (у `finally`), тож тест не залежить від сусідніх і нічого їм не лишає (`TRUNCATE` повертає і дані, і `AUTO_INCREMENT`: новий `POST` на свіжому сіді дає `id` 31). Не викликати `withFreshSeed` усередині `withBigTable` і навпаки: `TRUNCATE` комітить транзакцію. Двічі поспіль запущений `tests/api.php` має бути зеленим.
- Тести не покладаються на порядок виконання файлів між собою; перевірка **паритету схеми** (`tests/api/database.php`) скидає БД і сама відновлює стан, тому стоїть останньою у своєму файлі.
- Сід лежить у `database/seed/phrases.php`. Порядок рядків = `id`; нові випадки додаються **лише в кінець**.
- У `Seeder::CREATED_AT` дата фіксована, тож `createdAt` у відповідях можна порівнювати зі сталим значенням.

### Що покриває `tests/api/database.php`

Міграції на порожній БД; ідемпотентність повторного `up()`; `status()`; помилка в другому операторі міграції (не ковтається, міграція не записується, повтор доробляє решту); InnoDB і колації; типи й default колонок (дати без `DEFAULT`); round-trip діакритики, кирилиці, емодзі та переносів рядка; рівно 500 символів; 501-й → помилка `1406` замість мовчазного обрізання; індекси; `UTC_TIMESTAMP()` і `Iso8601`; типи `int` для `id` і `is_active`; детермінізм сіду (`reseed()` двічі → та сама карта `key → id`) і його склад; пошук без урахування регістру й діакритики; **паритет**: імпорт `schema.sql` дає ту саму схему (за `information_schema`), що й міграції, і після нього `Migrator::up()` нічого не застосовує.

### Що покриває `tests/api/message.php`

Форма відповіді (ключі `id`, `lang`, `text` у цьому порядку, `id` — число); `Cache-Control: no-store` у `200`, `400`, `404`; некоректний `lang` (відсутній, порожній, `de`, `LV`, `lv `, масив) → `400` без `fields`; неактивні фрази не видаються; порожні й «лише пробіли» переклади не видаються для своєї мови (множина виданих ID за 3000 запитів = кандидати, виведені з сіду); `404`, коли кандидатів немає; `exclude` (8 ID — 0 влучань і рівномірність решти), «усе виключено» → `200`, «лишилась одна» → вона; терпимість `exclude` до сміття, масиву, ін'єкцій, 1500 ID і 1 МБ сміття; ліміт 200 коректних ID (межі 1, 200, 201); рівномірність без `exclude`; точність тексту (діакритика, кирилиця, `\n`, HTML, емодзі, `len500`) за сирим тілом відповіді; «один запит — один рядок»; швидкодія на 600 фразах; відсутність авторизації й зайвих полів; `POST`/`PUT`/`DELETE`/`HEAD`/`PATCH` → `404`.

**Статистичні перевірки.** Рівномірність перевіряє `assertUniform($candidates, $counts, $draws)`: кожен кандидат зустрівся, жоден сторонній ID не випав, а лічильник кожного лежить у межах ±6σ від середнього (`σ = √(n·p·(1−p))`, `p = 1/N`). Смуга свідомо широка: шанс хибного спрацювання ~10⁻⁸, тест не «блимає». **Не звужувати смугу і не зменшувати число запитів** (по 3000): від числа запитів залежить і надійність, і чутливість — на 600 запитах нижня межа ±6σ пішла б у мінус і перевірка стала б беззубою. 3000 запитів у процесі — приблизно секунда.

**Вимір «один запит — один рядок».** Детерміновано, без таймерів: у транзакції до сіду додається 570 довгих фраз (разом 600), і порівнюється приріст сесійної змінної `Bytes_sent` для одного запиту ендпоінта (зі 100 виключеними ID) та для `SELECT id, text_lv FROM phrases WHERE is_active = 1`; перше має бути щонайменше в 10 разів меншим. Накладні витрати самого `SHOW SESSION STATUS` віднімаються (дельта двох `SHOW` поспіль). `Rows_sent` у MySQL 5.7 немає — не використовувати. Транзакція відкочується, після неї `reseed()` (відкат не повертає `AUTO_INCREMENT`).

### Що покриває `tests/api/auth.php`

Авторизація — задача про безпеку, тому кожне правило має «позитивну» й «негативну» перевірку, а негативні відмови доводяться позитивним контролем (коректно підписаний `forgeToken(...)` → `200`), щоб тест не проходив через сторонню помилку.

- **Облікові дані.** `tests/api.php` до `bootstrap` задає через `putenv` `ADMIN_LOGIN=test-admin`, `ADMIN_PASSWORD_HASH` (bcrypt **cost 4**: ≈1 мс замість ≈165 мс при cost за замовчуванням), `TOKEN_SECRET` (64 символи) і порожній `TOKEN_TTL_HOURS` (= 168 год). `getenv()` має пріоритет над `.env`, тож тести не залежать від локального `backend/.env`. Константи `TEST_ADMIN_LOGIN`, `TEST_ADMIN_PASSWORD`, `TEST_TOKEN_SECRET`.
- **Хелпери** (глобальні, префікс `auth`): `authLogin()`, `authToken()`, `authAs()`, `authClearAttempts()`, `authFail($ip, $n)`, `authCaptureLog()` (перенаправляє `error_log` у тимчасовий файл і повертає його вміст), `forgeToken($config, $payload, $headerJson)` — «ручний» випуск токена тим самим ключем для негативних перевірок; `withEnv()` — у `tests/lib.php` (зміна змінних процесу з обов'язковим відновленням у `finally`).
- **IP у тестах** — лише з `203.0.113.0/24` (TEST-NET-3, документаційний діапазон); кожен тест, що створює невдалі спроби, починає з `authClearAttempts()` і користується власними адресами, тож тести не заважають один одному (ліміт — 5 на IP).
