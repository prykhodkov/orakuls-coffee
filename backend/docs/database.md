# База даних

MySQL **5.7** (версія хостингу GoDaddy). Локально — `mysql:5.7` в Docker. Схема та міграції — задача BE-002 ([опис](tasks/BE-002-database-schema/task.md)); цей документ описує підключення, схему, міграції, сід і правила запитів.

## Підключення

`Support\Db::pdo()` — ліниве з'єднання (відкривається при першому зверненні, один раз на запит). Параметри — з [конфігурації](configuration.md) (`DB_*`).

| Налаштування PDO | Навіщо |
|------------------|--------|
| `ERRMODE_EXCEPTION` | Помилки БД — винятки, які ловить `Kernel` (→ `500`) |
| `EMULATE_PREPARES = false` | Справжні prepared statements, нативні типи |
| `STRINGIFY_FETCHES = false` | Числа з БД лишаються числами в JSON |
| `FETCH_ASSOC` | Результат — асоціативні масиви |
| `charset=utf8mb4` у DSN | Повна підтримка Unicode (емодзі в категоріях, латиські діакритики) |

## Налаштування сесії

На кожному з'єднанні виконується `SET`, щоб поведінка не залежала від конфігурації конкретного хостингу:

| Параметр | Значення | Чому |
|----------|----------|------|
| `NAMES` | `utf8mb4 COLLATE utf8mb4_unicode_ci` | Єдине кодування й порівняння (`utf8mb4_0900_*` є лише в 8.0) |
| `time_zone` | `+00:00` | Усі дати — в UTC, як вимагає контракт |
| `sql_mode` | `ONLY_FULL_GROUP_BY, STRICT_ALL_TABLES, NO_ZERO_IN_DATE, NO_ZERO_DATE, ERROR_FOR_DIVISION_BY_ZERO, NO_ENGINE_SUBSTITUTION` | Суворий режим: зайве не обрізається мовчки, помилки не ховаються |

## Правила запитів

- **Лише prepared statements** з параметрами. Жодної конкатенації значень у SQL — захист від ін'єкцій.
- Імена колонок і напрямок сортування, які залежать від вводу користувача, беруться з білого списку, а не підставляються з запиту.
- У `LIKE` ввід користувача, що має шукатись як звичайний текст, екранується, але **не** через `ESCAPE '\'`: на MySQL 5.7 `LIKE '%\\%' ESCAPE '\'` (пошук одного `\`) нічого не знаходить, хоч такі рядки є; те саме з будь-яким символом, що водночас є екранувальним (`!`, `|`). Надійний варіант (перевірено): `LIKE ? ESCAPE x'01'` — службовий керівний символ, якого не набрати в полі пошуку; його вилучають із вводу, а `%` і `_` екранують ним. `LOCATE()` замість `LIKE` не годиться: він нечутливий до регістру, але не до діакритики, тобто суперечить D-13. Додатково: ввід, що **починається з `%`**, на цій колації дає хибні збіги навіть з `ESCAPE x'01'`, тому для нього `%` замінюється службовим `0x02` і в шаблоні, і в колонці (`REPLACE`). Докладно, з експериментом — [D-24](decisions.md); реалізація — `PhraseRepository::search()`, розділ «Список фраз і пошук» нижче.
- Довжину рядків рахуємо в **символах** (`mb_strlen`), а не в байтах: ліміт 500 символів — це не 500 байт.
- Не використовуємо можливості MySQL 8.0: CTE (`WITH`), віконні функції, `utf8mb4_0900_*`, `ADD COLUMN … INSTANT`, `JSON_TABLE`.
- Випадковий вибір — `ORDER BY RAND() LIMIT 1`: на ~600 фразах це швидко. Шаблон з виключеннями — у розділі «Порожній переклад і випадкова фраза».
- SQL до `phrases` живе в `Repository\PhraseRepository` ([D-17](decisions.md)), не в контролерах.
- Результати агрегатів (`COUNT`, `SUM`) приводимо до `(int)` у коді, бо MySQL може віддати `SUM` як `DECIMAL`-рядок.

## Дати

У БД — `DATETIME` в UTC. У JSON — ISO 8601 з `Z`: `2026-10-26T18:30:00Z`. Перетворення виконується в одному місці — `Support\Iso8601::fromDb()` (`'2026-10-26 18:30:00'` → `'2026-10-26T18:30:00Z'`; некоректне значення, зокрема неіснуюча дата, — `InvalidArgumentException`), щоб формат не розходився між ендпоінтами. Записуємо дати завжди явно через `UTC_TIMESTAMP()`: значень за замовчуванням у колонок `created_at`/`updated_at` немає, щоб часовий пояс сесії (наприклад, у phpMyAdmin) не міг тихо підставити не UTC.

## Схема

Кодування всіх таблиць — `utf8mb4` / `utf8mb4_unicode_ci`, рушій InnoDB.

| Таблиця | Задача | Що в ній |
|---------|--------|----------|
| `phrases` | BE-002 ✅ | Фраза з трьома мовами |
| `migrations` | BE-002 ✅ | Службова: які міграції вже застосовано |
| `login_attempts` | BE-004 ✅ | Невдалі спроби входу для ліміту (`ip`, `attempted_at`); міграція `002`, прострочені записи видаляються під час перевірки |

### `phrases`

| Поле | Тип | Примітка |
|------|-----|----------|
| `id` | `INT UNSIGNED AUTO_INCREMENT` PK | |
| `category` | `VARCHAR(16) NOT NULL` | допустимі коди перевіряє код, не БД (див. нижче) |
| `text_lv`, `text_en`, `text_ru` | `VARCHAR(500) NOT NULL DEFAULT ''` | 500 **символів**; порожній рядок = переклад відсутній |
| `is_active` | `TINYINT(1) NOT NULL DEFAULT 1` | |
| `created_at`, `updated_at` | `DATETIME NOT NULL`, **без** `DEFAULT` | UTC; код передає `UTC_TIMESTAMP()` |

Індекси: `idx_phrases_category`, `idx_phrases_is_active`. `EXPLAIN` запиту `GET /api/message` (BE-003): `type: ALL`, `Using where; Using temporary; Using filesort` — `ORDER BY RAND()` однаково проходить усіх кандидатів, індекс тут не допомагає; на ~600 фразах це ≈1 мс. Запити списку (`GET /api/admin/phrases`, BE-005): `EXPLAIN` на сіді — фільтр за `category` іде по `idx_phrases_category`, сортування `id DESC` — по первинному ключу, а `LIKE '%…%'` і `TRIM(…)` індекс використати не можуть і проходять усі рядки (`type: index` по `PRIMARY`); на 600 фразах це ≈1 мс (тест швидкодії вимагає медіану < 300 мс). Додаткові індекси не потрібні.

**Типи з БД.** Нативні prepared statements повертають `id` і `is_active` як `int` (не рядок і не `bool`), `DATETIME` — як рядок `'2026-10-26 18:30:00'`. У JSON `isActive` треба явно приводити `(bool)`, дату — через `Iso8601::fromDb()`; це робить `Domain\Phrase::fromRow()` (BE-005, [D-26](decisions.md)). Регресію типів фіксує `tests/api/database.php`.

### `login_attempts` (BE-004)

| Поле | Тип | Примітка |
|------|-----|----------|
| `id` | `BIGINT UNSIGNED AUTO_INCREMENT` PK | |
| `ip` | `VARCHAR(45) NOT NULL` | `REMOTE_ADDR` (найдовший IPv6 — 45 символів) або `unknown` |
| `attempted_at` | `DATETIME NOT NULL`, **без** `DEFAULT` | UTC; код передає `UTC_TIMESTAMP()` |

Індекс `idx_login_attempts_ip_time (ip, attempted_at)`. Рядок = одна **невдала** спроба входу з перевіркою пароля; успіхи, заблоковані запити та відмови `400`/`422` не записуються (D-22, D-23). Запити — у `Auth\LoginRateLimiter`:

```sql
-- очищення (перед кожною перевіркою ліміту)
DELETE FROM login_attempts WHERE attempted_at < UTC_TIMESTAMP() - INTERVAL ? SECOND          -- 900

-- перевірка ліміту й Retry-After: останні 5 спроб у вікні, вік у секундах
SELECT TIMESTAMPDIFF(SECOND, attempted_at, UTC_TIMESTAMP()) AS age FROM login_attempts
 WHERE ip = ? AND attempted_at > UTC_TIMESTAMP() - INTERVAL ? SECOND
 ORDER BY attempted_at DESC LIMIT 5

-- запис невдачі
INSERT INTO login_attempts (ip, attempted_at) VALUES (?, UTC_TIMESTAMP())
```

Якщо у вибірці 5 рядків — IP заблоковано, а `Retry-After = 900 − age` п'ятого (найстарішого з п'яти): коли він вийде з вікна, у вікні лишиться менше 5 спроб. Параметр у `INTERVAL ? SECOND` працює з нативними prepared statements на MySQL 5.7. Вибірка «останніх п'яти» (а не `COUNT`) не дає зайвим записам одночасних запитів зсунути розрахунок. Таблиця не росте безмежно: старше за 15 хв видаляється при кожному вході.

### Міграції

Нумеровані SQL-файли в `database/migrations/` і runner `Database\Migrator` (CLI — `bin/migrate.php`). Таблиця `migrations` (`name`, `applied_at`) веде облік; runner створює її сам (`CREATE TABLE IF NOT EXISTS`), а не міграційним файлом. Повторний запуск нічого не застосовує. Паралельні запуски розводить advisory-lock `GET_LOCK('orakuls_migrate')`.

Правила для **всіх** міграцій:

- ім'я файлу `NNN_snake_case.sql` (три цифри — порядок застосування; опечатка в імені чи повторений номер — помилка, а не мовчазний пропуск);
- DDL у MySQL **неатомарний** (кожен `CREATE`/`ALTER` комітить неявно), тому міграція з кількома операторами має бути ідемпотентною посередині (`IF NOT EXISTS`), щоб повторний запуск після збою доробив решту; невдала міграція в `migrations` не записується;
- без `DELIMITER`, процедур, тригерів і `SELECT`-ів;
- застосовану міграцію **не редагувати** — додавати нову;
- задача, що змінює схему, додає міграцію і перегенеровує `schema.sql` (`php bin/build-schema.php`).

**Оператори виконуються по одному** ([D-15](decisions.md)): `PDO::exec()` з кількома операторами не кидає виняток, якщо помилка не в першому, а наступні запити на з'єднанні падають з `2014`. Тому файл розбиває `Database\SqlSplitter` (розуміє рядки, ідентифікатори, коментарі, `/*! … */`; `DELIMITER` не підтримує). Налаштування PDO заради цього не міняємо.

### `schema.sql`

`database/schema.sql` — повна схема для ручного імпорту через phpMyAdmin (на shared-хостингу CLI може не бути). Файл **генерується** з міграцій (`php bin/build-schema.php`), вручну не редагується ([D-16](decisions.md)). Він містить DDL `migrations` і `INSERT IGNORE` застосованих імен, тож після імпорту runner не застосовує ці міграції вдруге. Даних (сіду) там немає. Дві перевірки охороняють файл: `schema.sql актуальний` (`tests/run.php`, також `php bin/build-schema.php --check`) і `паритет` (`tests/api/database.php`: імпорт `schema.sql` дає ту саму схему за `information_schema`, що й міграції). `login_attempts` (міграція `002`) у ньому є.

### Порожній переклад і випадкова фраза

**Порожній переклад** = `TRIM(колонка) = ''` у SQL. Умову «переклад є» дає `PhraseRepository::hasTextSql($lang)` (`` TRIM(`text_lv`) <> '' ``), а протилежну «перекладу немає» — `PhraseRepository::lacksTextSql($lang)` (`` TRIM(`text_lv`) = '' ``) — поряд, щоб визначення порожнього було єдиним для `GET /api/message` (BE-003), фільтра `missing` (BE-005) і статистики (BE-008); власних версій умови не писати. `TRIM` у MySQL прибирає **лише пробіли** (рядок із табуляцій чи переносів не вважається порожнім), а `trim()` у PHP — усі пробільні символи. BE-006 при записі обрізає по-юнікодному, як JS `trim()` (`PhraseValidator::trim()`, [D-27](decisions.md)): прибирає й табуляції та переноси, і нерозривний пробіл. Розбіжність із SQL-`TRIM` можлива лише для застарілих або внесених вручну даних.

**Випадкова фраза** (`PhraseRepository::findRandom()`, [D-19](decisions.md)):

```sql
-- без exclude
SELECT `id`, `text_lv` AS `text` FROM `phrases`
 WHERE `is_active` = 1 AND TRIM(`text_lv`) <> ''
 ORDER BY RAND() LIMIT 1

-- з exclude (по одному ? на кожен ID, PDO::PARAM_INT)
SELECT `id`, `text_lv` AS `text` FROM `phrases`
 WHERE `is_active` = 1 AND TRIM(`text_lv`) <> ''
 ORDER BY (`id` IN (?, ?, …)) ASC, RAND() LIMIT 1
```

- `(id IN (…))` дає `0` для непереглянутих і `1` для виключених: спершу перемішуються непереглянуті, виключені йдуть лише коли інших немає — запасний варіант «ігнорувати `exclude`» не потребує другого запиту.
- **При порожньому списку `IN` не додається взагалі**: `IN ()` у MySQL — синтаксична помилка (1064).
- Ім'я колонки — лише з `Languages::column()`, ID — лише параметрами.
- Вартість: на 600 фразах із 100 виключеними ≈1 мс (тест `tests/api/message.php` вимагає медіану < 200 мс і перевіряє, що сервер БД віддає один рядок, а не таблицю).

### Список фраз і пошук (BE-005)

`PhraseRepository::search(PhraseFilter)` виконує **рівно два** запити (D-26). `WHERE` будується один раз (приватний `buildWhere()` повертає SQL і типізований список параметрів) і використовується в обох, тож `total` завжди відповідає фільтрам:

```sql
-- сторінка: параметри WHERE, потім perPage і offset (усі позиційні, нумерація з 1 наскрізна)
SELECT `id`, `category`, `text_lv`, `text_en`, `text_ru`, `is_active`, `created_at`, `updated_at`
  FROM `phrases`
 WHERE `category` = ?                                    -- category (PARAM_STR)
   AND `is_active` = ?                                   -- isActive (PARAM_INT, 1/0)
   AND TRIM(`text_en`) = ''                              -- missing (lacksTextSql, без параметрів)
   AND (`text_lv` LIKE ? ESCAPE x'01'                    -- search: той самий параметр тричі
        OR `text_en` LIKE ? ESCAPE x'01'
        OR `text_ru` LIKE ? ESCAPE x'01')
 ORDER BY `id` DESC LIMIT ? OFFSET ?

-- кількість: тільки параметри WHERE
SELECT COUNT(*) FROM `phrases` WHERE …                   -- ті самі умови
```

- Умови додаються через `AND` лише для заданих полів; без жодного фільтра `WHERE` немає. `LIMIT ? OFFSET ?` біндуються `PDO::PARAM_INT` (працює при нативних prepared statements).
- `search`: значення `'%' . escapeLike($search) . '%'`. `escapeLike()` вилучає `0x01` з вводу і екранує `%` та `_` ним; `\` і решта символів звичайні. У коді `ESCAPE x'01'` записано в PHP-рядку як `x'01'` (керівного символа в тексті коду немає). Імена колонок — лише з `Languages::column()`.
- **Ввід, що починається з `%`** (наприклад `%_`): на `utf8mb4_unicode_ci` MySQL 5.7 екранований `%` одразу після початкового `%` шаблону трактує як шаблонний, тож `search=%_` знаходив би все, де є `%` і далі `_`. Для таких вводів `%` замінюється службовим `0x02` у шаблоні й у колонці (`` REPLACE(`text_lv`, '%', _utf8mb4 x'02') LIKE ? ESCAPE x'01' ``). Перевірено перебором усіх вводів ≤ 4 символів над алфавітом `a b % _ \` пробіл: розбіжностей з бінарним порівнянням немає тільки в такому варіанті (D-24).
- `search` порожній після `trim` у запит не потрапляє: `LIKE '%%'` знайшов би усе.
- `COUNT(*)` повертається як `(int)`; `items` — завжди список (`array_values`).
- Сторінка за межами діапазону — звичайний запит, що повертає `[]` без помилки (`page=999999999` перевіряє тест, `OFFSET` порядку 5·10¹⁰ вміщується в 64-бітний `int`); `SQL_CALC_FOUND_ROWS` не використовується.
- `find($id)`: `SELECT <ті самі колонки> FROM phrases WHERE id = ?` (`PARAM_INT`) → `Phrase` або `null`.

### Запис фраз (BE-006)

`PhraseRepository::create()`, `update()`, `delete()` ([D-29](decisions.md)). Усі значення — лише параметри (`bindValue`), імена колонок текстів — з `Languages::column()`. Дані до репозиторію приходять уже нормалізованими (`PhraseInput` від `PhraseValidator`, [D-27](decisions.md)).

```sql
-- create: 2 запити (INSERT + find). created_at і updated_at — два UTC_TIMESTAMP() в одному операторі, тож збігаються
INSERT INTO `phrases` (`category`, `text_lv`, `text_en`, `text_ru`, `is_active`, `created_at`, `updated_at`)
VALUES (?, ?, ?, ?, ?, UTC_TIMESTAMP(), UTC_TIMESTAMP())      -- is_active: PARAM_INT 1/0; id = lastInsertId()

-- update: 2 запити (UPDATE + find). created_at не чіпається
UPDATE `phrases`
   SET `category` = ?, `text_lv` = ?, `text_en` = ?, `text_ru` = ?, `is_active` = ?, `updated_at` = UTC_TIMESTAMP()
 WHERE `id` = ?

-- delete: 1 запит
DELETE FROM `phrases` WHERE `id` = ?
```

- Відповідь `create`/`update` — `find($id)` після запису, тож тип і формат полів ті самі, що й у читанні (D-26).
- **`update()` не спирається на `rowCount()`**: `UPDATE`, що не змінив жодного значення (ті самі дані в ту ж секунду, `updated_at` теж збігся), повертає `0` — так само, як і для неіснуючого `id`. Тому після `UPDATE` робиться `find($id)`: `null` означає, що фрази немає. `delete()` повертає `rowCount() > 0` — для `DELETE` це реальна кількість видалених.
- Текст пишеться як є: без екранування HTML, без нормалізації `
`; довжина ≤ 500 символів гарантується валідатором (інакше БД відхилила б запис помилкою `1406`, див. «Схема»).
- Транзакцій і `SELECT … FOR UPDATE` немає: адмін один.
- `id` після `DELETE` InnoDB (5.7) після перезапуску сервера може віддати знову (`AUTO_INCREMENT` обчислюється як `MAX(id) + 1`); для цього проєкту наслідок мізерний.

### Категорії не захищені на рівні БД

`category` — звичайний `VARCHAR(16)`, а не `ENUM` (D-11): нова категорія не потребує міграції. Допустимі коди (`love`, `money`, `luck`, `work`, `travel`, `mood`) перевіряє код — з одного списку, який використовують валідація й фільтри. На `CHECK` у БД покладатися не можна: **MySQL 5.7 приймає `CHECK`, але ігнорує його**. Тому будь-який шлях запису у `phrases` (створення, оновлення, імпорт) мусить перевіряти категорію в коді.

### Пошук: регістр і діакритика

Колація `utf8mb4_unicode_ci` робить `LIKE` нечутливим до регістру **і до діакритики** (D-13). Перевірено на MySQL 5.7:

| Запит | Знаходить | Коментар |
|-------|-----------|----------|
| `sodien` | `Šodien` | латиські літери з діакритикою = базові (`š`=`s`, `ā`=`a`, `ū`=`u`, `ķ`=`k` перевірено) |
| `bus` | `būs` | |
| `ТЕСТ` | `тест` | регістр кирилиці не важливий |
| `елка` | `ёлка` | `ё` = `е` |
| `иога` | — | `й` ≠ `и`, не знаходить `йога` |
| 😀 | будь-який емодзі | всі 4-байтові символи в цій колації рівні між собою |

Для адмінського пошуку це зручно (не треба вводити діакритику), але має бути відомо: пошук за емодзі не розрізняє емодзі. Строгий варіант (`utf8mb4_bin` + `LOWER()`) гірше працює з кирилицею та латиською, тому не обраний.

## Тестова БД

Перевірки ендпоінтів з БД виконуються на окремій базі **`orakuls_test`** (D-14), не на робочій локальній `orakuls`.

- Базу створює `docker-compose` разом з основною: init-скрипт `docker/mysql-init/01-create-test-database.sql` (імена зашиті — `.sql` не читає змінні оточення; змінюєш `DB_USER`/`DB_NAME` в `.env` — онови файл). Користувач `orakuls` має доступ до обох баз. Init-скрипти MySQL виконуються лише при створенні volume, тож для вже існуючого потрібен одноразовий `docker compose down -v`.
- `tests/api.php` перед кожним прогоном скидає таблиці `orakuls_test`, застосовує міграції й заливає сід (`database/seed/phrases.php`), після чого викликає `Kernel` у процесі, без HTTP-сервера. Дані завжди однакові.
- **Запобіжник:** `Database\DatabaseGuard` дивиться на БД, до якої фактично підключено PDO (`SELECT DATABASE()`), а не на конфіг; `Seeder`, `bin/seed.php` і `tests/api.php` відмовляються працювати, якщо назва не закінчується на `_test`. Так не можна випадково стерти локальні дані чи прод. Код «стерти всі таблиці» живе лише в `tests/`.
- Сід — лише для тестової БД. Робоча `orakuls` після міграцій порожня, реальні фрази туди завантажує адмін через імпорт.
- Деталі запуску — [testing.md](testing.md).

### Склад сіду

30 фраз, `id` = порядок у файлі (1, 2, 3 …), `created_at` = `updated_at` = `2026-10-26 18:30:00` (`Seeder::CREATED_AT`). **Порядок не міняти, нові рядки додавати лише в кінець** — тести інших задач спираються на `id`.

| Ключі | Для чого |
|-------|----------|
| `love_1` … `mood_3` (18) | по 3 активні фрази з усіма мовами на кожну з 6 категорій |
| `hidden` | прихована фраза (love) |
| `only_lv`, `only_en`, `no_ru`, `blank_en` | порожні переклади різними мовами; `blank_en` — лише пробіли |
| `diacritics`, `cyrillic_case` | пошук `sodien`, `bus`, `тест` |
| `emoji`, `multiline` | емодзі та справжній перенос рядка |
| `len500` | рівно 500 символів (`š` і `😀`) |
| `html`, `like_chars` | `<script>…` зберігається як є; `%`, `_` і зворотний слеш для екранування `LIKE` |

## Розбіжність версій
