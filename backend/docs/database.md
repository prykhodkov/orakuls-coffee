# База даних

MySQL **5.7** (версія хостингу GoDaddy). Локально — `mysql:5.7` в Docker. Схема та міграції — задача BE-002 ([опис](tasks/BE-002-database-schema/task.md)); цей документ описує підключення, схему, міграції, сід і правила запитів.

## Підключення

`Support\Db::pdo()` — ліниве з'єднання (відкривається при першому зверненні, один раз на запит). Параметри — з [конфігурації](configuration.md) (`DB_*`).

| Налаштування PDO | Навіщо |
|------------------|--------|
| `ERRMODE_EXCEPTION` | Помилки БД — винятки, які ловить `Kernel` (→ `500`) |
| `EMULATE_PREPARES = false` | Справжні prepared statements, нативні типи |
| `STRINGIFY_FETCHES = false` | Числа з БД лишаються числами в JSON |
| `FETCH_ASSOC` | Результат — асоціативні масиви |
| `charset=utf8mb4` у DSN | Повна підтримка Unicode (емодзі в категоріях, латиські діакритики) |

## Налаштування сесії

На кожному з'єднанні виконується `SET`, щоб поведінка не залежала від конфігурації конкретного хостингу:

| Параметр | Значення | Чому |
|----------|----------|------|
| `NAMES` | `utf8mb4 COLLATE utf8mb4_unicode_ci` | Єдине кодування й порівняння (`utf8mb4_0900_*` є лише в 8.0) |
| `time_zone` | `+00:00` | Усі дати — в UTC, як вимагає контракт |
| `sql_mode` | `ONLY_FULL_GROUP_BY, STRICT_ALL_TABLES, NO_ZERO_IN_DATE, NO_ZERO_DATE, ERROR_FOR_DIVISION_BY_ZERO, NO_ENGINE_SUBSTITUTION` | Суворий режим: зайве не обрізається мовчки, помилки не ховаються |

## Правила запитів

- **Лише prepared statements** з параметрами. Жодної конкатенації значень у SQL — захист від ін'єкцій.
- Імена колонок і напрямок сортування, які залежать від вводу користувача, беруться з білого списку, а не підставляються з запиту.
- У `LIKE` спецсимволи `%`, `_`, `\` з вводу екрануються.
- Довжину рядків рахуємо в **символах** (`mb_strlen`), а не в байтах: ліміт 500 символів — це не 500 байт.
- Не використовуємо можливості MySQL 8.0: CTE (`WITH`), віконні функції, `utf8mb4_0900_*`, `ADD COLUMN … INSTANT`, `JSON_TABLE`.
- Випадковий вибір — `ORDER BY RAND() LIMIT 1`: на ~600 фразах це швидко.
- Результати агрегатів (`COUNT`, `SUM`) приводимо до `(int)` у коді, бо MySQL може віддати `SUM` як `DECIMAL`-рядок.

## Дати

У БД — `DATETIME` в UTC. У JSON — ISO 8601 з `Z`: `2026-10-26T18:30:00Z`. Перетворення виконується в одному місці — `Support\Iso8601::fromDb()` (`'2026-10-26 18:30:00'` → `'2026-10-26T18:30:00Z'`; некоректне значення, зокрема неіснуюча дата, — `InvalidArgumentException`), щоб формат не розходився між ендпоінтами. Записуємо дати завжди явно через `UTC_TIMESTAMP()`: значень за замовчуванням у колонок `created_at`/`updated_at` немає, щоб часовий пояс сесії (наприклад, у phpMyAdmin) не міг тихо підставити не UTC.

## Схема

Кодування всіх таблиць — `utf8mb4` / `utf8mb4_unicode_ci`, рушій InnoDB.

| Таблиця | Задача | Що в ній |
|---------|--------|----------|
| `phrases` | BE-002 ✅ | Фраза з трьома мовами |
| `migrations` | BE-002 ✅ | Службова: які міграції вже застосовано |
| `login_attempts` | BE-004 ⏳ | Спроби входу для ліміту (`ip`, `attempted_at`); створюється власною міграцією BE-004, старі записи видаляються |

### `phrases`

| Поле | Тип | Примітка |
|------|-----|----------|
| `id` | `INT UNSIGNED AUTO_INCREMENT` PK | |
| `category` | `VARCHAR(16) NOT NULL` | допустимі коди перевіряє код, не БД (див. нижче) |
| `text_lv`, `text_en`, `text_ru` | `VARCHAR(500) NOT NULL DEFAULT ''` | 500 **символів**; порожній рядок = переклад відсутній |
| `is_active` | `TINYINT(1) NOT NULL DEFAULT 1` | |
| `created_at`, `updated_at` | `DATETIME NOT NULL`, **без** `DEFAULT` | UTC; код передає `UTC_TIMESTAMP()` |

Індекси: `idx_phrases_category`, `idx_phrases_is_active`. Аналіз `EXPLAIN` конкретних запитів виконують BE-003 і BE-005.

**Типи з БД.** Нативні prepared statements повертають `id` і `is_active` як `int` (не рядок і не `bool`), `DATETIME` — як рядок `'2026-10-26 18:30:00'`. У JSON `isActive` треба явно приводити `(bool)`, дату — через `Iso8601::fromDb()`; це робить серіалізатор фрази (BE-005). Регресію типів фіксує `tests/api/database.php`.

### Міграції

Нумеровані SQL-файли в `database/migrations/` і runner `Database\Migrator` (CLI — `bin/migrate.php`). Таблиця `migrations` (`name`, `applied_at`) веде облік; runner створює її сам (`CREATE TABLE IF NOT EXISTS`), а не міграційним файлом. Повторний запуск нічого не застосовує. Паралельні запуски розводить advisory-lock `GET_LOCK('orakuls_migrate')`.

Правила для **всіх** міграцій:

- ім'я файлу `NNN_snake_case.sql` (три цифри — порядок застосування; опечатка в імені чи повторений номер — помилка, а не мовчазний пропуск);
- DDL у MySQL **неатомарний** (кожен `CREATE`/`ALTER` комітить неявно), тому міграція з кількома операторами має бути ідемпотентною посередині (`IF NOT EXISTS`), щоб повторний запуск після збою доробив решту; невдала міграція в `migrations` не записується;
- без `DELIMITER`, процедур, тригерів і `SELECT`-ів;
- застосовану міграцію **не редагувати** — додавати нову;
- задача, що змінює схему, додає міграцію і перегенеровує `schema.sql` (`php bin/build-schema.php`).

**Оператори виконуються по одному** ([D-15](decisions.md)): `PDO::exec()` з кількома операторами не кидає виняток, якщо помилка не в першому, а наступні запити на з'єднанні падають з `2014`. Тому файл розбиває `Database\SqlSplitter` (розуміє рядки, ідентифікатори, коментарі, `/*! … */`; `DELIMITER` не підтримує). Налаштування PDO заради цього не міняємо.

### `schema.sql`

`database/schema.sql` — повна схема для ручного імпорту через phpMyAdmin (на shared-хостингу CLI може не бути). Файл **генерується** з міграцій (`php bin/build-schema.php`), вручну не редагується ([D-16](decisions.md)). Він містить DDL `migrations` і `INSERT IGNORE` застосованих імен, тож після імпорту runner не застосовує ці міграції вдруге. Даних (сіду) там немає. Дві перевірки охороняють файл: `schema.sql актуальний` (`tests/run.php`, також `php bin/build-schema.php --check`) і `паритет` (`tests/api/database.php`: імпорт `schema.sql` дає ту саму схему за `information_schema`, що й міграції). `login_attempts` з'явиться в `schema.sql` разом з BE-004.

### Єдині списки в коді

| Клас | Що |
|------|----|
| `Domain\Categories` | `CODES` — єдиний список категорій (`love`, `money`, `luck`, `work`, `travel`, `mood`), `isValid()` — сувора перевірка (`LOVE`, `love ` не проходять). Його використовують валідація (BE-006, BE-007) і фільтри (BE-005) |
| `Domain\Languages` | `CODES` (`lv`, `en`, `ru`) і `column($lang)` → `text_lv` / `text_en` / `text_ru`. Єдине місце, де код мови стає частиною SQL; невідомий код — `InvalidArgumentException`, ввід у запит не потрапляє |
| `Support\Iso8601` | Перетворення дат БД на ISO 8601 (див. «Дати») |

Нова категорія додається лише в `Categories::CODES`; міграція не потрібна.

### Категорії не захищені на рівні БД

`category` — звичайний `VARCHAR(16)`, а не `ENUM` (D-11): нова категорія не потребує міграції. Допустимі коди (`love`, `money`, `luck`, `work`, `travel`, `mood`) перевіряє код — з одного списку, який використовують валідація й фільтри. На `CHECK` у БД покладатися не можна: **MySQL 5.7 приймає `CHECK`, але ігнорує його**. Тому будь-який шлях запису у `phrases` (створення, оновлення, імпорт) мусить перевіряти категорію в коді.

### Пошук: регістр і діакритика

Колація `utf8mb4_unicode_ci` робить `LIKE` нечутливим до регістру **і до діакритики** (D-13). Перевірено на MySQL 5.7:

| Запит | Знаходить | Коментар |
|-------|-----------|----------|
| `sodien` | `Šodien` | латиські літери з діакритикою = базові (`š`=`s`, `ā`=`a`, `ū`=`u`, `ķ`=`k` перевірено) |
| `bus` | `būs` | |
| `ТЕСТ` | `тест` | регістр кирилиці не важливий |
| `елка` | `ёлка` | `ё` = `е` |
| `иога` | — | `й` ≠ `и`, не знаходить `йога` |
| 😀 | будь-який емодзі | всі 4-байтові символи в цій колації рівні між собою |

Для адмінського пошуку це зручно (не треба вводити діакритику), але має бути відомо: пошук за емодзі не розрізняє емодзі. Строгий варіант (`utf8mb4_bin` + `LOWER()`) гірше працює з кирилицею та латиською, тому не обраний.

## Тестова БД

Перевірки ендпоінтів з БД виконуються на окремій базі **`orakuls_test`** (D-14), не на робочій локальній `orakuls`.

- Базу створює `docker-compose` разом з основною: init-скрипт `docker/mysql-init/01-create-test-database.sql` (імена зашиті — `.sql` не читає змінні оточення; змінюєш `DB_USER`/`DB_NAME` в `.env` — онови файл). Користувач `orakuls` має доступ до обох баз. Init-скрипти MySQL виконуються лише при створенні volume, тож для вже існуючого потрібен одноразовий `docker compose down -v`.
- `tests/api.php` перед кожним прогоном скидає таблиці `orakuls_test`, застосовує міграції й заливає сід (`database/seed/phrases.php`), після чого викликає `Kernel` у процесі, без HTTP-сервера. Дані завжди однакові.
- **Запобіжник:** `Database\DatabaseGuard` дивиться на БД, до якої фактично підключено PDO (`SELECT DATABASE()`), а не на конфіг; `Seeder`, `bin/seed.php` і `tests/api.php` відмовляються працювати, якщо назва не закінчується на `_test`. Так не можна випадково стерти локальні дані чи прод. Код «стерти всі таблиці» живе лише в `tests/`.
- Сід — лише для тестової БД. Робоча `orakuls` після міграцій порожня, реальні фрази туди завантажує адмін через імпорт.
- Деталі запуску — [testing.md](testing.md).

### Склад сіду

30 фраз, `id` = порядок у файлі (1, 2, 3 …), `created_at` = `updated_at` = `2026-10-26 18:30:00` (`Seeder::CREATED_AT`). **Порядок не міняти, нові рядки додавати лише в кінець** — тести інших задач спираються на `id`.

| Ключі | Для чого |
|-------|----------|
| `love_1` … `mood_3` (18) | по 3 активні фрази з усіма мовами на кожну з 6 категорій |
| `hidden` | прихована фраза (love) |
| `only_lv`, `only_en`, `no_ru`, `blank_en` | порожні переклади різними мовами; `blank_en` — лише пробіли |
| `diacritics`, `cyrillic_case` | пошук `sodien`, `bus`, `тест` |
| `emoji`, `multiline` | емодзі та справжній перенос рядка |
| `len500` | рівно 500 символів (`š` і `😀`) |
| `html`, `like_chars` | `<script>…` зберігається як є; `%`, `_` і зворотний слеш для екранування `LIKE` |

## Розбіжність версій

Локальний образ — `mysql:5.7.44`, на хостингу — 5.7.38. Мінорна різниця не впливає на синтаксис, але остаточну перевірку схеми й запитів виконуємо на хостингу (BE-009, BE-010).
