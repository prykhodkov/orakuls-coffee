# Архітектурні рішення

Журнал рішень: що вирішили, чому, що відкинули. Нове рішення — наступний номер `D-0xx`; старі не видаляються, а, якщо змінились, позначаються `Замінено на D-0xx`.

---

## D-01 · Без фреймворка і без Composer
**Дата:** 2026-11-01 · **Статус:** прийнято

**Контекст.** ~10 ендпоінтів, shared-хостинг GoDaddy, обслуговування мінімальне.
**Рішення.** Власний роутер (~60 рядків) і автозавантаження через `spl_autoload_register`.
**Альтернативи.** Slim чи подібний мікрофреймворк — додає `vendor/`, який треба викладати й оновлювати, і залежність від його версій; Composer — немає на машині розробника й може бути недоступний на хостингу.
**Наслідки.** Менше залежностей і нічого оновлювати. Зате все потрібне пишемо самі (токен у BE-004, валідація в BE-006), а фреймворкових можливостей (middleware-ланцюжки, DI) немає — до них доведеться додавати власний простий код.

## D-02 · Локальне оточення в Docker
**Дата:** 2026-11-01 · **Статус:** прийнято

**Контекст.** На машині розробника немає PHP та MySQL, а версії мають збігатися з хостингом.
**Рішення.** `docker compose`: `php:8.4-cli` (вбудований сервер) + `mysql:5.7`.
**Альтернативи.** XAMPP або встановлення PHP/MySQL на Windows — версія MySQL 5.7 під Windows ставиться погано, розбіжності з продом.
**Наслідки.** Потрібен Docker Desktop. Образ `mysql:5.7` лише для x86 (на ARM знадобиться емуляція). Вбудований сервер PHP — не Apache, тож поведінку `.htaccess` локально не перевірити; це робимо на хостингу (BE-009).

## D-03 · PHP 8.4 і MySQL 5.7
**Дата:** 2026-11-01 · **Статус:** прийнято

**Рішення.** Беремо найновіші версії, що підтримує хостинг GoDaddy cPanel (див. [deployment.md](deployment.md)).
**Наслідки.** Код не використовує можливостей MySQL 8.0. MySQL 5.7 знято з підтримки розробником (2023) — ризик прийнято, бо хостинг іншого не дає; запасний варіант — MariaDB 10.6.

## D-04 · Єдиний формат помилок; несподіване — це 500 без деталей
**Дата:** 2026-11-01 · **Статус:** прийнято

**Рішення.** Усі помилки — `{ "error": { code, message, fields? } }` за `API.md`. Необроблений виняток і PHP warning → `500 server_error`, деталі лише в лог. Deprecated лише логується.
**Чому warning → помилка.** Мовчазний warning (наприклад, неіснуючий ключ масиву) дав би «успішну» відповідь із неправильними даними. Краще явний `500`, який видно в логах.
**Чому deprecated не ламає запит.** Хостинг може оновити мінорну версію PHP, і код не повинен падати через застаріле попередження.
Деталі — [error-handling.md](error-handling.md).

## D-05 · Невідомий метод на існуючий шлях → 404
**Дата:** 2026-11-01 · **Статус:** прийнято

**Рішення.** `404 not_found`, а не `405`.
**Чому.** У таблиці помилок `API.md` немає коду 405; відповідаємо в межах контракту. Фронт у будь-якому разі обробляє лише коди з таблиці.

## D-06 · Логи — лише стандартний `error_log()`
**Дата:** 2026-11-01 · **Статус:** прийнято (завершення — BE-009)

**Контекст.** Клієнт хостингом не опікується: налаштовуємо один раз, і воно має працювати роками.
**Рішення.** Власних файлів логів немає, тільки `error_log()`; пишемо лише несподіване (500, фатальні, збій БД у health).
**Відкинуто.** Власний файл `storage/logs/app.log`: без ротації він з часом з'їв би квоту хостингу, і його довелося б чистити вручну.
**Наслідки.** Куди йде лог на хостингу — налаштування PHP/cPanel; перевірити, що файл не публічний і ротується хостингом, треба в BE-009.

## D-07 · `GET /api/health` поза контрактом
**Дата:** 2026-11-01 · **Статус:** прийнято

**Контекст.** На cPanel-хостингу немає вбудованого health check. Для зовнішнього монітора (UptimeRobot тощо) та перевірки деплою потрібен легкий ендпоінт.
**Рішення.** `GET /api/health`: `200 {"status":"ok"}` або `503 {"status":"error"}` залежно від `SELECT 1`. У `API.md` не додаємо — фронт його не використовує. Версій і причин у відповіді немає.

## D-08 · Налаштування сесії MySQL задаються з коду
**Дата:** 2026-11-01 · **Статус:** прийнято

**Рішення.** При кожному з'єднанні: `utf8mb4` / `utf8mb4_unicode_ci`, `time_zone=+00:00`, суворий `sql_mode`.
**Чому.** Налаштування за замовчуванням на хостингу нам невідомі й можуть змінитись; код має поводитись однаково локально й на проді.

## D-09 · Типи в JSON задаються явно
**Дата:** 2026-11-01 · **Статус:** прийнято

**Контекст.** Запит F-003: PHP/PDO легко віддають числа й булеві рядками, порожні об'єкти — масивами; фронт на цьому ламається.
**Рішення.** Нативні prepared statements + `STRINGIFY_FETCHES=false`; `Json::object()` для порожніх об'єктів; явне приведення типів на межі БД → JSON.
Деталі — [api-conventions.md](api-conventions.md).

## D-10 · Заголовок `Authorization` читається з двох місць
**Дата:** 2026-11-01 · **Статус:** прийнято

**Рішення.** `Request` бере його з `HTTP_AUTHORIZATION`, а якщо немає — з `REDIRECT_HTTP_AUTHORIZATION`.
**Чому.** Apache з PHP як CGI/FastCGI часто не передає заголовок напряму; після `RewriteRule … E=HTTP_AUTHORIZATION` він інколи з'являється з префіксом `REDIRECT_`. Разом із правилом у `.htaccess` (BE-009) це закриває пункт 4 запиту F-003.

## D-11 · Категорія — `VARCHAR(16)` з перевіркою в коді, а не `ENUM`
**Дата:** 2026-11-01 · **Статус:** прийнято (реалізація — BE-002)

**Контекст.** Шість фіксованих категорій з `API.md`.
**Рішення.** Колонка `category VARCHAR(16) NOT NULL`; допустимі коди перевіряє код з єдиного списку (валідація BE-006/BE-007, фільтри BE-005).
**Альтернативи.** `ENUM` — захищає на рівні БД, але нова категорія вимагає міграції (`ALTER TABLE`), а на хостингу без CLI це ручна робота.
**Наслідки.** БД допустимість категорії не гарантує: MySQL 5.7 ігнорує `CHECK`. Будь-який шлях запису у `phrases` мусить перевіряти категорію в коді. Нову категорію додаємо в один список, міграція не потрібна.

## D-12 · Кожна задача приносить власні міграції; `login_attempts` — у BE-004
**Дата:** 2026-11-01 · **Статус:** прийнято

**Рішення.** BE-002 створює `phrases`, `migrations` і runner. Таблицю `login_attempts` створює BE-004 власною міграцією й додає в `schema.sql`. Старі записи там видаляються при перевірці ліміту, тож таблиця не росте безмежно.
**Чому.** Таблиця потрібна лише авторизації; не тримаємо в схемі нічого, що ще не використовується. Правило «задача, що змінює схему, додає міграцію й оновлює `schema.sql`» закріплено в `tasks/README.md`.

## D-13 · Пошук нечутливий до регістру й діакритики
**Дата:** 2026-11-01 · **Статус:** прийнято

**Контекст.** Колація `utf8mb4_unicode_ci` (єдина зі зручних, що працює в MySQL 5.7 з кирилицею й латиською) порівнює без урахування регістру та діакритики.
**Рішення.** Приймаємо це як поведінку адмінського пошуку: `sodien` знаходить `Šodien`.
**Альтернативи.** `utf8mb4_bin` + `LOWER()` — строгіший, але погано працює з кирилицею та латиською.
**Межі** (перевірено на MySQL 5.7): `ё` = `е`, але `й` ≠ `и`; усі емодзі між собою порівнюються як рівні. Деталі — [database.md](database.md).

## D-14 · Окрема тестова БД `orakuls_test`, сід — лише для неї
**Дата:** 2026-11-01 · **Статус:** прийнято (реалізація — BE-002)

**Контекст.** Тести ендпоінтів потребують відомих даних, а в робочій локальній БД лежать дані розробника (з BE-007 — реальні фрази).
**Рішення.** `docker-compose` створює `orakuls_test`. `tests/api.php` перед кожним прогоном застосовує міграції, очищає таблиці, заливає сід і викликає `Kernel` у процесі, без HTTP-сервера. Сід і `tests/api.php` відмовляються працювати з БД, назва якої не закінчується на `_test`.
**Альтернативи.** Тестувати на робочій БД — тести стирали б або засмічували дані; повторне використання HTTP-сервера на :8000 — він працює з робочою БД.
**Наслідки.** Для вже створеного Docker-volume потрібен одноразовий `docker compose down -v` (init-скрипти MySQL виконуються лише при створенні volume). Запобіжник за назвою БД захищає також прод.

## D-15 · Оператори міграцій виконуються по одному (`SqlSplitter`)
**Дата:** 2026-11-01 · **Статус:** прийнято

**Контекст.** Перевірено на `mysql:5.7` і PHP 8.4: `PDO::exec()` з кількома операторами **не кидає виняток, якщо помилка не в першому операторі**, а наступні запити на цьому з'єднанні падають з `2014 Cannot execute queries while there are pending result sets`. Міграція могла б «успішно» застосуватись наполовину.
**Рішення.** `Database\SqlSplitter` розбиває файл на оператори (рядки, ідентифікатори, `--`/`#`/`/* */`-коментарі, умовні `/*! */`; `DELIMITER` не підтримується), `Migrator` виконує їх у циклі окремими `exec()` і при збої кидає виняток із номером оператора, не записуючи міграцію в `migrations`. Той самий розбирач виконує `schema.sql` у тесті паритету.
**Альтернативи.** `PDO::MYSQL_ATTR_MULTI_STATEMENTS` / зміна `Db` — ховає проблему в налаштуваннях з'єднання, яке використовує і веб-шар, і не вирішує мовчазну втрату помилок. Підключати зовнішній розбирач — суперечить D-01.
**Наслідки.** У міграціях не можна процедури й тригери (потрібен `DELIMITER`). DDL неатомарний, тому міграція з кількома операторами пишеться ідемпотентно (`IF NOT EXISTS`).

## D-16 · `schema.sql` генерується з міграцій; два тести охороняють розходження
**Дата:** 2026-11-01 · **Статус:** прийнято

**Контекст.** Повний `schema.sql` потрібен для імпорту через phpMyAdmin, але файл, який пишеться вручну паралельно з міграціями, рано чи пізно розійдеться з ними.
**Рішення.** `bin/build-schema.php` (`Database\SchemaBuilder`) збирає `schema.sql` з `database/migrations/*.sql` детерміновано: DDL таблиці `migrations`, оператори кожної міграції, `INSERT IGNORE` її імені в облік. Вручну файл не редагується. Тест `schema.sql актуальний` (`tests/run.php`, `bin/build-schema.php --check`) ловить застарілий файл; тест **паритету** (`tests/api/database.php`) імпортує `schema.sql` в чисту тестову БД і порівнює схему з міграційною за `information_schema`.
**Альтернативи.** Дамп `mysqldump` після міграцій — залежить від клієнта й версії, дає шум у diff. Ручний файл — розходження.
**Наслідки.** Коментарі міграцій у `schema.sql` не переносяться. Задача, що додає міграцію, мусить запустити `bin/build-schema.php`, інакше `tests/run.php` впаде.

## D-17 · SQL живе в шарі `Repository`, контролер тонкий
**Дата:** 2026-11-01 · **Статус:** прийнято (реалізація — BE-003)

**Контекст.** До таблиці `phrases` звертатимуться чотири задачі: випадковий вибір (BE-003), список і фільтри (BE-005), запис (BE-006, BE-007) і статистика (BE-008). SQL у контролерах розповзся б між ними, а критерій «переклад порожній» довелося б повторювати.
**Рішення.** Запити до `phrases` — у `Repository\PhraseRepository`. Репозиторій отримує `PDO` у конструкторі й сам `Db::pdo()` не викликає; контролер лише розбирає ввід, викликає репозиторій і формує відповідь. Критерій «порожній переклад» — один метод `PhraseRepository::hasTextSql($lang)` (`TRIM(колонка) <> ''`): BE-003, BE-005 (`missing`) і BE-008 використовують його ж. `Repository` залежить від `Domain` і `Support`, але не від `Http`.
**Альтернативи.** SQL прямо в контролері — швидше для одного ендпоінта, але дублювання при BE-005/BE-008. Окремий ORM/Active Record — суперечить D-01.
**Наслідки.** Один додатковий клас на таблицю. `TRIM` в SQL обрізає лише пробіли, а `trim()` у PHP — усі пробільні символи; BE-006 при записі обрізає по-PHP-шному, тож розбіжність можлива лише для застарілих або внесених вручну даних (рядок із самих табуляцій SQL вважає непорожнім).

## D-18 · `exclude` — підказка «найкращого зусилля»: сміття ігнорується, `400` дає лише `lang`
**Дата:** 2026-11-01 · **Статус:** прийнято (рішення користувача; реалізація — BE-003)

**Контекст.** Фронт передає в `exclude` до 100 ID, які користувач уже бачив, і оновлює список «побачених» **лише після успішної відповіді**; при будь-якій помилці показує загальне повідомлення. `API.md` каже: «бекенд намагається їх уникнути».
**Рішення.** `Support\IdList::parse()` ніколи не кидає винятків: елемент, що не є невід'ємним цілим до 10 цифр (`abc`, порожній, `-5`, `1.5`, `+5`), мовчки пропускається (пробіли навколо числа толеруються); повтори прибираються; враховуються перші 200 коректних ID (удвічі більше, ніж тримає фронт), решта ігнорується; `exclude` не рядок (`exclude[]=1`) трактується як відсутній (для цього `Request::rawQuery()` замість `query()`, яке кидає `400` на масив). Ліміту за довжиною в символах немає. `400` на `/api/message` дає лише `lang`.
**Чому не `400` на поганий `exclude`.** Підказка не повинна ламати основну функцію. Помилка сама не лікується: фронт не оновив би список, і той самий поганий список застряг би, а користувач щоразу бачив би помилку. Ліміт за символами крихкий: ID ростуть, і 100 ID по 7 цифр (1014 символів у query) уже б його перевищили. Реальні розміри малі: 100 ID по 10 цифр — 1314 символів із кодованими комами (`%2C`), тоді як `LimitRequestLine` Apache за замовчуванням — 8190 байт (на хостингу перевіримо в BE-009). `max_input_vars=1000` рахує кількість змінних, а не довжину.
**Альтернативи.** Суворий розбір із `400` і ліміт довжини рядка в символах — див. вище. Ліміт у 200 ID (а не 100) — запас на випадок, якщо фронт збільшить свій список; береться початок списку, бо фронт передає ID від новішого до старішого.
**Наслідки.** Сміття в `exclude` мовчки втрачається: фронт про це не дізнається, а найгірший наслідок — користувач може раніше побачити повтор. Граничні випадки покриті юніт-перевірками `IdList` і `tests/api/message.php`.

## D-19 · Випадковий вибір одним запитом: `ORDER BY (id IN (…)) ASC, RAND() LIMIT 1`
**Дата:** 2026-11-01 · **Статус:** прийнято (реалізація — BE-003)

**Контекст.** Потрібна рівномірно випадкова активна фраза з непорожнім перекладом, бажано не з `exclude`, а якщо нічого іншого немає — будь-яка доступна (не `404`).
**Рішення.** Один запит. Вираз `(id IN (…))` дає `0` для непереглянутих і `1` для виключених, тож `ORDER BY … ASC, RAND()` спершу перемішує непереглянутих і лише за їх відсутності бере виключених. Це реалізує правило «ігнорувати `exclude`, якщо нічого не лишилось» без другого запиту. Якщо список порожній, `IN` і `ORDER BY (…)` у запит не додаються (`IN ()` у MySQL — синтаксична помилка). ID прив'язуються як `PDO::PARAM_INT`, ім'я колонки — з `Languages::column()`. Перевірено на `mysql:5.7`: розподіл рівномірний (3000 запитів по 28 кандидатів — лічильники 89…119 при середньому 107, σ≈10), серед не виключених теж без зсуву в бік менших ID; запит зі 200 плейсхолдерами на 600 фразах — ≈1 мс.
**Альтернативи.**
- *Два запити* (спершу `NOT IN`, потім без нього) — удвічі більше звернень до БД і складніша гілка.
- *`NOT IN` із запасним варіантом у PHP* — те саме, плюс залежність від порядку виконання двох запитів.
- *Випадковий номер у PHP* (`COUNT(*)`, потім `LIMIT 1 OFFSET n`) — два запити, а рівномірність при виключених ID потребує обчислень у PHP.
- *Завантажити кандидатів у PHP і вибрати там* — тягне всю таблицю на кожен запит.
**Наслідки.** `ORDER BY RAND()` сортує всіх кандидатів: прийнятно для ~600 фраз (≈1 мс); якщо таблиця виросте на порядки, вибір треба буде переглянути.

## D-20 · Захист `/api/admin/*` — guard у `Kernel` до маршрутизації, за замовчуванням закритий
**Дата:** 2026-11-01 · **Статус:** прийнято (реалізація — BE-004)

**Контекст.** Адмінських ендпоінтів буде десяток (BE-004 … BE-008). Якщо перевірку токена викликає кожен контролер (або вішається на кожен маршрут окремо), один забутий виклик — це відкрита адмінка. Для задачі про безпеку це неприйнятно.
**Рішення.** `Http\AdminGuard::check()` викликається в `Kernel::handle()` **до** `Router::dispatch()`. Будь-який шлях, що дорівнює `/api/admin` або починається з `/api/admin/`, вимагає дійсного `Authorization: Bearer <token>`; єдиний виняток — `POST /api/admin/auth/login`. Невідомий адмін-шлях без токена дає `401`, а не `404`, тож по відповідях не видно, які адмін-ендпоінти існують. Контролери перевірку токена не повторюють. Конфігурація автентифікації (`AuthConfig`) читається **ліниво** — лише для адмін-шляхів: помилка в `TOKEN_SECRET` не повинна класти публічні `/api/message` і `/api/health`. Некоректна конфігурація на адмін-шляху — `500`, доступ не відкривається ніколи (fail-closed).
**Альтернативи.**
- *Middleware на кожен маршрут* або виклик у кожному контролері — захист «за згодою»: новий ендпоінт без виклику лишився б відкритим.
- *Список захищених шляхів* — те саме, навпаки: незнайомий шлях не потрапив би до списку.
**Наслідки.** Новий адмін-ендпоінт у `routes.php` захищений без жодних дій. Тестове ядро `kernelWith()` збирається без guard'а (`Kernel` приймає його необов'язковим параметром), боєве `Kernel::create()` — завжди з ним; це зафіксовано тестом.

## D-21 · Токен — JWT HS256 без бібліотек, ключ із секрету та хеша пароля, строга перевірка, термін 7 діб
**Дата:** 2026-11-01 · **Статус:** прийнято (термін — рішення користувача)

**Контекст.** Контракт формат токена не фіксує (фронт його не розбирає). Бібліотеки заборонені D-01; сесії й таблиця токенів роблять бекенд stateful.
**Рішення.** `Auth\TokenService`: `base64url(header).base64url(payload).base64url(підпис)`, header рівно `{"alg":"HS256","typ":"JWT"}`, payload `{"sub", "iat", "exp"}`, підпис `HMAC-SHA256` над `header.payload`. Ключ підпису = `HMAC-SHA256` з ключем `TOKEN_SECRET` над рядком `ADMIN_PASSWORD_HASH` (сирі 32 байти): **зміна пароля, секрету або логіна анулює всі видані токени** — списку відкликаних не потрібно. Перевірка строга й у фіксованому порядку: довжина ≤ 2048 → рівно три непорожні частини → header **порівнюється як константа** (поле `alg` з токена не читається, тож `none`/`HS512` неможливі) → підпис через `hash_equals` по сирих 32 байтах → лише після цього розбір payload → типи (`sub` рядок, `iat` і `exp` цілі) → `exp > now` (суворо) → `sub` збігається з `ADMIN_LOGIN`. base64url декодується канонічно (після декодування кодується назад і порівнюється з входом): паддінг `=`, стандартний алфавіт і «зайві біти» відхиляються. Термін — `TOKEN_TTL_HOURS`, за замовчуванням **168 год (7 діб)**, діапазон 1…720; порожнє значення = за замовчуванням.
**Чому 7 діб.** Рішення користувача: адмін рідше вводить пароль. Компроміс: вкрадений токен діє довше, а фронт тримає його в `localStorage`; пом'якшення — зміна пароля чи `TOKEN_SECRET` анулює все.
**Альтернативи.** Бібліотека JWT (D-01); випадковий токен у таблиці (stateful, зайва таблиця й запит на кожен виклик); ключ лише з `TOKEN_SECRET` (зміна пароля не анулювала б токени — відкинуто).
**Наслідки.** Достроково відкликати один токен не можна — лише всі разом. `logout` на бекенді немає (токен stateless, фронт просто забуває його).

## D-22 · Ліміт спроб входу — за IP, лише `REMOTE_ADDR`, 5 спроб за 15 хвилин
**Дата:** 2026-11-01 · **Статус:** прийнято (перевірка IP на хостингу — BE-009)

**Рішення.** `Auth\LoginRateLimiter` + таблиця `login_attempts` (`ip`, `attempted_at` у UTC). 5 невдалих спроб з одного IP за 900 с → `429 rate_limited` із `Retry-After` (секунди до виходу найстарішої з п'яти спроб із вікна, 1…900). Заблоковані запити в таблицю **не записуються** (блокування не продовжується) і `password_verify` не запускають; успішний вхід лічильник не збільшує. Прострочені записи видаляються під час перевірки (таблиця не росте). IP — лише `REMOTE_ADDR` (`Request::ip`, валідований `filter_var`; інакше `unknown`); `X-Forwarded-For` та інші заголовки ігноруються.
**Чому за IP, а не за логіном.** Логін адміна один і відомий: ліміт за логіном дозволив би будь-кому заблокувати адміна, просто надсилаючи неправильні паролі.
**Чому не `X-Forwarded-For`.** Його підробляє будь-який клієнт: довіра йому знімає ліміт (кожен запит «з нового IP») або дозволяє заблокувати чужу адресу.
**Чому саме такий запит.** Один `SELECT … ORDER BY attempted_at DESC LIMIT 5` дає і кількість спроб у вікні, і вік п'ятої — з нього рахується `Retry-After`. Вибірка «останніх п'яти» (а не `COUNT`) стійка до одночасних запитів, що проскочили перевірку разом.
**Наслідки.** Спільний IP (офіс, NAT) ділить ліміт. Чи є `REMOTE_ADDR` на хостингу справжнім IP клієнта (а не адресою проксі), перевіряється в BE-009 — див. [deployment.md](deployment.md). Відмови `400`/`422` ліміт не рахує (див. D-23).

## D-23 · Порядок перевірок логіну, `password_verify` без короткого замикання, коди відповідей
**Дата:** 2026-11-01 · **Статус:** прийнято

**Рішення.** `AuthController::login` виконує кроки в такому порядку: конфігурація (`500`) → тіло (`400` для порожнього/не-JSON/не-об'єкта) → валідація полів (`422`: `login` і `password` — непорожні рядки, пароль ≤ 1024 байт; `fields`: `required` / `too_long`) → ліміт (`429`) → перевірка облікових даних (`401`). Відмови на перших кроках у спроби не рахуються. `password_verify` виконується **завжди**, навіть при неправильному логіні, а умова невдачі обчислюється без короткого замикання (`$loginOk` і `$passwordOk` рахуються окремо, логін порівнюється через `hash_equals`): інакше неправильний логін відповідав би на ~170 мс швидше, і по часу можна було б дізнатись, чи існує логін. Повідомлення `401` однакове для будь-якої причини (`Invalid credentials`). Некоректна конфігурація (порожній/невалідний `ADMIN_PASSWORD_HASH`, `TOKEN_SECRET` коротший за 32 символи, відсутній `ADMIN_LOGIN`, `TOKEN_TTL_HOURS` поза 1…720) → `500 server_error` і на логіні, і на guard'і; у `error_log` — один рядок з **назвою** змінної, без значень.
**Чому `422`, а не `401`, для порожніх полів.** Фронт сам не відправляє порожні поля, тож це помилка клієнта, а не спроба підбору; рахувати її в ліміт означало б давати змогу заблокувати чужий IP порожніми запитами.
**Чому ліміт до `password_verify`.** bcrypt у PHP 8.4 коштує ≈170 мс CPU на запит; без цього заблокований клієнт і далі витрачав би процесор сервера.
**Наслідки.** Помилка конфігурації помітна одразу (`500` замість «усі паролі неправильні»), але потребує перегляду логу, бо клієнту причину не показуємо.
