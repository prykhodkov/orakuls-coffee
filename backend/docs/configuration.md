# Конфігурація

Конфігурація — змінні з файлу `.env` та змінні процесу. **Змінні процесу мають пріоритет над файлом** (зручно для CI та Docker).

## Де що лежить

| Файл | У git | Призначення |
|------|-------|-------------|
| `backend/.env.example` | так | Шаблон із заглушками — документує, які змінні існують |
| `backend/.env` | **ні** (`.gitignore`) | Реальні значення на конкретному оточенні |

Файл читає `Support\Config::load()` із `APP_ROOT/.env` (`APP_ROOT` — корінь застосунку, `bootstrap.php` визначає його як батьківську папку `src/`). Якщо файлу немає — це не помилка; обов'язкові змінні перевіряються при першому використанні, і `Config::require()` кидає виняток із назвою відсутньої змінної.

## Формат `.env`

```
# коментар
KEY=value
KEY="значення з пробілами"
HASH='$2y$10$abc…'
```

- Один рядок — одна змінна; порожні рядки й `#`-коментарі ігноруються.
- Лапки (`"…"` або `'…'`) знімаються. **Інтерполяції нема** — `$` береться як звичайний символ, тому хеші паролів безпечні для самого застосунку. Але `.env` читає і `docker compose`, який у подвійних лапках трактує `$…` як змінну, тож хеш — **лише в одинарних лапках** (див. нижче).

## Змінні

| Змінна | Обов'язкова | За замовчуванням | Призначення |
|--------|-------------|------------------|-------------|
| `DB_HOST` | так | — | Хост MySQL. У Docker — `db` |
| `DB_PORT` | ні | `3306` | Порт MySQL |
| `DB_NAME` | так | — | Назва бази (локально `orakuls`). Тести ендпоінтів (`tests/api.php`) самі підставляють `orakuls_test` і від цього значення не залежать |
| `DB_USER` | так | — | Користувач БД |
| `DB_PASS` | ні | порожній | Пароль БД |
| `DB_ROOT_PASS` | лише Docker | `root` | Root-пароль локального MySQL; читає `docker-compose.yml`, застосунок — ні |
| `ADMIN_LOGIN` | для адмінки | — | Логін єдиного адміна. Порожній або відсутній → `500` на адмін-шляхах (fail-closed) |
| `ADMIN_PASSWORD_HASH` | для адмінки | — | Хеш пароля адміна (`password_hash`), не сам пароль; готується `bin/hash-password.php`. Порожній або «не хеш» → `500` |
| `TOKEN_SECRET` | для адмінки | — | Ключ підпису токена: випадковий рядок **не коротший за 32 символи**, на кожному оточенні свій. Коротший або порожній → `500` |
| `TOKEN_TTL_HOURS` | ні | `168` (7 діб) | Термін дії токена в годинах, ціле число 1…720. Порожнє значення = за замовчуванням; поза діапазоном або нечислове → `500` |

`docker-compose.yml` підставляє `DB_NAME`, `DB_USER`, `DB_PASS`, `DB_ROOT_PASS` у контейнер MySQL (зі значеннями за замовчуванням `orakuls`/`orakuls`/`orakuls`/`root`), тому `.env` і локальна БД завжди узгоджені.

## Облікові дані адміна (BE-004)

Адмін один, його дані лише в конфігурації (ендпоінтів створення/зміни акаунта немає). Усі команди — з папки `backend/`.

1. **Хеш пароля.** Пароль не передається аргументом (він лишився б в історії оболонки) — скрипт читає його зі stdin:

   ```
   docker compose exec php php bin/hash-password.php            # у терміналі: запитує пароль двічі, без відлуння
   printf '%s\n' 'мій-довгий-пароль' | docker compose exec -T php php bin/hash-password.php   # з pipe (CI, скрипти)
   ```

   Пароль: щонайменше 12 символів і не більше 72 байтів (bcrypt ігнорує решту). Скрипт друкує готовий рядок `ADMIN_PASSWORD_HASH='$2y$…'` і нічого не пише у файли. Хеш argon2id теж працюватиме (`password_verify` розпізнає алгоритм з хеша), але на хостингу він може бути недоступним, тому за замовчуванням bcrypt.
2. **Секрет токена:** `docker compose exec php php -r "echo bin2hex(random_bytes(32));"` (64 символи; мінімум 32). На кожному оточенні свій.
3. **Вписати в `.env`** (не через `echo`/`sed` — оболонка розкриє `$`):

   ```
   ADMIN_LOGIN=admin
   ADMIN_PASSWORD_HASH='$2y$12$…'
   TOKEN_SECRET='…64 символи…'
   TOKEN_TTL_HOURS=168
   ```

**Хеш — завжди в одинарних лапках.** Він містить `$`; у подвійних `docker compose` вважає `$2y…` змінною і сиплє попередженнями (перевірено; одинарні — ні). Власний парсер `Config` обидва варіанти читає однаково, але `.env` читає й `docker compose`. Перевірка: `docker compose -f docker-compose.yml config -q` не друкує попереджень.

**Зміна пароля** = новий хеш у `.env` (процедура вище). Це **анулює всі видані токени** (ключ підпису виводиться з `TOKEN_SECRET` і хеша), тож адмін увійде заново. Те саме при зміні `TOKEN_SECRET` чи `ADMIN_LOGIN` — зручний спосіб «вийти всюди», якщо токен міг витекти.

**Помилки конфігурації** не відкривають доступ: порожній чи «не хеш» `ADMIN_PASSWORD_HASH`, `TOKEN_SECRET` коротший за 32 символи, порожній `ADMIN_LOGIN`, некоректний `TOKEN_TTL_HOURS` дають `500 server_error` на логіні й на будь-якому `/api/admin/*`. Причина — один рядок у `error_log` (`Auth config invalid: …`) з назвою змінної, без значення (`docker compose logs php`). Публічні `/api/message` і `/api/health` від цього не залежать. Для прод-оточення — процедура з BE-009.

## Секрети

- Реальні значення — лише в `backend/.env` на потрібній машині, у репозиторій не потрапляють.
- Пароль адміна зберігається **тільки як хеш**.
- На хостингу `.env` лежить поза `public_html` (див. [deployment.md](deployment.md)).
- Значення секретів не логуються й не повертаються в API.

## Додати нову змінну

1. Прочитати її через `Config::get('NAME', 'default')`, `Config::require('NAME')` або `Config::bool('NAME')`.
2. Додати в `.env.example` із коментарем.
3. Додати рядок у таблицю вище.
