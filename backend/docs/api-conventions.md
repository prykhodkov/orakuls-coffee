# Як код реалізує контракт API

Контракт — [../../docs/API.md](../../docs/API.md), він єдине джерело правди. Цей документ — про правила в коді, які гарантують, що відповіді відповідають контракту. Помилки описані окремо: [error-handling.md](error-handling.md).

## Типи в JSON

Фронт чутливий до типів (`"42"` ≠ `42`, `"0"` у JS істинне), тому:

| Правило | Як забезпечено |
|---------|----------------|
| Числа — числами (`id`, `total`, `page`, `perPage`…) | PDO: нативні prepared statements (`EMULATE_PREPARES=false`) і `STRINGIFY_FETCHES=false`; у сумнівних місцях — явне `(int)` |
| Булеві — булевими (`isActive`) | TINYINT з MySQL приводити через `(bool)` |
| Об'єкти — об'єктами, навіть порожніми (`text`, `byCategory`, `missing`, `fields`) | `Json::object($array)` перетворює `[]` на `{}`; `json_encode([])` дає `[]` |
| Масиви — масивами (`items: []`, не `null`) | Порожній список лишається `[]` |
| Дати — ISO 8601 UTC, `2026-10-26T18:30:00Z` | Сесія MySQL у `+00:00`, форматування в одному місці — `Support\Iso8601::fromDb()` |
| Ідентифікатори — цілі числа | Нечисловий `{id}` у шляху → `404 not_found` |
| Юнікод не екранується | `Json::encode()` використовує `JSON_UNESCAPED_UNICODE` |

Усі відповіді кодуються лише через `Response::json()` → `Json::encode()`, напряму `json_encode` у контролерах не викликаємо.

## Запит

- `Request::query('name')` — рядок або `null`; масив у параметрі → `400`. Для **обов'язкових** параметрів (`lang`).
- `Request::rawQuery('name')` — сире значення без перевірок: рядок, масив або `null`. Для **параметрів-підказок** (`exclude`), де некоректний ввід має ігноруватись, а не давати `400`.
- Принцип: **обов'язковий параметр, який клієнт сформував неправильно, — `400`; параметр-підказка, який можна безпечно проігнорувати, — ніколи не `400`** (D-18). Підказка не повинна ламати основну функцію, а помилка, яку клієнт не вміє лікувати, застрягла б назавжди.
- Принцип для адмінки: **явні фільтри, які адмін обирає сам, строгі** — невідоме значення це `400` (D-25), бо мовчки показати «не те» гірше за помилку. Підказки лояльні (`exclude`), явні фільтри строгі (`GET /api/admin/phrases`). Порожній рядок (`category=`) для явних фільтрів — те саме, що параметра немає. Регулярні вирази на вході пишуться з модифікатором `D`: без нього `$` пропускає перенос рядка наприкінці (`"1\n"`).
- `Request::json()` — тіло як асоціативний масив; порожнє / не-JSON / не-об'єкт → `400`. **Валідність полів** (типи, довжини, довідники) перевіряє окремий код і кидає `ApiException::validation()` → `422`.
- `Request::header('Authorization')` — імена заголовків нечутливі до регістру. На Apache заголовок читається з `HTTP_AUTHORIZATION` або `REDIRECT_HTTP_AUTHORIZATION`.
- Кінцевий `/` у шляху ігнорується.

## Відповідь

- `Response::json($data, $status = 200, $headers = [])`.
- `Response::noContent()` → `204` без тіла і без заголовків. Для `DELETE` фраз потрібен `no-store`, тому там `new Response(204, null, ['Cache-Control' => 'no-store'])` (D-29).
- Публічні та адмінські відповіді мають `Cache-Control: no-store` (за контрактом для `GET /api/message`; для адмінки — щоб браузер не показував застарілі дані).
- Заголовок `X-Powered-By` прибирається.

## Додати ендпоінт

1. Переконатися, що він є в `API.md`. Нового там немає → спершу запит у `docs/BACK-TO-FRONT.md` (правила — `docs/README.md`).
2. Створити контролер `src/Controller/…Controller.php`:

   ```php
   final class ExampleController
   {
       public function show(Request $request, array $params): Response
       {
           $id = ctype_digit($params['id']) ? (int) $params['id'] : throw ApiException::notFound();

           return Response::json(['id' => $id]);
       }
   }
   ```

3. Зареєструвати маршрут у `src/routes.php` — шлях **з `/api`**:

   ```php
   $router->get('/api/example/{id}', [new ExampleController(), 'show']);
   ```

4. Додати перевірки: логіку — в `tests/run.php`, наскрізну поведінку — в `tests/smoke.php` ([testing.md](testing.md)).
5. Позначити зміни в `docs/BACKEND.md`, якщо вони впливають на фронт або розгортання.

Адмінські ендпоінти (шлях під `/api/admin/`) додаються так само, але **нічого для захисту робити не треба** — див. нижче.

## Адмінка: токен і guard (BE-004)

Контракт — `API.md` → «Авторизація».

- **Guard автоматичний** ([D-20](decisions.md)). `Kernel` перед маршрутизацією викликає `Http\AdminGuard`: будь-який шлях `/api/admin` чи `/api/admin/…`, окрім `POST /api/admin/auth/login`, вимагає `Authorization: Bearer <token>`. Новий адмін-ендпоінт у `routes.php` захищений без жодних дій у контролері; **контролер перевірку токена не повторює** і не повинен покладатися на власну. Невідомий адмін-шлях без токена дає `401`, не `404`.
- **Схема `Authorization`:** `Bearer` нечутлива до регістру, рівно один пробіл, токен із трьох частин (`A-Za-z0-9_-`). Інша схема, порожній токен, зайві пробіли, `Bearer` без пробілу → `401`. Повідомлення завжди `Unauthorized`.
- **Конфігурація автентифікації** (`AuthConfig::fromEnv()`) читається лише для адмін-шляхів; некоректна → `500` і на логіні, і на guard'і. Публічні шляхи від неї не залежать.
- **`Cache-Control: no-store`** — у всіх адмінських відповідях (передається явно: `Response::json` його сам не додає; помилки його мають завжди).
- **IP клієнта** — `Request::ip`: лише `REMOTE_ADDR` (валідований `filter_var`), інакше `'unknown'`; конструктор приймає його останнім параметром зі значенням за замовчуванням. `X-Forwarded-For` не читається ніколи ([D-22](decisions.md)).
- **Ендпоінти:** `POST /api/admin/auth/login` → `200 {token, expiresAt}` (`expiresAt` — `Iso8601::fromTimestamp()`, UTC з `Z`); `GET /api/admin/auth/me` → `200 {"login": "<ADMIN_LOGIN>"}`. Коди: `400` (порожнє/не-JSON тіло), `422` (порожні чи нерядкові поля, пароль > 1024 байт), `401` (`Invalid credentials`), `429` + `Retry-After`. Докладно — [error-handling.md](error-handling.md).
- **Токен** stateless: `logout` немає, фронт просто забуває його; термін — 7 діб ([D-21](decisions.md)).

## `GET /api/message` (BE-003)

Публічний, без авторизації; контракт — `API.md`. Реалізація — `MessageController` + `PhraseRepository::findRandom()`.

| Що | Як |
|----|----|
| Відповідь `200` | `{ "id": 42, "lang": "lv", "text": "…" }` — рівно ці ключі в цьому порядку; `id` — число; `text` — як у БД (без `htmlspecialchars` і `trim`, юнікод не екрануються) |
| Заголовок | `Cache-Control: no-store` (передається явно в контролері; `Response::json` його сам не додає) |
| `lang` | обов'язковий; `lv` / `en` / `ru` у нижньому регістрі без пробілів. Відсутній, порожній, невідомий, `LV`, `lang[]=lv` → `400 bad_request` |
| `exclude` | необов'язковий, ID через кому — **підказка**: ніколи не дає `400` (див. нижче) |
| Кандидати | `is_active = 1` і непорожній текст мовою `lang` (`PhraseRepository::hasTextSql()`), усі категорії разом |
| Немає кандидатів | `404 not_found` |
| Інший метод | `404 not_found` (як для будь-якого шляху, див. D-05) |

Правила `exclude` (`Support\IdList::parse()`, D-18):

- розбиття за комою, пробіли навколо числа обрізаються; елемент, що не є невід'ємним цілим до 10 ASCII-цифр (`abc`, порожній, `-5`, `+5`, `1.5`, `1e3`), мовчки пропускається;
- повтори прибираються, враховуються перші 200 коректних ID (сміття в ліміт не рахується), решта ігнорується; розглядається не більше 1000 фрагментів, тож рядок на мегабайти не шкодить; ліміту за довжиною в символах немає;
- `exclude` не рядок (`exclude[]=1`) трактується як відсутній;
- виключені фрази не вибираються, поки є інші кандидати; якщо інших немає — `exclude` ігнорується і повертається будь-яка доступна (D-19).

## `GET /api/admin/phrases` і `GET /api/admin/phrases/{id}` (BE-005)

Під `AdminGuard` (D-20): без токена `401`. Реалізація — `PhraseController` + `PhraseRepository::search()`/`find()`, фраза — `Domain\Phrase`.

**Параметри списку** (усі необов'язкові; порожній рядок = параметра немає; розбір — `PhraseController::parseFilter()`):

| Параметр | Допустимо | Інакше |
|----------|-----------|--------|
| `category` | точний код з `Categories::CODES` (`love`, `money`, `luck`, `work`, `travel`, `mood`) | `400` (`LOVE`, `love `, `x`) |
| `missing` | `lv`, `en` або `ru`: переклад цією мовою порожній після `TRIM` | `400` (`de`, `EN`) |
| `isActive` | рівно `true` або `false` | `400` (`1`, `True`, `yes`) |
| `search` | підрядок у будь-якій з трьох мов; `trim()`; порожній після обрізання = немає; нечутливий до регістру й діакритики (D-13); `%`, `_`, `\` шукаються як звичайні (D-24) | довший за 200 **символів** → `400` |
| `page` | ціле 1…999 999 999 (`^[1-9][0-9]{0,8}$`), за замовчуванням `1` | `400` (`0`, `-1`, `1.5`, `abc`, `01`, `1000000000`) |
| `perPage` | ціле 1…100 (`^[1-9][0-9]{0,2}$` і ≤ 100), за замовчуванням `50` | `400` (`0`, `101`, `050`, `abc`) |

Параметр-масив (`category[]=love`) — `400`. Повідомлення `400` містять назву параметра, але не повторюють значення. Фільтри комбінуються через `AND`. Відхилений запит не виконує жодного SQL.

**Відповідь `200`:** `{ "items": Phrase[], "total", "page", "perPage" }` — ключі в цьому порядку; `total` — кількість після фільтрів (а не загальна), `page` і `perPage` — застосовані значення; сортування `id` за спаданням; `Cache-Control: no-store` (і у `200`, і в `400`, `404`). `Phrase` — `{ id, category, text: { lv, en, ru }, isActive, createdAt, updatedAt }`: `id` — число, `isActive` — boolean, порожній переклад — `""`, дати — ISO 8601 UTC.

- **Сторінка за межами діапазону** — `200`, `items: []` (масив), правильний `total`, той самий `page`. Фронт після видалення останнього запису на сторінці сам зменшує номер і перепитує, тож `400` тут було б помилкою.
- **Порожній результат** — `items: []`, `total: 0`.
- **`GET /api/admin/phrases/{id}`:** `id` — лише канонічне ціле (`^[1-9][0-9]{0,9}$`, модифікатор `D`); `007`, `1.5`, `abc`, `-1`, `0`, `1e3`, 11 цифр, пробіл чи перенос рядка в кінці → `404 not_found` без звернення до БД; формально коректний, але неіснуючий `id` → `404` після одного запиту.
- **Кількість запитів:** список — рівно 2 (сторінка + `COUNT(*)`, D-26), фраза — 1, відхилені — 0. Контролює `statementCount()` у тестах.

## `POST`, `PUT`, `DELETE /api/admin/phrases` (BE-006)

Під `AdminGuard` (D-20): без токена `401` навіть із невалідним тілом. Реалізація — `PhraseController` (`create`/`update`/`delete`), `PhraseValidator`, `PhraseRepository::create()`/`update()`/`delete()`; рішення — [D-27 … D-29](decisions.md).

| Ендпоінт | Успіх | Тіло |
|----------|-------|------|
| `POST /api/admin/phrases` | `201` + `Phrase` | `{ category, text: { lv, en, ru }, isActive? }` |
| `PUT /api/admin/phrases/{id}` | `200` + `Phrase` | те саме; **повна заміна** `category`, `text`, `isActive` |
| `DELETE /api/admin/phrases/{id}` | `204` без тіла | немає |

**Порядок перевірок** (відхилений запит не виконує жодного SQL):

- `POST`: тіло (`400`) → валідація (`422`) → запис → `201`;
- `PUT`: формат `id` (`404`) → тіло (`400`) → валідація (`422`) → запис (немає фрази — `404`) → `200`. Тобто `PUT` неіснуючого `id` з невалідним тілом дає `422`, а з валідним — `404`;
- `DELETE`: формат `id` (`404`) → видалення (немає фрази — `404`) → `204`.

`id` у шляху — лише канонічне ціле (`^[1-9][0-9]{0,9}$/D`), як у `GET /{id}`: `007`, `abc`, `0`, `1.5`, `-1`, 11 цифр, `1%0A` → `404`.

**Тіло запису.** `Request::json()` дає `400` для порожнього тіла, не-JSON, JSON-не-об'єкта (число, рядок, список), глибини > 32, невалідного UTF-8 і lone surrogate в JSON-рядку. Далі `PhraseValidator::validate()` збирає **всі** помилки полів в один `fields` (`422 validation_error`); ключі йдуть у порядку `category`, `text` або `text.lv`/`text.en`/`text.ru`, `isActive`. **Невідомі ключі ігноруються** (на верхньому рівні — `id`, `createdAt`…, і всередині `text` — `de`); `id` з тіла `id` фрази не змінює.

| Ключ у `fields` | Код | Коли |
|-----------------|-----|------|
| `category` | `required` | ключа немає або `null` |
| `category` | `invalid` | не рядок або не з `Categories::CODES` (`LOVE`, `love `, `5`, `["love"]`, `""`) |
| `text` | `required` | ключа немає |
| `text` | `invalid` | не об'єкт: рядок, число, `null`, `true`, непорожній список (`["a","b","c"]`) |
| `text` | `empty` | `text` — об'єкт, жодної помилки `text.*` немає, і всі три тексти порожні після trim |
| `text.lv` / `text.en` / `text.ru` | `required` | `text` — об'єкт без цього ключа; порожній `text` (`{}` чи `[]`) дає `required` для всіх трьох |
| `text.xx` | `invalid` | не рядок (число, `null`, масив, `bool`); невалідний UTF-8; після trim є керівний символ (`U+0000–U+0008`, `U+000B`, `U+000C`, `U+000E–U+001F`, `U+007F`; дозволені `\t \n \r`) |
| `text.xx` | `too_long` | після trim понад 500 **символів** (не байтів; емодзі = 1) |
| `isActive` | `invalid` | не `bool` (`1`, `0`, `"yes"`, `"true"`, `null`); ключа немає → `true` |

- Текст зберігається **trimmed** (юнікодний trim як у JS `trim()`: NBSP, `U+3000`, `U+FEFF`, `U+2028` … прибираються; `U+200B` і `U+0085` — ні), як plain text: `\n`, `\r\n` і `\t` лишаються, HTML не екранується й не вилучається. Порожній переклад (`""`) дозволений, якщо інша мова непорожня.
- `Cache-Control: no-store` — на `201`, `200`, `204` і на всіх помилках.
- `createdAt` встановлюється при створенні (`createdAt = updatedAt`) і не змінюється; `updatedAt` оновлюється при кожному `PUT`.
- Кількість SQL-запитів: відхилені — 0; `POST` — 2 (INSERT + SELECT); `PUT` — 2 (UPDATE + SELECT), навіть для неіснуючого `id`; `DELETE` — 1.

## Службові ендпоінти поза контрактом

`GET /api/health` — для моніторингу та перевірки розгортання. Фронт його не використовує і в `API.md` його немає. Відповіді: `200 {"status":"ok"}`, `503 {"status":"error"}` (БД недоступна); версій і деталей у відповіді немає.
